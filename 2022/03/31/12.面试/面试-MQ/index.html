五、MQ

格式说明：每题先 口述版，下方 具体介绍。RB=RabbitMQ，KF=Kafka。

5.1 为什么用 MQ 与选型

M1. 引入 MQ 解决什么问题？

口述版： 四个词：异步减 RT、削峰保护下游、解耦上下游、最终一致（发消息驱动别的系统）。比如下单后发 MQ 做积分、短信，不用等全部做完才返回。

具体介绍

  • 异步：主流程只写 DB+发 MQ，消费者慢慢处理。
    • 面试可量化：接口 RT 从「串行调 3 个 RPC 各 200ms」降到「写库 50ms + 发 MQ 10ms」。
    • RB/KF/Rocket 均支持异步发送；同步 send 仅用于强校验场景（confirm / acks 结果）。
  • 削峰：秒杀流量先进队列，消费者按能力拉。
    • 队列深度 = 生产 TPS × 持续时间 − 消费 TPS × 持续时间；消费能力不足时 depth/lag 单调涨（见 M15、M55）。
  • 解耦：接口契约变成 Topic/Queue，改消费者不影响生产者编译。
    • RB：Exchange + Binding 改路由；KF：新 Consumer Group 订阅同一 Topic；Rocket：Tag/Filter 订阅子集。
  • 最终一致：跨库、跨服务用事件驱动。
    • 与 M6、M21 本地消息表 / Outbox / 事务消息衔接；监控「pending 消息表条数」「lag」作为一致性滞后指标。
  • 边界：MQ 解决跨进程协作，不替代缓存、不解决强一致读；选型仍要看 M2/M5。
  • 失败语义：异步链路要有 可查询状态 + 补偿（M52），避免用户重复提交。

面试追问

  • 异步后用户如何知道最终结果？失败如何通知与重试？（答： 提供 订单/任务状态查询、WebSocket/轮询、短信邮件；失败走 重试 + DLQ + 告警，业务表记录 终态与幂等键。）
  • 削峰后 lag 长期不降，你会从哪三层（生产/ Broker/消费）查？

生产注意

  • 上线前必须有 lag、DLQ、confirm/发送失败率告警；无监控勿强依赖 MQ。
  • 消费者扩容前先算 DB 连接池与下游 QPS（M51），否则 lag 仍涨。

M2. MQ vs RPC vs Redis Stream？

口述版： 要立刻结果用 RPC；要缓冲、广播、堆积、回溯用 MQ；轻量队列、已有 Redis 可 Stream/List，但缺完整 ACK、消费组、运维生态时用专业 MQ。

具体介绍

方式 适用 与 MQ 边界
RPC 强同步、查即得 超时、重试、熔断在客户端；无天然堆积
MQ 异步、削峰、多订阅者 有 backlog、可 DLQ、可回溯（KF 尤其强）
Redis Stream/List 简单队列、短消息、已有运维 Stream 有消费组与 ACK，但无 RB 级路由、无 KF 级日志 retention 生态
  • 选型口诀：要「等结果」→ RPC；要「扛峰值 + 多下游」→ MQ；Redis 适合 低 QPS、短 retention、团队不想上新中间件 的过渡方案。
  • 组合用法：RPC 查实时状态 + MQ 发变更事件很常见；Stream 适合 已有 Redis、量级不大 的过渡。
  • 迁移成本：从 List/Stream 迁到 RB/KF 要重做 ack、路由、运维面板。

面试追问

  • Redis Stream 消费组 ack 与 Kafka offset 提交有什么相似与不同？（答： 相似：都标记 已处理进度；不同：Stream 按消息 ID ack，Kafka 按 offset 批量 commit；KF 有 __consumer_offsets 与 rebalance，Stream 更轻、无完整 ISR 语义。）
  • 什么情况下「RPC 超时改 MQ」反而是反模式？（答： 需要 同步结果/强一致读、调用链短且可 熔断重试 时；改 MQ 会 延迟可见、状态难查，反而增加 对账与幂等 成本。）

生产注意

  • Stream 无长期 retention 与跨机房联邦时，别承担 审计级消息留存 需求。

M3. 点对点 vs 发布订阅？

口述版： 点对点一条消息通常只被一个消费者消费；发布订阅一条消息可被多个订阅者各收一份。Rabbit 用 Exchange 做 pub/sub；Kafka 用多个 Consumer Group 各读一份。

具体介绍

  • JMS：Queue vs Topic。
  • Kafka：同一 Group 内 partition 竞争；不同 Group 各自消费全量。
  • 三件套对照：
    语义 RB KF Rocket
    点对点 单 Queue 多 Consumer（竞争） 同 Group 分 partition 竞争 同 Group 竞争
    发布订阅 Fanout/Topic Exchange → 多 Queue 多 Consumer Group 多 Group / 广播 Topic
  • RB 注意：竞争消费需 prefetch + 手动 ack；KF 注意：partition 数上限并行度。
  • 重复投递：pub/sub 下游各收一份，每条链路都要幂等；点对点竞争消费只需组内幂等。
  • RB 实践：Fanout 绑多个 Queue 实现广播；每个 Queue 独立 DLQ 与消费速率。

面试追问

  • Kafka 同一 Topic 两个 Group 同时消费，Broker 存储会翻倍吗？（答： 不会；日志 只存一份，各 Group 独立 offset；存储由 retention/compact 决定，与 Group 数量无关。）
  • Rabbit 竞争消费时如何保证「尽量均匀」？（答： 多 consumer 绑 同一 Queue；调 prefetch 避免单 consumer hoard；消息 无 key 时 近似轮询，热点 key 需 拆队列或 sharding。）

生产注意

  • 广播场景消费慢会拖垮单个 Queue depth；按下游 SLA 拆 Queue 或限流。

M4. 丢失 / 重复 / 乱序 与投递语义？

口述版： 丢失要从生产、Broker、消费三端加固；重复几乎不可避免，靠幂等；乱序靠单队列或单 partition 保序。工业界多是 at-least-once + 业务幂等。

具体介绍

  • At-most-once：可能丢，不重复。
  • At-least-once：可能重复，一般不丢（配合 ack）。
  • Exactly-once：Broker 与业务都复杂，Kafka 有语义但业务仍要幂等设计。

可靠性三板斧（生产 / Broker / 消费）— 总纲

环节 丢失典型原因 RB 加固要点 KF 加固要点 Rocket 加固要点
生产 发送失败未重试、以为成功实际未落盘 Publisher Confirm + mandatory/return acks=all + retries + 等 metadata 同步发送 + 重试 + 事务消息（关键链路）
Broker 单点、未持久化、副本未同步 durable + 镜像/Quorum Queue replica ISR + min.insync.replicas 同步刷盘策略 + 主从同步
消费 自动 ack、先 ack 后业务、处理中宕机 手动 ack，业务成功后再 ack 处理成功后 commit offset 消费成功再 CONSUME_SUCCESS
  • 重复：三板斧任一端重试或 rebalance 都会带来；业务幂等（M19）是必答题，不是可选项。
  • 乱序：全局顺序代价是单线程；业务常用 同一业务 key 进同一 queue/partition（M20）。
  • 乱序处理：除单 partition/单队列外，可接受乱序的业务用 版本号/时间戳 丢弃旧事件。
  • 监控映射：丢消息查三板斧表；重复查幂等表与 messageId；乱序查 key 路由是否变更。

面试追问

  • at-least-once 下「业务执行一次」和「消息投递一次」是一回事吗？（答： 不是；消息可能 重复投递，业务须 幂等 保证「效果一次」；投递语义与 本地事务 是两层问题。）
  • Kafka exactly-once 能替代业务幂等表吗？为什么？（答： 不能；EOS 管 生产-消费-Kafka 事务边界，跨 DB/HTTP/外部系统 仍可能重复；业务 幂等键/唯一索引 仍是最后防线。）

生产注意

  • 宣称 exactly-once 前问清范围：仅 Broker 写？含 consume-transform-produce？
  • 改 partition 数、换 routing key 策略会导致 顺序语义变化，需评审。

M5. RabbitMQ / Kafka / RocketMQ 对比？

口述版： Rabbit 路由灵活、延迟低、吞吐中等，适合业务消息；Kafka 日志型、超高吞吐、回溯，适合日志/大数据；Rocket 阿里系、事务消息成熟，国内电商常用。

具体介绍

维度 RabbitMQ Kafka RocketMQ
模型 Exchange + Queue，AMQP Topic + Partition 日志 Topic + Queue 索引 + CommitLog
吞吐 万～十万/s（视消息大小与镜像） 百万级/s（批量+顺序写） 十万级/s
延迟 毫秒级，适合业务命令 批量拉取，ms～百 ms 毫秒～十 ms 级
顺序 单 Queue 单 Partition 单 Queue / 单 Partition
路由 Direct/Topic/Fanout 灵活 Topic + Key → Partition Tag、SQL92 过滤
回溯 消费即 ack 删除（无长期 log） retention 可重放 按时间/offset 可重消费
延迟消息 TTL + DLX 外部调度 / 时间轮 固定 18 级 delay level
事务消息 无原生半消息（靠本地表） 事务 API + 幂等生产者 半消息 + 回查 成熟
HA 镜像 / Quorum Queue ISR + Controller 主从 + Dledger（4.x+）
运维 Erlang 集群，内存水位敏感 ZK/KRaft、partition 均衡 NameServer 无 ZK
  • 图中 ActiveMQ 偏老牌 JMS，新项目较少选；对比时重点 Rabbit / Rocket / Kafka 即可。

选型速查

  • 订单、支付通知、工作流、复杂路由 → RB 或 Rocket（国内电商偏 Rocket）。
  • 日志、埋点、CDC、流计算、大数据管道 → KF。
  • 要 Broker 侧事务消息 + 国内案例 → Rocket；要 AMQP 生态 + 低延迟路由 → RB。

常见配置锚点（面试提名词即可）

  • RB：publisher-confirm-type=correlated、durable=true、Quorum Queue policy。
  • KF：acks=all、min.insync.replicas=2、replication.factor=3、enable.idempotence=true。
  • Rocket：sendMsgTimeout、同步刷盘、transactionCheckListener 回查。
  • 消息大小：KF 适合大 batch 小消息；RB 单消息过大占内存，建议 大附件走 OSS + 消息传 URL。
  • 合规与多租户：Pulsar/云 MQ 在多租户隔离上更成熟；自建三件套靠 vhost/ACL/Topic ACL。

面试追问

  • 订单系统选 RB 还是 Rocket，你会问业务哪三个问题？（答： 吞吐与堆积量级、是否需要事务/延迟/顺序、团队运维与生态（路由/DLQ/监控/多活）；强事务本地消息 vs Rocket 半消息也要问。）
  • Kafka 做业务命令通道的最大坑是什么？（答： 无原生延迟/DLQ/路由，消费慢导致 rebalance；命令类还要 幂等 + 状态机，否则 重复消费 直接改业务数据。）

生产注意

  • 镜像/Quorum、ISR、同步刷盘等 HA 配置按 SLA 写进 变更 checklist，避免口头「高可用」。

M6. 事务消息、本地消息表、Outbox？

口述版： 本地消息表是 DB 和业务同事务写「待发送」，定时扫表发 MQ；Outbox 类似；Rocket 半消息+回查是 Broker 侧事务；都是解决「DB 成功消息必 eventual 发出」。

具体介绍

  • 本地消息表：状态 pending/sent/confirmed。
    • 表字段建议：id, biz_key, payload, status, retry_count, next_retry_at, created_at。
    • 定时任务扫 pending + 指数退避；发送成功改 sent；消费者回调或业务确认改 confirmed。
  • Outbox + CDC：Debezium 读 binlog 发 MQ。
    • 优点：业务只写 Outbox 表，不发 MQ 代码路径；缺点：CDC 延迟与 schema 变更治理。
  • Rocket 半消息：Broker 存 half → 本地事务 → commit/rollback → 超时 回查（M22、M48）。
  • TCC/Saga：与 MQ 配合做长事务（S）；MQ 发 补偿事件，消费端必须幂等。
  • 选型：强一致「写库必发」→ 本地表/Outbox/ Rocket 半消息；长流程 → Saga + 补偿 Topic。
  • 对账：无论哪种方案，都要有 pending 超时扫描 + 人工介入 通道。

面试追问

  • Outbox + CDC 与本地消息表扫表发 MQ，各适合什么团队规模？（答： Outbox+CDC 适合 有 DBA/流平台、要解耦扫表 的中大团队；扫表发 MQ 适合 小团队快速落地，但要控 扫表频率与连接池。）
  • 半消息回查接口超时，Broker 会怎么处理？（答： Broker 按策略重试回查；长期 UNKNOWN 可能 rollback 半消息 或告警；业务回查应 快速只读查本地事务状态。）

生产注意

  • 本地消息表与业务同库，注意 表膨胀与索引（status + next_retry_at）。
  • CDC 链路要测 DDL 变更 与 tombstone 对下游的影响。

M7. 什么场景不该用 MQ？

口述版： 必须同步返回、流量小直连就够、消费者无幂等、团队无 MQ 运维能力、问题难排查却强依赖链路——别为了「架构先进」硬上。

具体介绍

  • 强一致读己之写：RPC+DB 更直接。
  • 链路过长：故障点增多，需全链路监控。
  • 反模式清单：无 DLQ / 无幂等 / 无 lag 告警仍上 MQ；消费者数 > KF partition 数却期望线性扩容；RB 镜像未开却宣称「消息绝不丢」。
  • 同步强依赖：用户提交后必须立刻看到结果（余额、库存扣减确认）→ 同步 RPC + 单库事务更可控。
  • 低 QPS 直连：无峰值、无多订阅，MQ 只增加 运维、排查、一致性滞后。
  • 组织成熟度：无 on-call、无 lag/DLQ playbook 时，MQ 故障会拖垮全链路。
  • 调试成本：分布式异步比同步难 trace，无 traceId 透传（M58）勿大规模上 MQ。
信号 建议
必须同步返回且强一致 RPC + DB，或 Seata 等，慎 MQ
消费者无法幂等 先补幂等键/状态机再接入
峰值 < 下游 2 倍容量 限流/扩容直连往往够用
无监控与 DLQ 先补可观测性再引 MQ

面试追问

  • 「解耦」是否值得用 MQ？什么耦合其实是 healthy coupling？（答： 为 削峰、异步、多订阅 值得；强一致同一聚合根 的同步调用是 healthy coupling，硬上 MQ 只会 分布式一致性问题。）
  • 团队第一次上 MQ，你会要求哪些最低运维基线？（答： Lag/堆积、发送失败率、DLQ 深度 告警；镜像/quorum/ISR 说明；消费幂等与重试 规范；演练：Broker 宕机、磁盘满。）

生产注意

  • 反模式：为「技术栈先进」引入 MQ，却无 积压与毒消息 处理预案。
  • 强依赖 MQ 的核心链路要有 降级（同步兜底或本地队列限域），避免 Broker 全挂业务停摆。

5.2 通用核心概念

M8. Producer、Broker、Consumer 等术语？

口述版： 生产者发消息到 Broker，Broker 存/路由，消费者拉或推；Topic 是逻辑分类，Queue 是存储；Consumer Group 是负载均衡单位。

具体介绍

  • Binding：Rabbit 里 Queue 连 Exchange 的规则。
  • Offset：Kafka 消费位移。
  • Lag：未消费条数。
  • 对照表：
    概念 RB KF Rocket
    逻辑分类 Exchange + routing key Topic Topic
    存储单元 Queue Partition 日志段 Queue + CommitLog
    负载均衡 Queue 上竞争消费 Consumer Group Consumer Group
    未消费积压 messages_ready consumer lag consume lag
  • Producer 生命周期：连接池、channel 复用（RB）；KF producer 线程安全可单例；Rocket 注意 ProducerGroup。
  • Consumer 伸缩：KF 以 partition 为上限；RB 以 Queue + prefetch 平衡；Rocket 以 Queue 数与线程池。

面试追问

  • Lag 是 consumer 概念还是 broker 概念？RB 上如何近似看 lag？（答： Lag 本质是 生产 offset − 消费 offset；RB 无统一 lag，看 Queue 深度、ready/unacked、消费速率 近似。）
  • Binding 改动能热更新吗？对正在 fly 的消息有何影响？（答： 一般 可动态改 binding；已在途消息按 旧路由 或已入队规则走，新 binding 只影响之后 publish；改错可能导致 丢路由或进错队列。）

生产注意

  • 术语混用面试易扣分：Kafka 没有 Queue；Rabbit 没有 Consumer Group（是竞争消费）。

M9. Push vs Pull 消费？

口述版： Push 是 Broker 推给消费者，实时性好但要控 prefetch 防压垮；Pull 是消费者拉，Kafka 典型，可自己控速率。

具体介绍

  • Rabbit：基本 Push + QoS。
  • Kafka：Long polling pull。
  • Rocket：推模式为主（长轮询），也可拉。
  • 反压：慢消费要减并发或扩容消费者；RB 调小 prefetch；KF 减小 max.poll.records、增大 max.poll.interval.ms；避免消费者线程池无限排队导致 OOM。
  • Push 典型问题：Broker 推太快 → 消费者 OOM、DB 打满；必须用 prefetch / 并发上限 / 背压。
  • Pull 典型问题：poll 间隔过大延迟高；过小空轮询浪费 CPU；需调 fetch.max.wait.ms 等。
  • 长轮询：Rocket/KF 减少空 poll，兼顾实时与资源。
模式 优点 风险 代表
Push 低延迟、实现简单 需流控 Rabbit 默认
Pull 消费速率自控 参数调不好则延迟或空转 Kafka
推+长轮询 折中 仍要限并发 Rocket

面试追问

  • 慢消费者场景 Push 如何「不丢消息又不被压垮」？（答： 调低 prefetch、限流、独立队列；Broker 流控 block publisher；必要时 扩容 consumer 或 降级非核心消费。）
  • Kafka consumer 是 Push 还是 Pull？为什么说「伪 Push」？（答： API 层 poll 拉取；长轮询 + broker 攒 batch 像 Push；背压由 consumer 主动 poll 频率 控制。）

生产注意

  • RB：prefetch 与 consumer 数乘积 ≈ 未 ack 上限，要小于下游连接池与内存预算。
  • KF：max.poll.records × 单条处理内存 × 并发线程 ≈ 堆占用，大消息要特别压测。

M10. ACK 机制？

口述版： 自动 ack 收到就确认，可能处理中宕机丢消息；手动 ack 处理完再 ack，配合重试。失败可 nack 重新入队或进 DLQ。

具体介绍

  • 至少一次：手动 ack 在业务成功后。
  • 重复：ack 前宕机会重投。
  • 幂等必须配合（M19）。
  • 三端 ACK 对照：
    • RB：basicAck / basicNack(requeue=false) 进 DLQ。
    • KF：auto commit vs commitSync after business success。
    • Rocket：CONSUME_SUCCESS vs RECONSUME_LATER（有限次后进 DLQ）。
  • 半成功：批量 ack 时部分失败要明确 nack 哪几条 或拆批；KF 批次 offset 提交粒度要谨慎。
  • 重试风暴：requeue=true 无限重试会堵死队列；必须 上限 + DLQ（M13、M54）。

面试追问

  • 自动 ack 在什么 demo 场景可以，生产为什么几乎不用？（答： Demo 单线程、可丢可重跑；生产 处理完再 ack 才能 at-least-once，自动 ack 可能在 业务失败前已 ack 导致 静默丢消息。）
  • 消费失败 requeue 与进 DLQ 如何选择？（答： ** transient 错误（网络抖动）有限次 requeue+退避；毒消息/逻辑错误** 进 DLQ 人工修复，避免 无限 requeue 打满 Broker。）

生产注意

  • RB 先 ack 后写 DB 是经典丢消息写法；面试/生产都要说清 先 commit 业务再 ack。

M11. Prefetch / 批量拉取？

口述版： prefetch 大则消费者一次拿很多条，吞吐高但可能堆积在慢消费者；prefetch=1 更公平。Kafka 用 max.poll.records 类似。

具体介绍

  • Rabbit：basicQos(prefetchCount)，global=false 按 channel 限流。
  • KF：max.poll.records（单次 poll 条数）、fetch.min.bytes / fetch.max.wait.ms（批量凑包）。
  • 消费慢时调小 prefetch / max.poll.records 或加消费者；RB prefetch 过大 会导致一条慢消息占满 channel 未 ack 窗口。
  • 公平性 vs 吞吐：prefetch=1 最公平但 RTT 多；大 prefetch 适合 批处理、同质耗时 消息。
  • 全局 QoS：basicQos(global=true) 少见，理解 per-channel 限流即可。

面试追问

  • 三个 consumer 同 Queue，prefetch=10，最多多少条 unacked？（答： 最多约 3×10=30 条 已投递未 ack（各 channel 独立 prefetch）；实际还受 Broker credit 与 consumer 处理速度 影响。）
  • KF fetch.min.bytes 和 prefetch 思想上的对应关系？（答： 都控制 「攒一批再往下游推」；fetch.min.bytes 让 consumer 少空 poll，prefetch 限制 未 ack 在途量，减轻慢消费者压力。）

生产注意

  • 消费逻辑变长时，未 ack 堆积会占满 prefetch，表现为 其它 consumer 饿死，需降 prefetch 或拆队列。

M12. 持久化三处配合？

口述版： 消息、队列、Exchange 设 durable；Producer 开 confirm；Consumer 手动 ack；三者缺一会增加丢消息概率。

具体介绍

  • 持久化消息仍要经过 刷盘 策略。
  • 集群下还要 镜像/副本（M17、M25）。
  • 检查清单：
    1. RB：Queue/Exchange durable + deliveryMode=2 + confirm。
    2. KF：acks=all + 足够 replica（非 acks=1 单副本）。
    3. Rocket：同步刷盘 vs 异步刷盘（性能 tradeoff 要说清）。
  • 非持久化场景：临时通知、可丢的 metrics 可用 transient，但要 文档化 可丢范围。
  • 集群切换：durable 消息在未 mirror/quorum 时，节点故障仍可能不可达（M26）。

面试追问

  • deliveryMode=1 和 2 在 RB 里分别代表什么？谁决定落盘？（答： 1 非持久（内存），2 持久（需 durable queue + 持久消息 才可靠落盘）；落盘由 队列/消息属性 + 镜像/quorum 共同决定。）
  • KF 没有「队列 durable」概念，持久化靠哪些参数？（答： Topic retention、cleanup.policy、replication.factor、min.insync.replicas、producer **acks=all**；日志在 broker 本地盘 多副本。）

生产注意

  • 三处缺一：常见 bug 是 Queue durable 但消息 transient，或开了 confirm 但 Exchange 非 durable。

M13. 死信队列 DLQ？

口述版： 消费被拒、TTL 到期、队列超长可进 DLQ，避免毒消息无限重试堵死主队列；DLQ 要监控+人工/补偿任务。

具体介绍

  • Rabbit：x-dead-letter-exchange、x-dead-letter-routing-key；或 x-delivery-limit（3.8+）。
  • KF：无原生 DLQ，常用 重试 topic + 最终进 dead-letter topic 或 Streams 侧车。
  • Rocket：%RETRY% 队列 + %DLQ%（重试次数耗尽）。
  • 重试次数上限后转 DLQ；DLQ depth 告警 + 审计 requeue。
  • DLQ 消费：DLQ 也要 幂等 + 限流，避免补偿任务再次打爆下游。
  • requeue 审计：从 DLQ 重回主队列要记录 operator、原因、messageId。

面试追问

  • 毒消息不进 DLQ 一直 requeue，对 Rabbit 内存和磁盘有什么影响？（答： 无限 redelivery 占 unacked/队列深度，打高 CPU/磁盘 IO，可能触发 内存/alarm 流控，拖垮 同集群其他队列。）
  • Kafka 没有原生 DLQ，你们项目怎么实现「最终进死信」？（答： 消费失败 retry topic 或 计数后写入 DLQ topic；用 拦截器/包装 listener 统一路由；配合 监控与人工 replay。）

生产注意

  • DLQ 只堆积不处理等于 延迟炸弹；depth 告警阈值要低于磁盘/内存水位。

M14. 延迟消息实现？

口述版： Rabbit 用 TTL+DLX 到延迟队列；Rocket 固定延迟级别；Kafka 用时间轮或外部调度；也可用 Redis 延迟 ZSet。

具体介绍

  • 延迟精度、堆积、重启可靠性各不同。
  • 订单超时关单常用。
  • 对比：RB TTL+DLX 灵活但 同队列不同 TTL 头阻塞；Rocket 1s 5s 10s ... 2h 固定档；KF 常用 延迟 topic + 时间轮 consumer 或 DB/Redis 调度发正式 topic。
  • 订单关单：延迟到期后 幂等关单（状态机只允许待支付→关闭一次）。
  • 精度需求：Rocket 固定档 vs RB TTL 灵活 vs 外部调度（XXL-Job/Redis ZSet）按 SLA 选。
  • 重启可靠性：延迟状态在 Broker 队列 vs 外部调度器，要明确 重启后是否丢延迟任务。
方案 精度 坑
RB TTL+DLX 较灵活 同队列头阻塞
Rocket delay level 固定 18 档 非任意毫秒
KF 时间轮/外部 可定制 自建运维
Redis ZSet 灵活 与 MQ 一致性要自己兜

面试追问

  • TTL 在 message 上和在 queue 上有什么区别？（答： 消息 TTL 单条过期；队列 TTL 整队 idle 过期；过期常进 DLX，配置在 policy/arguments，别混用导致 误删。）
  • 延迟消息堆积百万级，Broker 扛不住时如何降级？（答： 限 生产速率、扩容、改 外部时间轮/DB 调度；非核心延迟 丢弃或合并；Rocket 固定级别 比任意 delay 更易控资源。）

生产注意

  • RB 头阻塞场景：一队列一 TTL 档 或 per-message TTL + 多 DLX 路由。
  • 延迟触发后的消费仍可能重复，关单接口必须幂等。

M15. 消息堆积排查？

口述版： 看 lag/队列 depth、生产速率 vs 消费速率、是否单条慢 SQL、消费者数够不够、是否 rebalance 卡住。

具体介绍

  • 临时扩容消费者（Kafka 不超过 partition 数）。
  • 降级：先丢弃非核心、转储后慢慢消费（S）。

通用排查步骤（5 步）

  1. 量化：RB messages_ready / messages_unacknowledged；KF kafka-consumer-groups.sh --describe 看 LAG；Rocket Console lag。
  2. 生产侧：TPS 是否突增、是否有 batch 重放、定时任务重复发。
  3. 消费侧：实例数、是否全 down、GC STW、max.poll.interval 超时被踢、单条耗时 P99。
  4. Broker：磁盘/IO、RB memory/disk alarm、KF under-replicated、Rocket commitlog 写满。
  5. 处置：扩 consumer（≤ partition 数）、优化慢 SQL、临时降级非核心 topic、增加 partition（KF 长期）、RB 增加消费者 + 调 prefetch。
  • 长期方案：临时扩容后仍要 优化单条耗时、加 partition、削生产；否则 lag 周期性复发。
  • 业务降级：非核心 topic 可暂停消费或丢弃并 审计，为核心链路腾资源。

面试追问

  • Kafka consumer 数大于 partition 数，多出来的进程在干什么？（答： 空闲 standby；同一 Group 内 一 partition 同一时刻只一个 consumer 读；多实例只为 failover 或减 rebalance 时间。）
  • unacked 很高而 ready 很低说明什么（RB）？

生产注意

  • 扩容 consumer 前先看 是否慢 SQL/GC；否则只是把堆积从 Broker 挪到 consumer 内存。

5.3 可靠性与幂等

M16. 生产端如何尽量不丢？

口述版： 发送失败重试+退避；开 Publisher Confirm 等 Broker 落盘再认为成功；关键消息落本地消息表，扫表补发。

具体介绍

  • Rabbit：confirm 模式、mandatory+return 处理不可路由。
  • Kafka：acks=all、retries、min.insync.replicas。
  • 同步 send 等结果 vs 异步 callback。
  • 生产端配置示例（口述）：
    • RB：spring.rabbitmq.publisher-confirm-type=correlated，confirm 回调失败入补发表；publisher-returns=true + mandatory=true。
    • KF：acks=all，retries=Integer.MAX_VALUE，delivery.timeout.ms，enable.idempotence=true 防重试重复写。
    • Rocket：同步 send 对关键消息；失败落本地消息表异步重发。
  • 别踩坑：异步 send 不等 confirm 就关进程；RB confirm 与 transaction 模式别混用搞不清语义。
  • 顺序与重试：生产端重试可能导致 乱序；关键 key 要用同一 partition/顺序发送或接受乱序+版本号。
  • 超时：delivery.timeout.ms 与 retries 配合，避免无限阻塞发送线程。

面试追问

  • confirm 成功是否等于 consumer 一定收到？差在哪一段？（答： 不等于；confirm 只到 Exchange/队列入队（或 KF broker ack）；consumer 未拉取/处理失败/宕机 仍可能丢或重复，需 ack+幂等。）
  • 本地消息表与 confirm 能否同时用？如何防双发？（答： 可以；表记录 SENT 状态 + 唯一 bizId，confirm 回调与 定时扫表 用 CAS 更新 防双发；consumer 仍要 幂等。）

生产注意

  • KF acks=1 在 leader 宕机切换时可能 丢已 ack 未复制 的消息，生产应用 all+min.insync。

M17. Broker 如何尽量不丢？

口述版： 队列/消息持久化；多副本同步复制；磁盘、内存告警与流控；集群避免单点。

具体介绍

  • Rabbit：镜像队列（M25）/ Quorum Queue（Raft，推荐新项目）。
  • Kafka：replica 进 ISR 才 ack；unclean.leader.election.enable=false 防丢数据选 leader。
  • Rocket：同步双写 / 同步刷盘（配置级 tradeoff）。
  • 刷盘：性能 vs 可靠性 tradeoff（RB lazy queue、KF log.flush、Rocket flushDiskType）。
  • RB lazy queue：大堆积落盘减内存，但 磁盘 IO 上升，与 M32 联动监控。
  • KF 磁盘规划：retention × 吞吐决定磁盘；under-replicated 期间别扩 retention 雪上加霜。

面试追问

  • Quorum Queue 与经典镜像在一致性模型上差异一句话？（答： Quorum 基于 Raft 多数派复制；经典镜像是 异步/master 复制，故障时 丢消息风险与脑裂 行为不同。）
  • ISR shrink 时 producer 还能写吗？取决于哪些配置？（答： 看 acks 与 **min.insync.replicas**；ISR 小于 min 时 acks=all 会写失败；acks=1 可能 降级写 leader。）

生产注意

  • 流控/block 连接时，上游应用要有 发送超时与降级，避免线程池耗尽。

M18. 消费端如何尽量不丢？

口述版： 手动 ack，业务处理成功再 ack；处理幂等；宕机未 ack 会重投，要有重复处理能力。

具体介绍

  • 先 DB 事务提交再 ack，顺序要对。
  • 长处理：延长 visibility timeout / max.poll.interval。
  • 推荐顺序：开本地事务 → 写业务 + 幂等表 → commit → 再 ack/commit offset。
  • 反例：先 ack 再调 DB → 宕机则 消息丢处理（at-most-once 效果）。
  • RB 长任务：心跳续期或拆小消息；KF：max.poll.interval.ms > 最坏处理时间。
  • 幂等与 ack 顺序：同一 messageId 重复处理应 结果一致；ack 仅影响是否重投。
  • 批量消费：一批 10 条一条失败，是 整批 nack 还是记录失败单条进 DLQ，要设计清楚。

面试追问

  • 消费线程处理 5 分钟，KF 被踢出 group 的根因参数是？（答： max.poll.interval.ms 超过（处理时间 > 两次 poll 间隔）；另 session.timeout.ms/heartbeat 失效也会 rebalance。）
  • RB 消费中如何续期避免 channel 被关？（答： 长任务 拆小 ack 或 独立线程消费+短 ack；调大 consumer_timeout（慎用）；避免 同 channel 阻塞 IO。）

生产注意

  • max.poll.interval.ms 必须大于 P99 处理时间 + GC；留 2～3 倍余量。

M19. 重复消费与幂等？

口述版： 用业务唯一键：订单号+事件类型做 DB 唯一索引；或 Redis setnx；或状态机只允许从 A→B 一次。

具体介绍

  • 天然幂等：覆盖写、删除。
  • 非幂等：扣库存要先查是否已扣。
  • 消息带 messageId 去重表。
  • 三 MQ 携带键：RB messageId in properties；KF header idempotency-key；Rocket keys / 业务 property。
  • 表设计：uniq(biz_type, biz_id, event_type) 或 processed_message(message_id)。
  • 状态机幂等：只允许 CREATED→PAID 一次，重复 PAID 事件直接 return success。
  • 去重表 TTL：messageId 表可定期归档，但要覆盖 最大重投窗口（如 7 天）。

面试追问

  • 数据库唯一索引冲突时，算成功还是失败？对 ack 有何影响？（答： 若业务定义 重复=已成功，应 ack 并记日志；若未知冲突应 nack/DLQ；幂等设计 要把冲突当 成功路径。）
  • Redis setnx 幂等与 DB 唯一索引各适合什么场景？（答： setnx 适合 轻量去重/短 TTL 防重；DB 唯一索引适合 强一致落库、审计；高并发 先 Redis 挡再 DB 常见。）

生产注意

  • 幂等键要覆盖 所有入口（HTTP 回调 + MQ + 定时补偿），否则双通道重复扣款（M56）。

M20. 顺序消息？

口述版： 全局顺序只能单线程单队列；一般只要 同一订单同一 partition/同一 routing key 顺序即可；提高并行就多分 partition，key 相同进同 partition。

具体介绍

  • Kafka：key hash % partition。
  • Rabbit：单队列单 consumer 或 一致性 hash 多队列（相同 routing key 进同队列）。
  • Rocket：MessageQueueSelector 按 orderId 选队列。
  • 乱序重排：业务可接受则用时间戳排序（有限）；扩 partition 后 仅保证分区内序。
  • 局部顺序：同一 orderId 进同一 partition/queue；不同订单并行，全局无序通常可接受。
  • 失败重试：重试可能 乱序到达，业务用版本号或状态机拒绝旧事件。
  • 扩容：增加 partition 只保证 分区内 序；新 partition 不参与旧 key 的历史序。
产品 保序手段 并行度
Kafka key → partition partition 数
Rabbit 单队列或 consistent hash 队列数 × consumer
Rocket MessageQueueSelector 队列数

面试追问

  • 消费端多线程处理同一 queue 的消息还能保序吗？怎么改？（答： 不能保全局序；要顺序则 单线程消费 或 按 key 分片到固定线程（KF 用 单 partition）。）
  • 全局顺序和分区顺序的 QPS 上限差多少量级？（答： 全局顺序 单线程/单 partition，QPS 常 数百~数千；分区顺序 线性扩展，可 一个数量级以上 差距。）

生产注意

  • 改 key 哈希或增 partition 前评估 顺序业务 是否受影响；需要 双写或灰度 验证。

M21. 本地事务 + 发 MQ 失败？

口述版： 同事务写业务表+本地消息表 pending；异步线程发 MQ 成功改 sent；失败重试；消费者处理完回调 confirmed，定时对账补发。

具体介绍

  • 避免「DB 回滚了消息已发出」：先发 MQ 再 DB 更危险，常用 事务消息或本地表。
  • 最大努力通知+对账兜底。
  • 对账任务：扫描 pending 超过 N 分钟、或 sent 无 confirmed 超过 M 分钟，告警 + 补发/人工。
  • 先发 MQ 再 DB 的典型事故：DB 失败但消息已发出 → 下游脏读；故 事务内写 outbox/本地表 优先。
  • 状态机：pending → sending → sent → confirmed；每步可监控与重试。
  • 与 Seata：2PC 重；本地表 + MQ 是互联网 最常见最终一致 落地。

面试追问

  • 扫表线程与业务争抢 DB 连接怎么办？（答： 独立连接池/只读从库、限流扫表、索引+分批；Outbox+CDC 移出业务库轮询。）
  • 消息已 sent 但消费者 never consume，如何对账？（答： 对 消息表/offset vs 业务终态；超时告警；补发或关单；KF 看 consumer lag，RB 看 queue depth。）

生产注意

  • 本地表 biz_key 唯一 防重复插入；扫表任务要 分布式锁或分片 防多实例重复发。

M22. 事务消息（半消息）？

口述版： Rocket：先发 half 消息，本地事务提交后 commit，失败 rollback；Broker 回查本地事务状态。Kafka 事务生产者+消费隔离级别了解即可。

具体介绍

  • 适合 订单创建+发消息 强一致诉求。
  • 实现复杂，监控回查失败（S）。
  • Rocket 流程：sendMessageInTransaction → 执行本地事务 → commit/rollback → Broker 定时 checkLocalTransaction。
  • Kafka：transactional.id + read_committed 消费；端到端仍常配合幂等表。
  • 回查风暴：本地事务慢或 check 接口超时会导致 Broker 频繁回查，要限流与缓存状态。
  • Kafka 事务：适合 consume-transform-produce 同集群；跨库仍靠幂等。

面试追问

  • half 消息 commit 前，消费者能拉到吗？（答： 不能；半消息对下游 不可见，直到 commit/rollback；避免 未决事务被消费。）
  • 回查返回 UNKNOWN 多次会怎样？（答： Broker 继续回查 直至 超时 rollback 或得到 COMMIT/ROLLBACK；业务应 避免长期 UNKNOWN。）

生产注意

  • Rocket 事务消息 仅适合单库本地事务 + 发一条消息；多资源协调用 Saga/本地表。

5.4 RabbitMQ 专章

M23. Exchange 类型？

口述版： Direct 精确 routing key；Fanout 广播；Topic 通配符；Headers 很少用。业务路由选 Direct/Topic 最多。

具体介绍

类型 路由
Direct key 完全匹配
Fanout 忽略 key，全绑定队列
Topic * 一词 # 多词
  • 面试设计题：支付成功 pay.success、退款 pay.refund 可用 Topic；全站广播用 Fanout。
  • Headers Exchange：按 header 匹配，性能与运维成本高，面试知道即可。
  • 默认 Exchange：空名 direct，routing key=queue 名，适合简单点对点。

面试追问

  • Topic 里 * 和 # 分别匹配什么？举两个 routing key 例子。（答： * 匹配 一个词；# 匹配 零或多个词；如 binding order.* 匹配 order.created；order.# 匹配 order.created.paid。）
  • Fanout 还要 routing key 吗？Binding 怎么配？（答： 忽略 routing key；Queue 绑 Exchange routing key 填空 即可，广播到所有绑定队列。）

生产注意

  • 生产环境 Exchange/Queue 命名规范 + mandatory 防路由黑洞（M24、M29）。

M24. Binding 与 Routing Key？

口述版： Exchange 不存消息，消息进 Exchange 按类型和 binding 规则进 Queue；routing key 是 Direct/Topic 的匹配字段。

具体介绍

  • 一个 Exchange 绑多个 Queue 实现多消费。
  • Alternate Exchange 处理无法路由的消息（配合 mandatory 避免静默丢）。
  • 排查无法消费：Management UI 看 Publish rate / Deliver rate、Binding 是否存在、routing key 是否 typo。
  • 多 Binding：同一 Exchange 绑多个 Queue 实现 一条消息多下游；注意各下游 独立 ack。
  • 权限：vhost 隔离、用户 tag 限制 publish/consume，防误删 Binding。

面试追问

  • Exchange 删除时 Queue 会怎样？消息呢？（答： Queue 仍存在（除非级联配置）；未路由消息 可能丢；已入队消息 仍在 Queue，直到被消费或 TTL。）
  • routing key 大小写敏感吗？（答： 敏感；Order.created 与 order.created 是 不同 key，Topic 模式按 字面匹配（除通配符规则外）。）

生产注意

  • 改 Binding 前在 影子 vhost 或低峰验证，避免生产消息进错队列。

M25. 镜像队列 Mirrored Queue？

口述版： 普通集群队列只在一个节点，宕机队列没了；镜像队列在多个节点同步副本，policy 开启，可设 master 和 mirror 数量，提高可用性。

具体介绍

  • 开启：对队列/模式设 ha-mode、ha-params（经典镜像；新版用 Quorum Queue 了解）。
  • 与 M26 普通集群对比是 Rabbit 高可用核心。
  • Quorum Queue：基于 Raft，推荐替代经典镜像；参数 x-queue-type=quorum。
  • Policy 示例（口述）：ha-mode=all 或 ha-mode=exactly, ha-params=2（经典）；生产新建优先 Quorum。
  • 性能：经典镜像写放大明显；Quorum 基于 Raft，写延迟与 majority 相关，读仍走 leader。
  • 迁移：经典镜像 → Quorum 需 新队列迁移 计划，非原地 flip。

面试追问

  • ha-mode=all 和 exactly=2 在故障时行为差在哪？（答： all 所有 mirror；exactly=2 限定镜像数；故障时 同步延迟、谁晋升 master 与 是否丢 unacked 不同。）
  • Quorum Queue 是否适合 超大堆积 场景？（答： 不太适合；Raft 复制与 磁盘/WAL 成本高；超大堆积更常 经典队列+镜像 或 KF 日志型。）

生产注意

  • 镜像/Quorum 解决 消息 HA，不替代 客户端重连与 LB（M28）。

M26. 普通集群宕机为何仍可能丢？

口述版： 队列 metadata 在集群同步，但 消息体默认只在创建队列的节点，该节点挂了队列不可用，未同步到其他节点的消息就丢了；持久化也要镜像或 quorum 才真正 HA。

具体介绍

  • 原文亲测：仅持久化、无镜像，节点故障仍可能丢。
  • 生产：镜像/quorum + 持久化 + confirm。
  • 面试一句话：RB 集群 ≠ 队列 HA；消息 HA 靠 Quorum/Mirrored。
  • metadata 同步 ≠ 数据同步：队列定义全集群可见，但 消息体默认单节点。
  • 恢复流程：节点重启后队列 mirror/quorum 选举，未同步副本可能 lag catch-up。
  • 持久化误区：disk 上仍有未 replicate 到 mirror 的消息在旧 master 磁盘，节点永久丢失则丢。

面试追问

  • 为什么说「Rabbit 集群」不等于「高可用」？（答： 集群只 共享元数据；Queue 默认 单节点，宕机 队列不可用；HA 需 镜像/Quorum + 负载与监控。）
  • 持久化消息在普通集群节点宕机后，重启能否自动找回？（答： 若 未镜像 且磁盘 intact 可能 恢复该节点队列；已丢副本 则 不可恢复；生产必须 镜像/quorum。）

生产注意

  • 生产 checklist：Quorum/Mirror + durable + confirm 三件套写进架构评审。
  • 单节点队列故障时，客户端要 自动 failover 到存活节点（但队列需 HA 类型）。

M27. Federation 与 Shovel？

口述版： Federation 是 Exchange 上游下游联邦，跨机房延迟复制；Shovel 是主动从一个 broker 拉消息推到另一个，适合桥接系统。

具体介绍

  • 解决 跨地域、异构 MQ 同步。
  • 需装插件，注意顺序与重复。
  • 与 M57 双活：联邦是 异步复制，消费端必须幂等；延迟窗口内可能双发。
  • Federation：上游 Exchange 消息 异步 推到下游，适合 广域、多活读；延迟与重复要业务接受。
  • Shovel：点对点 主动搬运 Queue/Exchange，适合 系统迁移、异构桥接。
  • 顺序与重复：跨 DC 复制几乎必然 at-least-once，消费端幂等必备（M57）。

面试追问

  • Federation 与 Shovel 选型：谁主动、谁被动？（答： Federation 上游 主动推 到下游；Shovel 下游 主动拉 上游；跨机房 网络方向与权限 决定选型。）
  • 联邦链路中断重启后，会不会重复灌消息？（答： 可能重复；取决于 ack 点与重连策略；下游需 幂等或 dedup。）

生产注意

  • 插件版本与 Erlang/OTP 匹配；联邦 带宽与 TTL 要监控，避免拖垮上游。

M28. RabbitMQ 高可用与负载均衡？

口述版： 客户端连多节点或前面挂 HAProxy/Nginx/LVS+Keepalived；生产者 confirm；消费者镜像队列；监控内存磁盘 alarm。

具体介绍

  1. 集群模式：提高并发，但单节点队列问题见 M26。
  2. 镜像队列 / Quorum：多副本，policy 或 queue 类型。
  3. HA 负载均衡：haproxy+keepalived、nginx、lvs；TCP 5672，不要只 DNS 轮询无健康检查。
  4. Federation/Shovel：跨机房（M27）。
  5. 监控：rabbitmqctl list_queues name messages_ready messages_unacknowledged；Prometheus plugin。
  • 客户端：Java 用 address shuffle + automatic recovery；多 URI 连接串优于单 IP。
  • 脑裂：网络分区时 Rabbit 可能 双主写（classic 镜像时代问题）；Quorum 依赖 Raft 多数派。
  • 容量：连接数、channel 数、队列数上限要在 峰值压测 中验证。

面试追问

  • TCP 负载均衡为什么要 长连接 且注意 sticky 吗？（答： AMQP channel 状态在连接上；短连接 握手贵；部分场景要 同一连接落同一节点（或 客户端直连多个 broker）。）
  • 如何验证 mirror/quorum 真的在同步？（答： 看 policy/operator 状态、**rabbitmqctl list_queues** slave/sync 标记；压测 kill master 看 消息是否丢、晋升时间。）

生产注意

  • blocked connection 告警要联动 上游发布限流，否则雪崩到应用线程池。

M29. Publisher Confirm 与 Return？

口述版： Confirm 是 Broker 确认已接收/持久化；Return 是 mandatory 模式下消息无法路由到队列时退回生产者。

具体介绍

  • 异步 confirm 吞吐更高。
  • 不可路由要监听 return 回调打日志告警。
  • Spring AMQP：CorrelationData 关联 confirm；return callback 打 不可路由 告警（常见 bug：Exchange 名错、Binding 缺失）。
  • Confirm 模式：单条 confirm vs 批量 confirm；批量吞吐高但 失败定位 要 correlationId。
  • Return：mandatory=false 时不可路由消息 静默丢弃，生产必须 true + 监听 return。
  • 事务模式：channel tx 性能差，现代用 confirm 代替 tx（除非要原子 batch 且可接受吞吐）。

面试追问

  • nack confirm 与 return 分别表示什么失败？（答： nack confirm：broker 未持久/不可路由 等；return：mandatory 消息 无队列可路由 退回 producer。）
  • 异步 confirm 回调线程里能否再 publish？有什么坑？（答： 能但慎；同 channel 同步 publish 可能 死锁（回调阻塞 IO 线程）；宜 另线程/ channel 或 批量 confirm。）

生产注意

  • confirm 超时要有 补发或落本地表；不要无限阻塞业务线程等 callback。

M30. Consumer QoS 与 prefetch？

口述版： basicQos(prefetchCount) 限制未 ack 条数，防止一个消费者 hoard 消息；fair dispatch 配合手动 ack。

具体介绍

  • prefetch=1：一条一条处理，最公平。
  • 批量处理可略增大 prefetch。
  • 多 consumer 同 queue：prefetch 总未 ack ≈ consumer 数 × prefetch（global=false 时 per channel）。
  • channel 与 consumer：每个 consumer 通常独占 channel；prefetch 按 channel 生效（global=false）。
  • unacked 与内存：unacked 消息仍占 Broker 内存/磁盘，慢 consumer 会拖高 unacked。

面试追问

  • prefetch=0 在 Rabbit 里表示什么？（答： 无上限（broker 尽可能推）；易 压垮慢 consumer，生产一般设 正整数。）
  • 公平调度 fair dispatch 依赖哪些开关？（答： basic.qos(prefetch=1) 等限制 unacked；多 consumer 同队列；必要时 单 active consumer（Quorum 特性）。）

生产注意

  • 批处理 consumer 可适度提高 prefetch，但要压测 最坏单条耗时 下的 unacked 峰值。

M31. TTL + DLX 延迟与死信？

口述版： 消息或队列设 TTL，过期进 dead-letter-exchange 绑定的队列，实现延迟消费或死信转移。

具体介绍

  • 延迟队列：TTL 队列 + DLX 指到真正消费队列。
  • 注意队列头阻塞（同队列不同 TTL 的坑）→ 解法：每条消息独立 TTL 时用 DLX + 多队列 或 Redis/DB 调度。
  • 死信原因：nack requeue=false、TTL、queue max-length。
  • 延迟链：delay queue (TTL) → DLX → work queue；work queue 消费者 手动 ack。
  • per-message TTL：更灵活但注意 队列头阻塞（M14）；高阶方案用 插件 rabbitmq_delayed_message_exchange（了解）。
  • 死信与延迟共用 DLX：routing 要区分 延迟到期 vs 消费失败，避免混流。

面试追问

  • 队列 TTL 和消息 TTL 过期后都进 DLX 吗？配置点在哪？（答： 配置了 dead-letter exchange 时 通常进 DLX；在 queue arguments（x-message-ttl/x-expires）与 policy 中设置。）
  • 延迟队列本身要不要 consumer？为什么？（答： 要；延迟实现多为 TTL+DLX 转投 或 插件；到期消息 需 consumer 真正处理，否则仍堆积。）

生产注意

  • 延迟队列堆积 = 定时炸弹；到期瞬间流量尖峰要 限流 consumer 或预扩容。

M32. 内存/磁盘告警与流控？

口述版： Rabbit 内存超 watermark 会 block 生产者；磁盘满同样；要监控、限流、增加消费者、换 quorum/换集群规格。

具体介绍

  • vm_memory_high_watermark（默认 0.4）；disk_free_limit。
  • 消息堆积 + 持久化 → 磁盘涨；流控时 publish 阻塞，表现为上游 RT 升高。
  • 排查：Management → Connections blocked；降 prefetch、扩 consumer、删无消费队列、开 lazy queue（冷数据落盘）。
  • alarm 级别：memory alarm → block publishers；disk alarm 同理；Management UI 标 blocking。
  • lazy queue：消息 predominantly on disk，缓解 memory alarm，适合 大 backlog。
  • policies：TTL、max-length、overflow（reject/drop-head）防止 单队列吃光内存。

面试追问

  • 流控 block 的是 publisher 还是 consumer？（答： Rabbit 内存/磁盘 alarm 主要 block connection 上的 publisher；consumer 慢间接导致 publisher 被反压。）
  • 如何在不丢消息前提下清空超大堆积？（答： 扩容 consumer、临时加队列分流（若可接受乱序）、降级跳过非核心；勿 无 ack purge；KF 可 调 retention 仅当业务允许丢历史。）

生产注意

  • 磁盘水位与 消息 retention（无消费） 联动；无 consumer 的 durable 队列是常见事故源。

M33. 设计：支付成功通知 + DLQ？

口述版： 支付成功发 Direct Exchange，routing 到 notify 队列；消费者调短信/积分，失败 nack 重试 3 次进 DLQ；DLQ 告警人工补偿；全程 messageId 幂等。

具体介绍

  • Confirm + 持久化 + 手动 ack。
  • 监控 DLQ 深度（S）。
  • 落地参数：x-dead-letter-exchange、应用内 retry 计数或 x-delivery-limit=3、幂等表 payment_id + notify_type。
  • 重试策略：应用内 retry 与 x-delivery-limit 二选一或组合；避免 双重重试 放大流量。
  • 下游隔离：短信/积分/推送 分队列 或分 consumer，避免慢通道拖死支付通知。
  • 可观测：messageId 贯穿 confirm → consume → 第三方回执。

面试追问

  • 支付成功消息重复，积分加了两次怎么从 MQ 侧证明根因？（答： 查 messageId/offset 重复投递、consumer 日志双 ack、重平衡重复消费；对比 broker 投递次数 与 业务幂等表。）
  • DLQ 消息如何安全 replay 到主队列？（答： 修根因后 单条 人工/脚本 replay；带 幂等；限流；记录 replay audit；避免 无限循环回 DLQ。）

生产注意

  • 第三方超时 不要无限 nack requeue；超时进 DLQ + 异步补偿更可控。

M34. Rabbit vs Kafka 业务选型？

口述版： 订单、通知、任务用 Rabbit；日志、埋点、CDC、大数据管道用 Kafka；要事务消息国内常 Rocket。

具体介绍

  • 团队栈、运维能力、顺序/吞吐需求决定。
  • 硬边界：要 多订阅 + 复杂路由 + 低延迟 → RB；要 TB 级日志 + 重放 + 流计算 → KF；要 事务消息 + 电商中间件 → Rocket。
  • 混合架构：业务 RB/Rocket + 日志 KF 很常见；同一事件双写 要幂等与对账。
  • 团队能力：运维 Kafka 需要 partition 均衡、ZK/KRaft 经验；Rabbit 要懂 内存与 mirror。

面试追问

  • CDC 进 Kafka 再 fan-out 给业务 consumer，和直接 RB 各优缺点？（答： CDC+KF 解耦 DB、可回溯、多订阅；RB 路由灵活、延迟低；CDC 要 运维 Connect/Schema，RB 适合 任务型队列。）
  • 小团队只有 Rabbit 运维经验，日志量日上亿怎么办？（答： 优先 KF/Pulsar 日志型 或 云托管 MQ；硬上 RB 会 镜像/磁盘/联邦 吃紧；或 采样+批量 降量。）

生产注意

  • 避免 用 Kafka 做复杂路由 却缺少 stream 处理团队；避免 用 Rabbit 存 TB 日志。

5.5 Kafka 专章

M35. Topic、Partition、Replica？

口述版： Topic 逻辑名；Partition 是并行与存储单元，有序日志；Replica 跨 broker 备份，leader 对外读写，follower 同步。

具体介绍

  • Partition 数 ≥ 消费者数才能满并行。
  • 增加 partition 可提高吞吐但 key 顺序范围缩小（同 key 仍进同一 partition，新 partition 只分担无 key/新 key）。
  • 配置：num.partitions 默认、replication.factor 生产建议 3；log.segment.bytes 影响 retention 段文件。
  • Leader 分布：同一 broker 不要承载过多 partition leader，避免 热点机器。
  • 副本放置：replica.fetch.max.bytes 与消息大小匹配；跨 AZ 复制增加 延迟与 ISR 风险。

面试追问

  • partition 数谁决定？创建后能减吗？（答： 创建 topic 时指定；只能增不能减（减需 新 topic 迁移）；过多 partition 增 文件句柄与 rebalance 成本。）
  • 没有 key 的消息如何选 partition？（答： 轮询（sticky 批次内）；或 随机；无法保证同业务 id 同分区，有顺序需求必须 设 key。）

生产注意

  • 生产 topic 创建规范：RF、min.insync、retention 默认值不能沿用集群 default 就上线。

M36. Consumer Group 与 rebalance？

口述版： 同 Group 内一条消息只被一个 consumer 消费；成员变化、订阅变化、partition 变化会 rebalance，期间 stop the world 式暂停消费。

具体介绍

  • Group coordinator 管理 offset。
  • 不同 Group 各自独立消费全 topic。
  • rebalance 触发：member join/leave、订阅 topic 变更、partition 数变、session.timeout 心跳丢失。
  • 排查 lag 尖刺：对照 rebalance 日志时间点与 lag 曲线。
  • static membership：group.instance.id 重启不变，减少 不必要的 rebalance。
  • partition assignor：range vs round-robin vs sticky；sticky 利于 局部性 与减少迁移。

面试追问

  • rebalance 期间 consumer 还能 poll 吗？（答： 协议分版本；经典上 rebalance 会 stop fetch；新版 ** cooperative sticky** 减少 全停；仍应避免 长处理阻塞 rebalance。）
  • 一个 consumer 订阅两个 topic，rebalance 粒度是什么？（答： 以 Group 内所有 subscribed topic-partition 为 一次 rebalance 分配单元；一 topic 变化 整组重分配。）

生产注意

  • 频繁 deploy 导致 rebalance 尖刺 → 固定 group.instance.id 或 cooperative rebalance。

M37. Leader、Follower、ISR？

口述版： 每个 partition 一个 leader；ISR 是 caught-up 的 replica 集合；acks=all 要求 ISR 都 ack；unclean 选举可能丢数据换可用。

具体介绍

  • min.insync.replicas 与 acks 配合：例如 RF=3、min.insync=2、acks=all → 至少 2 副本 ack 才成功。
  • under-replicated 要告警（follower 落后或掉 ISR）。
  • Broker 可靠性：禁止 unclean leader election（数据完整性优先）。
  • HW/LEO（了解）：follower 落后 leader 的 offset 差影响 可见性 与 unclean 风险。
  • controller：负责 partition leader 选举；controller 迁移会有 短暂元数据不稳定。

面试追问

  • acks=all 但 min.insync=1 和 =2 在单 broker 宕机时有何差别？（答： min=1：至少 1 副本 即可写，易丢未同步；min=2：需 2 副本 ack，单副本宕机 可能写不可用 但 更安全。）
  • follower 掉出 ISR 后如何重新加入？（答： 追平 leader LEO 后 重新加入 ISR；取决于 replica.lag.time.max.ms 等；落后太多 持续 out of sync。）

生产注意

  • replica.lag.time.max.ms 过小会导致 ISR 抖动 与发送失败；要按网络 RTT 调。

M38. Offset 提交与 at-least-once？

口述版： 自动提交可能处理中宕机丢消息；手动提交在业务成功后 commitSync/Async；处理完再提交典型 at-least-once，失败不提交会重复。

具体介绍

  • 重复：提交后宕机已处理会再消费 → 幂等。
  • 丢失：先提交后处理失败 → 丢业务效果。
  • 推荐：enable.auto.commit=false；业务成功后 commitSync；批量消费注意 部分成功 的 offset 粒度（逐条 vs 批次）。
  • 异步 commit：commitAsync 失败可能 重复消费 更大；关键链路用 commitSync 或记录 业务幂等。
  • seek：人工 reset offset 用于 补数/重放，要有 审批与幂等，防生产误操作。

面试追问

  • 自动提交间隔 5s，处理 2s 宕机丢还是重复？（答： 可能 重复（已 auto commit 但未处理完）或 丢（处理完未 commit）；手动 commit 在 业务成功后 更可控。）
  • 消费进度存储在 __consumer_offsets，了解即可，它丢了怎么办？（答： Group 从 earliest/latest 或 reset 策略重消费；可能大量重复；需 备份 offset 与 幂等；内部 topic 多副本一般 不丢。）

生产注意

  • 消费 DB 事务与 offset 提交 无法单 ACID 跨系统，故 at-least-once + 幂等是常态。

M39. Kafka 为何高吞吐？

口述版： 顺序写磁盘+Page Cache、零拷贝 sendfile、批量压缩、partition 并行；消费也是拉批量。

具体介绍

  • 不适合 大量小消息极低延迟 且要复杂路由的场景（Rabbit 更合适）。
  • 日志 retention 可回溯重消费。
  • 调优口述：linger.ms + batch.size 凑批；compression.type=lz4/zstd；consumer fetch.min.bytes。
  • Page Cache：OS 缓存 + 顺序写，消费 lag 大时 读盘 增加；要监控 磁盘 read。
  • 零拷贝：sendfile 减少用户态拷贝；batch 大时 网络带宽 成瓶颈，压缩必选。
  • 对比 RB：RB 内存队列 + Erlang 进程模型，大消息/大堆积 内存压力更直观。

面试追问

  • 为什么 Kafka 顺序写磁盘还比随机写 DB 快？（答： 顺序写+Page Cache、批量 append、少 随机 B+树页；DB 还有 事务/WAL/锁；KF 不做 复杂更新语义。）
  • 小消息 QPS 极高时 batch 参数怎么调？（答： 调 linger.ms、batch.size 提高 batch；压缩；consumer **fetch.min.bytes**；权衡 延迟 vs 吞吐。）

生产注意

  • linger.ms 增大会 增延迟减 CPU；低延迟业务要压测平衡点。

M40. Retention 与 Compact？

口述版： 按时间或大小删旧段；compact topic 保留每个 key 最新值，适合 changelog、KV 同步。

具体介绍

  • 与 Rabbit 消费即删/ack 不同，Kafka 可 重复读。
  • retention.ms / retention.bytes；compact 用于 Connect offset、schema registry 等场景。
  • delete vs compact：普通 topic 按 retention 删段；compact 保留 key 最新值，** tombstone** 删 key。
  • 重放：新 consumer group 从 earliest/latest 开始，影响 历史洪峰。

面试追问

  • compact topic 上同一个 key 连续两条 null value 表示什么？（答： tombstone 删除该 key；compact 后 该 key 被移除；连续 null 仍 语义为删。）
  • retention 改小会立刻删数据吗？（答： 后台异步删 segment；不是 立刻；依赖 log.retention.check.interval.ms；磁盘仍可能短期占满。）

生产注意

  • 误设 retention.ms 过短导致 审计/补数无法重放；变更要走审批。

M41. Rebalance 优化？

口述版： 增大 session.timeout.ms、max.poll.interval.ms 防慢消费被踢；减少不必要的订阅变更；静态成员 group.instance.id 减 rebalance。

具体介绍

  • 消费逻辑别超过 max.poll.interval。
  • 大 rebalance 导致 lag 尖刺。
  • Cooperative sticky assignor（增量 rebalance）减少 stop-the-world；KIP 相关名词了解即可。
  • heartbeat 与 poll 分离（现代 consumer）：max.poll.interval 管处理时间，session.timeout 管心跳。
  • incremental cooperative rebalance：减少 全 partition 撤销 的时间窗口。

面试追问

  • 消费逻辑里调外部 HTTP 5 分钟，要改哪两个参数？（答： **max.poll.interval.ms**（拉长）与 **max.poll.records**（减小单批）；必要时 异步处理+手动 pause/resume。）
  • rebalance listener 里适合做什么、不适合做什么？（答： 适合 提交 offset、flush 缓存、暂停拉取；不适合 长 IO、阻塞 rebalance（会 踢 consumer）。）

生产注意

  • rebalance 期间 不要 在 listener 里做重 IO；只做 partition 缓存清理等轻量操作。

M42. Kafka 顺序与 Key？

口述版： 同一 key 进同一 partition 保证分区内有序；不同 key 并行；没 key 轮询 partition 无顺序保证。

具体介绍

  • 分区数变更多 key 可能 remap（慎用改 partition）；只增 partition 不保证历史 key 分布不变。
  • 自定义 Partitioner（2.4 前常见；新版本 sticky 默认）。
  • null key：轮询 partition，严格无序；适合日志但不适合订单事件。
  • key 热点：同一 key 过多 → 单 partition 热点，需拆 key（如 orderId+shard）或接受热点。

面试追问

  • 自定义 Partitioner 在 2.4+ 默认策略下还需要吗？（答： 默认 Sticky + murmur2 key 多数够用；特殊路由（按机房/租户）才自定义；注意 升级兼容。）
  • 增加 partition 后旧 key 会迁移吗？（答： 会；hash(key) % N N 变了 bucket 变；扩容后 短期乱序/重复处理，需 幂等或 rehash 策略。）

生产注意

  • 顺序业务 禁止随意改 key 算法；变更需新 topic 双写迁移。

M43. Exactly-once 了解？

口述版： 幂等生产者防重复写；事务 API 可 read-process-write 原子；端到端还要 consumer 事务或外部幂等，业务很少宣称真 exactly-once。

具体介绍

  • enable.idempotence=true（PID + sequence）。
  • 与 M4、M19 衔接：面试结论 — Broker EOS ≠ 业务 EOS，表幂等仍要做。
  • 事务边界：Kafka 事务保证 同一 transactional.id 的 produce 与 consume offset 提交原子性（同集群）。
  • 外部系统：写 DB + 发 Kafka 仍 非原子，除非 outbox/幂等。

面试追问

  • 幂等生产者防的是哪种重复？consumer 重复谁管？（答： 幂等 producer 防 broker 重试导致 duplicate publish；consumer 重复 靠 业务幂等/事务 outbox。）
  • read_committed 消费者看不到什么消息？（答： 看不到 未 commit 的事务消息 与 abort 的事务；只读 已 commit 事务批次。）

生产注意

  • 开启事务 producer 有 吞吐成本；只在 读-改-写链 必需时用，别全局开。

M44. Kafka 监控指标？

口述版： consumer lag、under-replicated partitions、offline partitions、请求延迟、ISR 收缩、磁盘。

具体介绍

  • Burrow、Kafka Manager、Prometheus exporter（kafka_exporter）。
  • lag 持续涨 → M15、M55。
  • JMX 口述：BytesInPerSec、RequestHandlerAvgIdlePercent、log flush 延迟。
  • Broker 侧：RequestHandlerAvgIdlePercent 低表示 broker 忙；NetworkProcessor 瓶颈看线程配置。
  • Consumer 侧：lag 按 partition 看 热点 partition；单 partition lag 高常是 key 热点（M42）。

面试追问

  • offline partition 和 under-replicated 哪个更紧急？（答： offline partition（不可读写）更紧急；under-replicated 是 副本落后，有 丢数据风险 但可能仍服务。）
  • lag 为 0 是否等于没有堆积？（考虑 compact/新 group）

生产注意

  • 告警要分 绝对 lag 与 lag 增长率；突发尖峰与慢性堆积策略不同。

M45. 日志/埋点架构？

口述版： App→Kafka→Flink/Spark 或→Logstash→ES；或 Kafka→Hive；多 consumer group 各做实时与离线。

具体介绍

  • 高吞吐、可回溯、多订阅（S）。
  • 与 RB 对比：埋点 不怕重复（可去重）要吞吐 → KF；业务命令事件 要路由+低延迟 → RB/Rocket。
  • 多订阅：同一 Kafka topic 多个 group：实时大屏、离线数仓、风控各读一份。
  • Schema：Avro/Protobuf + Schema Registry 防 字段漂移 打挂下游。
  • 与 OLAP：Kafka → Flink → ClickHouse/Druid 是常见 实时数仓 入口。

面试追问

  • 日志重复消费对数仓有什么影响？如何去重？（答： 事实表重复行；用 messageId/offset+业务键 dedup、幂等写入、MERGE/窗口去重。）
  • RB 能否做同样规模的埋点管道？瓶颈在哪？（答： 不推荐；瓶颈在 镜像复制、队列数、内存、无分区并行；亿级应 KF/Pulsar。）

生产注意

  • 埋点 topic retention 长、磁盘大；容量规划与 compaction 不适用 大 value 日志要想清。

M46. Kafka 扩容注意？

口述版： 加 broker 后 partition 重分配；消费者可扩到 partition 数上限；重分配期间性能波动；跨 rack 副本分布。

具体介绍

  • kafka-reassign-partitions.sh / Cruise Control。
  • 新 partition 只影响新 key 路由策略要文档化。
  • rack.aware.assign：副本跨机架，防整机架故障丢 ISR quorum。
  • throttle：重分配可限流 leader.replication.throttled.rate 避免 打满磁盘 IO。
  • 新 broker：空 broker 加入后需 主动 reassign 才会均衡；不会自动均匀。

面试追问

  • partition 数从 6 扩到 12，老消息的 key 分布变吗？（答： 已写入数据位置不变；新消息 按新 partition 数路由；消费分配 变化，不是把老消息重算。）
  • 重分配失败 halfway 如何排查？（答： 看 kafka-reassign-partitions 日志、under-replicated、磁盘/限流；用 **kafka-reassign-partitions --verify**；必要时 rollback 计划。）

生产注意

  • 扩 partition 不可逆减；初期按 峰值 2～3 年 估 partition，避免频繁 reassignment。

5.6 RocketMQ 与其它

M47. RocketMQ NameServer 与存储？

口述版： NameServer 轻量路由，无 ZK；Broker 存 CommitLog 顺序写，ConsumeQueue 索引；类似 Kafka 但队列语义更贴近业务。

具体介绍

  • 推拉结合；延迟级别内置。
  • 国内文档、事务消息案例多。
  • 与 KF 差异：CommitLog 全 topic 顺序写 + 逻辑 Queue 索引；NameServer 无强一致，Broker 向 NS 心跳注册。
  • 配置锚点：brokerRole=ASYNC_MASTER/SYNC_MASTER、flushDiskType=SYNC_FLUSH/ASYNC_FLUSH。
  • Broker 角色：Master/Slave、Dledger 选主；CommitLog 单文件顺序写 多 topic 共享。
  • ConsumeQueue：逻辑队列索引，加速 按 queue 拉取；与 KF partition log 类似不同。
  • NameServer：无状态可水平扩；Broker 注册 Topic 路由 客户端定期拉取。

面试追问

  • NameServer 挂了客户端还能发消息吗？（答： 客户端 缓存路由 短时间可发；无法发现新 broker/ topic 变更；NameServer 集群部署，挂久 路由过期 会失败。）
  • CommitLog 与 ConsumeQueue 不一致怎么修复（了解）？

生产注意

  • ASYNC_FLUSH 性能高但宕机可能 丢末批消息；金融级常用 SYNC_FLUSH + 主从同步。

M48. RocketMQ 事务消息？

口述版： 发 half 消息→执行本地事务→commit/rollback→Broker 回查未知状态；保证最终消息与本地事务一致。

具体介绍

  • 与 M22 呼应。
  • 回查接口要实现幂等。
  • 排查：半消息堆积、回查失败日志、checkLocalTransaction 超时 → 本地事务状态不明，需对账。
  • 状态回查：本地事务 UNKNOWN 时 Broker 反复 check；接口要 快速、幂等、可缓存。
  • 与本地表对比：半消息减少 扫表发 MQ 但绑定 Rocket；跨 MQ 产品迁移成本高。

面试追问

  • commit 和 rollback 调用失败（网络）怎么处理？
  • 半消息超时未决，下游从未收到，业务如何感知？（答： 查 事务状态接口/回查日志、本地事务表；告警 half 超时；用户侧 超时未支付/关单。）

生产注意

  • 回查逻辑 禁止 开新事务写 unrelated 表，避免死锁与状态不一致。

M49. Rocket 延迟 vs Rabbit TTL？

口述版： Rocket 固定 18 级延迟；Rabbit TTL+DLX 灵活但队列头阻塞要小心；Kafka 常外部调度。

具体介绍

  • 选型看延迟精度与运维。
  • Rocket：messageDelayLevel=1 对应 1s，共 18 级；不能任意 37 分钟这种细粒度除非改配置表。
  • 业务适配：订单 30 分钟超时关单，Rocket 2h 档可能 不够细 → 外部调度或 RB TTL。
  • Rabbit 插件：delayed_message_exchange 可替代部分 TTL+DLX 头阻塞问题（运维要装插件）。

面试追问

  • Rocket 延迟级别能运行时改吗？改完对已发消息有效吗？（答： 配置在 broker；已发消息按发送时级别；改配置 只影响新发。）
  • 同一业务既要 5s 又要 30min 延迟，Rocket 怎么配？（答： 用 不同 delay level 映射或 两条 topic；Rocket 固定级别， arbitrary delay 用 定时任务+MQ 更灵活。）

生产注意

  • 延迟消息 不是定时器服务；海量延迟任务考虑 时间轮 + DB/Redis 分片调度。

M50. Pulsar / 云 MQ？

口述版： Pulsar 存算分离、多租户；云 SQS 免运维；MQTT 物联网；超大规模或 Serverless 才常引入。

具体介绍

  • P1 了解即可。
  • 云 MQ（SQS、阿里云 MQ）：免运维、at-least-once、DLQ 原生；与自建 RB/KF/Rocket 的 tradeoff 是成本与管控粒度。
  • Pulsar：BookKeeper 存段、Broker 无状态，扩缩容 与多租户强；运维复杂度高于 Rocket。
  • MQTT：物联网弱网、QoS0/1/2；与 AMQP 业务消息 协议不同，网关桥接常见。
  • 云 MQ：SQS 可见性超时 ≈ ack 窗口；阿里云 MQ Rocket 协议兼容要注意 版本差异。

面试追问

  • Pulsar 存算分离对比 Kafka 的 broker 本地盘各适合什么规模？（答： Pulsar BookKeeper 分离 适合 云原生、多租户、弹性扩；KF 本地盘 成熟 超大吞吐、生态厚。）
  • Serverless 用 SQS 还要自己管幂等吗？（答： 要；SQS at-least-once、visibility timeout 仍 重复；Lambda 幂等+DLQ 必备。）

生产注意

  • 云 MQ 配额、计费、区域 要在架构期评估；跨 region 复制延迟与 M57 同类问题。

5.7 设计与排查

M51. 削峰与连接池？

口述版： 峰值进 MQ，消费者速率受限于线程池和 DB 连接池，消费者数×每线程连接不能超过池大小；否则消费者堵在拿连接，lag 仍涨。

具体介绍

  • 配合 限流、降级、扩容消费者与 DB 只读副本。
  • 公式：有效消费 TPS ≤ min(消费者并行度 / 单条耗时, 连接池大小 / 单条持有连接时间, 下游 RPC QPS 限额)。
  • 线程模型：consumer 线程数 ≠ 连接数；每线程持连接处理一条要注意 池大小 ≥ 并发。
  • 批量写库：合并 insert 提高吞吐，但要权衡 延迟与失败重试粒度。
  • 限流：Sentinel/RateLimiter 在 consumer 入口保护 DB。

面试追问

  • lag 涨但 CPU 低，可能是什么瓶颈？（答： 下游 DB/HTTP 慢、锁等待、prefetch 过小、单 partition、GC/IO wait；CPU 低不代表 无瓶颈。）
  • 消费者 20 个实例，连接池 max=10，会出现什么现象？（答： 连接等待/超时、lag 涨、假死；实例数应 ≤ 池大小 或 池按实例扩、批量处理。）

生产注意

  • 压测要模拟 峰值 lag 下连接池等待时间，而不只是单条 happy path。

M52. 同步改异步如何返回？

口述版： 接口先返回受理单号；客户端轮询状态；或 WebSocket 推送；或回调 URL；核心是保证 状态可查 与幂等提交。

具体介绍

  • 避免用户以为失败重复下单。
  • MQ 侧：受理单号写入 可查询状态表 再发消息；消息带 requestId 与 HTTP 入口一致。
  • 状态机对外：ACCEPTED → PROCESSING → SUCCESS/FAILED 枚举清晰，API 与 MQ 消费 同键更新。
  • 重复提交：入口 requestId 幂等 + MQ 消息带同一 id；用户重试 HTTP 不会双单。
  • 超时：轮询接口要 说明处理中 vs 不存在，防前端无限轮询。

面试追问

  • 消息已发但 DB 受理单未 commit，用户查状态显示什么？（答： 显示 处理中/未知；应用 先本地事务再发 MQ 或 Outbox；勿 先 MQ 后 DB 无补偿。）
  • WebSocket 推送失败如何与 MQ 消费结果对齐？（答： 消费成功 写推送任务表；WS 失败 重试/离线消息；同一 bizId 关联 MQ 消费与推送状态。）

生产注意

  • 禁止 仅返回 200 而无单号；异步受理必须有 可追溯 id。

M53. MQ 与分布式事务？

口述版： 强一致跨服务少用 MQ 一把梭；Saga 用 MQ 发补偿事件；TCC 的 try confirm cancel；本地消息表是最常见落地。

具体介绍

  • 2PC 在 MQ 场景少直接用。
  • 与 Seata、自研对账配合（S）。
  • Rocket 事务消息 适合「本地写 + 发一条下游事件」；Saga 适合多步长流程。
  • Saga 编排： orchestrator 发 step 事件，失败发 补偿；每步 consumer 幂等。
  • TCC：Try 占资源，Confirm/Cancel；与 MQ 配合时 Cancel 消息也要 可靠投递。
  • 2PC：XA 在 MQ 场景少，性能与 Broker 参与 都不友好。

面试追问

  • 本地消息表 vs Rocket 事务消息，你会在电商订单选哪个？（答： 已用 Rocket 且要半消息语义 选 Rocket；通用 DB 事务+扫表/CDC 选本地消息表；看 运维与回查成本。）
  • Saga 补偿顺序与正向顺序相反吗？乱序到达怎么办？（答： 补偿常 逆序；乱序用 状态机+可补偿标记、幂等；MQ 不保证全局序 时要 版本号。）

生产注意

  • 分布式事务文档要写清 最终一致窗口 与对账频率，避免业务误以为强一致。

M54. 毒消息处理？

口述版： 重试 N 次进 DLQ；记录 payload 和 stack；告警；人工修复后 requeue 或走补偿接口；别让一条坏消息 infinite redelivery。

具体介绍

  • Rabbit：x-delivery-limit 或应用计数。
  • KF：消费失败发 retry topic，次数上限进 DLT。
  • Rocket：RECONSUME_LATER 默认 16 次进 DLQ。
  • 跳过要有审计（谁、何时、哪条 messageId）。
  • 识别毒消息：固定 payload 必 fail、反序列化错误、下游 404 配置错误；应 快速进 DLQ 而非无限 retry。
  • 告警内容：含 topic、messageId、stack 摘要、前 1KB payload（脱敏）。
  • replay 流程：修代码/修数据 → DLQ requeue → 监控 重复幂等 是否生效。

面试追问

  • 重试指数退避在 MQ 层还是应用层做？（答： 应用层更可控（业务语义）；MQ TTL/DLX/retry queue 做 粗粒度；二者可 组合。）
  • 跳过毒消息不 ack 会怎样？（答： 一直 redelivery、阻塞后续消息（单 consumer 时）、lag 永降；应 nack+requeue=false 进 DLQ。）

生产注意

  • 生产 禁止 requeue=true 无上限；与 M13、M33 统一 retry 策略文档。

M55. 消费 lag 暴涨排查？

口述版： 看生产是否突增、消费者是否全挂、GC/STW、单条 SQL 慢、rebalance、Broker IO；再扩 consumer、优化代码、临时降级。

具体介绍

  • Kafka：kafka-consumer-groups.sh --describe --group xxx。
  • Rabbit：queue depth、consumer utilisation、blocked connections。
  • 交叉 JVM 模块 GC 毛刺（M58）。

分 MQ 排查清单

步骤 RB KF Rocket
1. 积压量 ready + unacked partition lag consume offset diff
2. 生产突增 publish rate BytesIn send TPS
3. 消费健康 consumer 数、utilisation consumer 实例、rebalance consumer 在线
4. 慢处理 单条 trace、DB max.poll 超时日志 消费耗时监控
5. Broker memory/disk alarm ISR、磁盘 commitlog、磁盘
6. 止血 扩 consumer、lazy queue 扩 consumer≤partition、降 batch 扩 consumer、降 pull batch
  • 时间对齐：lag 曲线与 发布变更、大促、rebalance 日志 对齐看因果。
  • JVM：Full GC 导致 max.poll.interval 超时 → 重复消费 + lag 假降真升。

面试追问

  • 只扩 consumer 不优化 SQL，lag 下降缓慢说明什么？（答： 瓶颈在 单条处理耗时/DB 非 并行度；需 优化 SQL、缓存、批处理 或 限流生产。）
  • Broker disk 100% 时 consumer lag 会怎样？（答： 生产 blocked、消费变慢、可能 crash；lag 暴涨；紧急 扩盘、删 segment、限流。）

生产注意

  • 止血顺序：停非核心生产 > 扩消费 > 优化热点 > 加 partition；避免无序操作。

M56. 重复扣款与 MQ？

口述版： 证明 messageId 重复投递或 consumer 重复 ack 前处理；查幂等表、支付渠道单号；根因常在 ack 顺序或重试无上限。

具体介绍

  • 支付回调 + MQ 双通道要 统一幂等键（S）。
  • 排查顺序：渠道侧单号是否重复 → 幂等表是否命中 → 消息 messageId 是否重复 → ack/offset 是否在业务前提交。
  • 双通道：支付渠道回调与 MQ 通知 同一 bizId 幂等；表 uniq(channel, out_trade_no)。
  • 对账文件：T+1 与渠道对账发现重复扣款，回溯 messageId 与 offset 提交顺序。
  • 资金类：宁可 重复处理返回成功（幂等） 不可漏 ack 导致重复 unknown 状态。

面试追问

  • 幂等表在扣款前还是后插入？失败怎么回滚？（答： 常 先占幂等键/预插入 processing，成功 更新 done；失败 标记 fail 可重试；扣款与 本地事务 同事务或 TCC。）
  • 如何证明是 MQ 重复而非渠道重复通知？（答： 对 messageId/offset、投递时间、consumer 日志 与 渠道回调 id；MQ 重复 同 payload 多 offset。）

生产注意

  • 金融链路 audit log 保留 messageId、offset、consumer instance，便于监管排查。

M57. 跨机房双活 MQ？

口述版： 异步复制有延迟，可能重复；冲突解决靠幂等与版本号；脑裂时两边都可能发，消费端要可识别来源；Federation/Shovel/Mirror 跨 DC 各有限制。

具体介绍

  • RPO/RTO 与业务接受度。
  • 优先单活写双活读等折中（S）。
  • RB Federation 非同步双写；KF MirrorMaker 延迟复制；Rocket Dledger 多副本 通常单集群内，跨 DC 仍多异步。
  • 写入策略：单活写（一个 DC publish）+ 双活读；或 分业务单元 各写各的 topic，全局聚合读。
  • 冲突：同一用户双活写可能 版本冲突；用 version/时间戳 拒绝旧更新。
  • MirrorMaker / Federation 延迟：RPO>0 时下游要 幂等 + 去重窗口 ≥ 复制延迟。

面试追问

  • 脑裂时两边都发订单创建消息，如何合并？（答： 全局唯一 bizId、DB 唯一约束、对账合并；MQ 不能防脑裂双写，靠 业务层。）
  • RPO/RTO 1 分钟 vs 1 小时对 MQ 架构有何不同要求？（答： RPO 1min 要 多 AZ 同步复制、监控、自动 failover；RTO 1h 可 冷备+手工切换；前者 成本高。）

生产注意

  • 跨机房 同步复制 MQ 延迟大，多数业务选 异步 + 幂等；宣传「双活零丢」要审技术方案。

M58. 全链路 traceId 透传？

口述版： HTTP 入口生成 traceId 放 MDC；发 MQ 写到 header/properties；消费者取出写 MDC 再调下游；日志、监控同一 trace 串起来。

具体介绍

  • Rabbit：AMQP correlation_id / headers traceId。
  • Kafka：record headers traceparent / W3C Trace Context。
  • Rocket：userProperty 透传。
  • OpenTelemetry 统一标准。
  • 案：结合项目 STAR 讲一次 lag/重复排查（S）— 用 traceId 关联 生产 send → Broker → 消费 → DB 四段日志，快速定位是 重复投递 还是 消费两次。
  • 跨语言：header 名统一 traceparent（W3C）或 X-Trace-Id；避免各服务自定义不可串联。
  • MQ 与 RPC：consumer 取出 trace 写 MDC，Feign/gRPC metadata 继续透传。
  • lag 排查案例：用 traceId 串 Producer send → Broker 落盘 → Consumer start → DB commit 四段，区分重复投递 vs 双消费。

面试追问

  • MDC 在线程池切换时如何不丢 traceId？（答： TaskDecorator 传递 MDC；TTL 线程池（TransmittableThreadLocal）；消费端 从 header 注入 MDC。）
  • 批量消费一条失败，trace 如何对应到单条 message？（答： 每条 独立 span/子 traceId 或 batchId+index；日志打 partition-offset-key；失败 只重试该条（若协议支持）。）

生产注意

  • 日志规范：入口生成 trace，禁止下游各自 random 新 id 导致链路断。

延伸阅读： 原 RabbitMQ 高可用实践已并入 M25～M28；后续若有 MQ 专题文可在此追加链接。

本章速记：可靠性三板斧

  1. 生产：RB confirm + mandatory return；KF acks=all + min.insync.replicas + 幂等生产者；Rocket 同步/事务 + 本地消息表兜底。
  2. Broker：RB Quorum/Mirror + durable；KF ISR + 禁 unclean election；Rocket SYNC_MASTER + SYNC_FLUSH（按 SLA 选）。
  3. 消费：手动 ack / 成功后 commit offset；幂等键；DLQ + 重试上限；lag/depth 告警。

堆积 / 丢消息排查入口：M15 通用五步 → M55 分 MQ 表 → M4 三板斧对号入座。
