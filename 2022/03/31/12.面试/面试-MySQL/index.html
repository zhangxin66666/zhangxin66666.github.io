My5. 为什么 InnoDB 推荐自增整型主键？

口述版： 自增主键插入基本是页尾追加，减少 B+ 树分裂和页移动；整型比 UUID 更短，二级索引叶子存主键值也更省空间。业务上用无意义 surrogate key，业务唯一性用唯一索引保证。

具体介绍

InnoDB 聚簇索引叶子存整行数据，主键即数据物理组织顺序。

顺序插入 vs 随机插入

主键类型 插入位置 页分裂 二级索引体积
自增 BIGINT 当前最大页尾 少 8 字节引用
UUID 随机 树中间任意页 多、碎片 16/36 字节引用
  • 二级索引：每条辅助索引记录都带主键值回表；主键越长，所有二级索引越大，Buffer Pool 命中率下降。
  • 业务主键：订单号等业务唯一键放 UNIQUE， surrogate id 自增做 PK 是常见模式。

面试追问

  • 分库分表为什么常用雪花而不是自增？（答： 全局唯一、趋势递增、无中心；接受略多页分裂与索引体积。）
  • 联合主键可以吗？（答： 可以，但二级索引更大；高并发表仍常见单列自增 id。）

常见坑

  • 用 UUID 字符串做主键却抱怨插入慢、表体积大——先改 id 策略或至少用 UUID_TO_BIN(uuid, swap) 等有序 UUID 方案。

My6. B+ 树为什么适合做数据库索引？

口述版： B+ 树非叶子只存键不存行，扇出大、树高低，磁盘 IO 少；叶子链表支持范围扫描和 order by；哈希只能等值，不适合范围与排序。

具体介绍

InnoDB 索引即 B+ 树（整型 PK 聚簇；辅助索引叶子存 PK + 可选覆盖列）。

结构 等值 范围扫描 排序 典型场景
哈希 O(1) 不支持 不支持 Memory 引擎、Redis
B 树 O(logN) 可 可 文件系统
B+ 树 O(logN) 叶子链表 叶子顺序 InnoDB
  • 非叶子不存行：单页 16KB 可存更多键 → 树高低 → 磁盘 IO 次数少（通常 2～4 层千万行）。
  • 叶子双向链表：WHERE id BETWEEN、</>、ORDER BY id 顺序读友好。
  • Memory 引擎 曾支持哈希索引，仅等值；InnoDB 自适应哈希 AHI 是内部优化，不替代 B+ 树。

面试追问

  • 为什么不用二叉/红黑树？（答： 扇出小、树高、一次磁盘 IO 读一页里很多键，B+ 更匹配页式存储。）
  • 覆盖索引和 B+ 树关系？（答： 辅助索引叶子若已含查询列，无需回表聚簇。）

常见坑

  • 把「哈希表 O(1)」直接类比 InnoDB 主键——主键仍是 B+ 树。

My7. 联合索引字段顺序如何设计？

口述版： 把区分度高、常作等值的列放前；范围查询列尽量放后（最左前缀遇范围停止）；若有 order by，让索引顺序与排序一致避免 filesort。

具体介绍

设计步骤（生产可落地）

  1. 列出 WHERE 中高频等值列（user_id、tenant_id）。
  2. 把选择性高的列靠前（区分度 count(distinct)/count(*) 越大越好）。
  3. 范围列（time、>、BETWEEN、LIKE 'xx%'）放等值列之后——最左前缀遇范围停止匹配后续列。
  4. 若 SQL 常 ORDER BY created_time DESC，考虑 (user_id, created_time) 与排序同向。

示例

  • 覆盖索引：SELECT user_id, created_time 且索引 (user_id, created_time) → Extra Using index。
  • 优化器可能对 IN/= 列重排，但不要依赖；建索引时按真实 SQL 顺序。

面试追问

  • (a,b,c) 索引，条件 a=1 AND c=3 能用索引吗？（答： 用到 a；c 无法跳过 b 单独用，除非 icp/索引条件下推部分场景。）

常见坑

  • 把低区分度 is_deleted 放第一列导致索引几乎无效。

My8. 前缀索引是什么，如何选长度？

口述版： 对长字符串只索引前 N 字符，省空间；长度要在选择性与大小间折中，用 count(distinct left(col,N))/count(*) 估算。

具体介绍

定义：对 VARCHAR/TEXT 只索引前 N 个字符：INDEX idx_email (email(20))。

选 N 的方法

权衡 说明
N 过小 选择性差，重复多，加速弱
N 过大 接近全列索引，占空间
唯一性 前缀索引不能保证整列唯一（需全列 UNIQUE）
  • 排序：前缀索引通常无法满足 ORDER BY email（除非前缀即排序前缀且兼容）。
  • utf8mb4：按字节算长度上限 3072（767 历史限制视版本/innodb_large_prefix）。

面试追问

  • 邮箱前缀 8 位够吗？（答： 看数据分布，用上面 SQL 量 selective，一般 12～20 常见。）

常见坑

  • 用前缀索引做唯一约束业务上「重复」——碰撞在完整 email 不同、前缀相同。

My9. 唯一索引与普通索引插入差异？

口述版： 普通索引更新可进 Change Buffer 延迟合并；唯一索引必须立刻读页判重，不能走 change buffer，插入往往更贵。

具体介绍

Change Buffer 前提：仅对非唯一的二级索引页，且页不在 Buffer Pool 时，把变更缓存在 change buffer，后续 merge 进索引页。

索引类型 插入 secondary 是否读页 能否 change buffer
普通二级 可延迟 可以
唯一二级 必须读页判重 不可以
  • 唯一校验：必须看到当前页所有记录 → 随机 IO + 无法合并优化 → 高并发插入唯一索引常成为瓶颈。
  • 优化：批量插入、先普通索引再异步去重（业务允许时）、或雪花 id 无业务唯一冲突。

面试追问

  • 主键唯一索引插入为何也慢？（答： PK 是聚簇，必改数据页，不走 change buffer 的是非唯一二级优化；PK 仍要维护 B+ 树。）

常见坑

  • 给每个字段都加 UNIQUE「保险」，却导致写入 TPS 骤降。

My10. Index Merge 索引合并是什么？

口述版： 优化器对多个单列/多索引分别扫描再 union/intersect，出现在 EXPLAIN type=index_merge。

具体介绍

Index Merge：对多个索引分别扫描，再 union / sort-union / intersect 得到 rowid/PK 集合。

Extra / type 含义
type=index_merge 使用合并
Using union(a,b) 两索引结果并集
Using intersect 交集（AND 多列各走索引）
  • 代价：多次索引扫描 + 去重/排序，有时不如 单列联合索引 或改写为 UNION ALL 两条子查询。
  • 优化器开关：optimizer_switch 含 index_merge=on/off。

面试追问

  • OR 一定走 index merge 吗？（答： 不一定；可能全表扫，或改写成 union all 更稳。）

常见坑

  • 看到 index_merge 就认为「用了两个索引一定快」——rows 仍可能很大。

My11. 没有主键时 row_id 隐藏主键？

口述版： 表无 PK/非空唯一键时 InnoDB 生成 6 字节 DB_ROW_ID 聚簇；多表共用计数器，仅兜底，生产应显式主键。

具体介绍

InnoDB 要求每行有聚簇键：优先用户定义的 PRIMARY KEY；否则第一个 NOT NULL UNIQUE；都没有则自动生成 DB_ROW_ID（6 字节，全局递增）。

  • 多表共享 row_id 计数器（非每表独立），仅保证聚簇唯一。
  • 所有二级索引叶子仍存 row_id → 运维 SHOW TABLE STATUS、逻辑备份行顺序与业务 id 不对齐。
  • 推荐：显式 BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY。

面试追问

  • 有 UNIQUE 但 nullable 会怎样？（答： 多个 NULL 不违反 UNIQUE，不能当聚簇键；仍可能生成 row_id。）

常见坑

  • 「表没主键也能用」——复制、pt-osc、某些 ORM 分页/同步依赖 PK 会踩坑。

My12. CHAR 与 VARCHAR、DATETIME 与 TIMESTAMP？

口述版： CHAR 定长省长度字段适合短码；VARCHAR 变长省空间。TIMESTAMP 4 字节有时区转换 2038 限制；DATETIME 8 字节范围大，推荐业务统一 UTC 存 DATETIME。

具体介绍

类型 存储 适用
CHAR(n) 定长 n×字符集字节，尾部空格 trim 比较（旧行为需注意） 固定长度码：MD5(32)、性别 M/F
VARCHAR(n) 1～2 字节长度 + 数据 变长姓名、地址
DATETIME 8 字节，1000-9999，无时区 业务存 UTC，应用层转换
TIMESTAMP 4 字节，1970-2038，会话时区 自动 ON UPDATE（慎用）
  • 索引长度：CHAR(255) utf8mb4 最多 1020 字节参与索引，易超长需前缀。
  • MySQL 8.0 默认 explicit_defaults_for_timestamp 等行为与 5.7 不同，迁移要测。

面试追问

  • 为什么很多公司禁 TIMESTAMP？（答： 2038、时区隐式转换、DST 边界。）

常见坑

  • status CHAR(1) 存 '1' 与 '01'——业务与 ORM 填充不一致。

My13. utf8 与 utf8mb4 区别？

口述版： MySQL 的 utf8 实为最多 3 字节，不支持 emoji；utf8mb4 完整 Unicode，生产默认 utf8mb4 + utf8mb4_unicode_ci 或 _0900_ai_ci（8.0）。

具体介绍

  • **utf8**：MySQL 历史别名，最多 3 字节，缺 4 字节字符（emoji、部分生僻字）→ 插入截断或报错。
  • utf8mb4：完整 UTF-8，每字符最多 4 字节；生产默认。
排序规则 特点
utf8mb4_general_ci 快，排序略粗
utf8mb4_unicode_ci 基于 Unicode 规范
utf8mb4_0900_ai_ci 8.0 默认，性能与准确性更好
  • 索引：同样 VARCHAR(191)，mb4 占满 767/3072 字节限制更快触顶 → 常见 191 可全列索引（旧 767 时代）。
  • 连接、客户端、表、列四层字符集应一致，避免 CONVERT(implicit) 导致索引失效。

面试追问

  • 从 utf8 迁 mb4 要注意？（答： 列长度字节变大、索引超长、锁表 DDL 时间。）

常见坑

  • 接口已 utf8mb4，表仍是 utf8，emoji 写入失败。

2.2 SQL 执行与 Buffer Pool

My15. 一条 SQL 的执行过程详解？

口述版： 从准备更新一条数据到事务的提交的流程描述 首先执行器根据 MySQL 的执行计划来查询数据，先是从缓存池中查询数据，如果没有就会去数据库中查询，如果查询到了就将其放到缓存池中

具体介绍

从准备更新一条数据到事务的提交的流程描述

  • 首先执行器根据 MySQL 的执行计划来查询数据，先是从缓存池中查询数据，如果没有就会去数据库中查询，如果查询到了就将其放到缓存池中
  • 在数据被缓存到缓存池的同时，会写入 undo log 日志文件
  • 更新的动作是在 BufferPool 中完成的，同时会将更新后的数据添加到 redo log buffer 中
  • 完成以后就可以提交事务，在提交的同时会做以下三件事
    • 将redo log buffer中的数据刷入到 redo log 文件中
    • 将本次操作记录写入到 bin log文件中
    • 将 bin log 文件名字和更新内容在 bin log 中的位置记录到redo log中，同时在 redo log 最后添加 commit 标记

至此表示整个更新事务已经完成

为什么Mysql不能直接更新磁盘上的数据而且设置这么一套复杂的机制来执行SQL了？

因为来一个请求就直接对磁盘文件进行随机读写，然后更新磁盘文件里的数据性能可能相当差。因为磁盘随机读写的性能是非常差的，所以直接更新磁盘文件是不能让数据库抗住很高并发的。

Mysql这套机制看起来复杂，但它可以保证每个更新请求都是更新内存BufferPool，然后顺序写日志文件，同时还能

保证各种异常情况下的数据一致性。

更新内存的性能是极高的，然后顺序写磁盘上的日志文件的性能也是非常高的，要远高于随机读写磁盘文件。

正是通过这套机制，才能让我们的MySQL数据库在较高配置的机器上每秒可以抗下几干的读写请求。

2.3 日志与 ACID

My23. ACID及实现原理？

口述版： （Atomicity）原子性： 事务是最小的执行单位，不允许分割。要么全都执行,要么全都不执行；——->原子性是由undolog日志来保证的，它记录了需要回滚的日志信息，事务回滚时，撤销已经执行成功的sql （Consistency）一致性： 执行事务前后，数据保持一致；——->原子性、隔离性、持久性就是为了来保证一致性

具体介绍

  • （Atomicity）原子性： 事务是最小的执行单位，不允许分割。要么全都执行,要么全都不执行；——->原子性是由undolog日志来保证的，它记录了需要回滚的日志信息，事务回滚时，撤销已经执行成功的sql
  • （Consistency）一致性： 执行事务前后，数据保持一致；——->原子性、隔离性、持久性就是为了来保证一致性
  • （Isolation）隔离性： 并发访问数据库时，一个事务不被其他事务所干扰，数据库系统提供一定的隔离机制,保证事务在不受外部并发操作影响的“独立”环境执行；——->锁机制和MVCC共同实现
  • （Durability）持久性: 一个事务被提交之后。对数据库中数据的改变是持久的，即使数据库发生故障也不会受到影响。——->持久性由redolog来保证的，mysql修改数据的时候会在redolog中记录一份日志数据，就算数据没有保存成功，只要日志保存成功了，数据仍然不会丢失。

2.4 MVCC、隔离与幻读

My33. MVCC？

口述版： MVCC 全称多版本并发控制，是 InnoDB 引擎为提升数据库并发能力设计的核心机制，核心目标是实现读写不阻塞，支撑不同事务隔离级别。 首先 InnoDB 把查询分为两种：快照读和当前读。普通不加锁的 select 是快照读，不加锁依赖 MVCC；update、delete、insert 以及 for update 加锁查询属于当前读，会加行排他锁读取最新数据。 MVCC 底层依赖三个核心组件：第一是每行记录三个隐藏列 trx_id、roll_ptr、row_id；第二是 undo 回滚日志，数据修改时会把旧版本存入 undo，通过 roll_ptr 串联成一条版本链表，既用于事务回滚，也用来生成快照；第三是 Read View 一致性视图，用来做版本可见性判断。 执行快照读时，事务会生成 Read View，拿着视图规则从最新数据开始遍历 undo 版本链，找到当前事务可见的历史版本返回。 RR 可重复读隔离级别，整个事务第一次查询只创建一次 Read View，后续复用，解决了不可重复读；而 RC 级别每条 select 都会新建视图，因此会出现不可重复读。 注意两点关键点： 第一，MVCC 只能解决快照读下的幻读，RR 级别彻底杜绝幻读靠的是临键间隙锁锁住插入间隙； MVCC 仅作用于快照读，它通过事务启动时的一致性视图，让当前事务看不到其他事务后续插入并提交的数据，只是在查询结果上规避了幻读的视觉现象，但无法阻止别的事务真正插入数据。 当执行 for update、update 等当前读时，MVCC 快照逻辑失效，此时必须依靠 InnoDB RR 隔离级别的临键间隙锁，锁住索引间隙阻止插入，才能从根本上彻底解决幻读问题。 第二，undo 日志由后台 Purge 线程清理，长事务会导致版本链过长拖慢查询性能。 整体优势就是大幅降低锁竞争、提升系统 QPS，缺点是 undo 占用存储、版本遍历有少量性能损耗。

具体介绍

InnoDB 每行记录都会自带 3 个隐藏字段：

  1. DB_TRX_ID：最后修改这条数据的事务 ID（核心）
  2. DB_ROLL_PTR：回滚指针，指向 undo log 里的历史版本链表
  3. DB_ROW_ID：隐藏主键，无主键时自动生成

Read View 核心 4 个属性：

  1. m_ids：当前活跃未提交的所有事务 ID 集合
  2. min_trx_id：m_ids 里最小事务 ID
  3. max_trx_id：下一个将要分配的事务 ID
  4. creator_trx_id：生成该视图的当前事务 ID
可见性判断规则（极简）

拿记录的 DB_TRX_ID 和 Read View 比对：

  1. trx_id < min_trx_id：已提交，可见
  2. trx_id 在 m_ids 中：未提交，不可见，顺着 roll_ptr 找 undo log 上一个版本
  3. trx_id > max_trx_id：未来事务，不可见

mvcc完整工作原理（分两段说，条理清晰）

阶段 1：数据修改，生成版本链
  1. 事务 A 执行 update 修改某行数据，先给当前行加排他锁
  2. 把修改前的原始数据拷贝到 undo log（旧版本）
  3. 更新本行 DB_TRX_ID 为事务 A 的 ID
  4. 更新 DB_ROLL_PTR 指针指向 undo log 里的旧数据
  5. 若多次修改，undo log 会形成一条版本链表，保存所有历史快照
阶段 2：快照读，通过 Read View 遍历版本链

事务 B 执行普通 select（快照读）：

  1. 生成当前事务的 Read View 一致性视图
  2. 从数据最新版本开始，拿该行 DB_TRX_ID 按可见性规则校验
  3. 如果当前版本不可见，就顺着 roll_ptr 回溯 undo log 版本链表
  4. 找到第一条符合可见性规则的历史版本，返回给查询语句

MVCC叫做多版本并发控制，实际上就是保存了数据在某个时间节点的快照。

MVCC主要解决三个问题：

第一、通过MVCC可以解决读写并发阻塞问题，从而提高数据库的并发处理能力；

第二、MVCC采用的是乐观锁的方式实现，降低了死锁的概率；

第三、解决了一致性读的问题，也就是事务启动的时候，根据某个条件去读取到的数据，直到事务结束的时候再去执行相同条件，还是读到同一份数据，不会发生变化变化。

MVCC用于读已提交（RC）和可重复读级别（RR）的控制，主要通过undo log日志版本链和read view来实现，

InnoDB中MVCC的实现依赖四个条件: 隐藏字段, 事务链表，read view, undo log

数据表额外字段

DB_TRX_ID(6字节): 在innoDB中, 会为每个事物分配一个事务ID. 而该字段表示的就是插入或更新该行的最后一个事务的事务标识符.

DB_ROLL_PTR(7字节): 这个字段称为回滚指针, 指向了回滚段的撤销日志. (undo log)

DB_ROW_ID(6字节): 这个字段包含了一个行ID. 该ID在插入新行时会单调增加. 这个字段是为了在表里没有主键ID的时候, 生成聚簇索引使用的.

rowid存的是什么？

rowid默认是主键，如果没有主键，会选择唯一键，如果没有唯一键，会生成6字节的rowid

undo日志版本链是指一行数据被多个事务依次修改过后，在每个事务修改完后，Mysql会保留修改前的数据undo回滚日志，并且用两个隐藏字段trx_id和roll_pointer把这些undo日志串联起来形成一个历史记录版本链

在可重复读隔离级别（RR），当事务开启，执行任何查询sql时会生成当前事务的一致性视图read-view，该视图在事务结束之前都不会变化(如果是读已提交隔离级别在每次执行查询sql时都会重新生成)，这个视图由执行查询时所有未提交事务id数组（数组里最小的id为min_id）和已创建的最大事务id（max_id）组成，事务里的任何sql查询结果需要从对应版本链里的最新数据开始逐条跟read-view做比对从而得到最终的快照结果。

版本链比对规则：

  1. 如果 row 的 trx_id 落在绿色部分( trx_id<min_id )，表示这个版本是已提交的事务生成的，这个数据是可见的；

  2. 如果 row 的 trx_id 落在红色部分( trx_id>max_id )，表示这个版本是由将来启动的事务生成的，是不可见的(若row 的 trx_id 就是当前自己的事务是可见的）；

  3. 如果 row 的 trx_id 落在黄色部分(min_id <=trx_id<= max_id)，那就包括两种情况

​ a. 若 row 的 trx_id 在视图数组中，表示这个版本是由还没提交的事务生成的，不可见(若 row 的 trx_id 就是当前自己的事务是可见的)；

​ b. 若 row 的 trx_id 不在视图数组中，表示这个版本是已经提交了的事务生成的，可见。

对于删除的情况可以认为是update的特殊情况，会将版本链上最新的数据复制一份，然后将trx_id修改成删除操作的trx_id，同时在该条记录的头信息（record header）里的（deleted_flag）标记位写上true，来表示当前记录已经被删除，在查询时按照上面的规则查到对应的记录如果delete_flag标记位为true，意味着记录已被删除，则不返回数据。

注意：begin/start transaction 命令并不是一个事务的起点，在执行到它们之后的第一个修改操作InnoDB表的语句，事务才真正启动，才会向mysql申请事务id，mysql内部是严格按照事务的启动顺序来分配事务id的。

MVCC机制的实现就是通过read-view机制与undo版本链比对机制，使得不同的事务会根据数据版本链对比规则读取同一条数据在版本链上的不同版本数据。

按照兼容性分类

InnoDB实现了以下两种类型的行锁。

「共享锁（S)」：又称读锁 (read lock)，是读取操作创建的锁。其他用户可以并发读取数据， 但任何事务都不能对数据进行修改（获取数据上的排他锁），直到已释放所有共享锁。当如果事务对读锁进行修改操作，很可能会造成死锁。

「排他锁（X)」：exclusive lock（也叫writer lock）又称写锁。 若某个事物对某一行加上了排他锁，只能这个事务对其进行读写，在此事务结束之前， 其他事务不能对其进行加任何锁，其他进程可以读取,不能进行写操作，需等待其释放。 「排它锁是悲观锁的一种实现」。

另外，为了允许行锁和表锁共存，实现多粒度锁机制，InnoDB还有两种内部使用的意向锁（Intention Locks），这两种意向锁都是表锁。

「意向共享锁（IS）」：事务打算给数据行加行共享锁，事务在给一个数据行加共享锁前必须先取得该表的IS锁。

「意向排他锁（IX）」：事务打算给数据行加行排他锁，事务在给一个数据行加排他锁前必须先取得该表的IX锁。

意向锁是有数据引擎自己维护的，用户无法手动操作意向锁，在为数据行加共享 / 排他锁之前，InooDB 会先获取该数据行所在在数据表的对应意向锁。

意向锁是InnoDB自动加的，不需用户干预。对于UPDATE、DELETE和INSERT写操作，InnoDB会自动给涉及数据集加排他锁（X)； 对于普通SELECT语句，InnoDB不会加任何锁；事务可以通过以下语句显示给记录集加共享锁或排他锁。

共享锁（S）：SELECT * FROM table_name WHERE … LOCK IN SHARE MODE。

排他锁（X)：SELECT * FROM table_name WHERE … FOR UPDATE。

用SELECT … IN SHARE MODE获得共享锁，主要用在需要数据依存关系时来确认某行记录是否存在， 并确保没有人对这个记录进行UPDATE或者DELETE操作。但是如果当前事务也需要对该记录进行更新操作， 则很有可能造成死锁，对于锁定行记录后需要进行更新操作的应用，应该使用SELECT… FOR UPDATE方式获得排他锁。

InnoDB在事务执行过程中，使用两阶段锁协议：

随时都可以执行锁定，InnoDB会根据隔离级别在需要的时候自动加锁；

锁只有在执行commit或者rollback的时候才会释放，并且所有的锁都是在同一时刻被释放。

按算法分类

「Record Lock」： 单个行记录上的锁

锁总会锁住索引记录，锁住的是key。

如果InnoDB存储引擎表在建立的时候没有设置任何一个索引，那么这时InnoDB会使用隐式的主键进行锁定。

如果要锁的没有索引，则会进行全表记录加锁。

「Gap Lock」 ：间隙锁，锁定一个范围，但不包含记录本身

锁定索引记录间隙，确保索引记录的间隙不变

间隙锁时针对事务隔离级别为可重复读或以上级别而配的

「Next-Key Lock」：临键锁，Gap Lock + Record Lock，锁定一个范围，并且包含记录本身

当查询的索引含有唯一属性时，InnoDB存储引擎会对Next-Key Lock 进行优化，将其降级为 Record Lock，即仅锁住索引本身，而不是范围。

  3. 从索引name找到下一个满足 name = ‘zhuge’ 条件的主键 id

  4. 重复步骤 2、3 直到不满足 name = ‘zhuge’

  5. 对 sort_buffer 中的数据按照字段 position 进行排序

  6. 返回结果给客户端

我们再看下双路排序的详细过程：

  1. 从索引 name 找到第一个满足 name = ‘zhuge’ 的主键id

  2. 根据主键 id 取出整行，把排序字段 position 和主键 id 这两个字段放到 sort buffer 中

  3. 从索引 name 取下一个满足 name = ‘zhuge’ 记录的主键 id

  4. 重复 3、4 直到不满足 name = ‘zhuge’

  5. 对 sort_buffer 中的字段 position 和主键 id 按照字段 position 进行排序

  6. 遍历排序好的 id 和字段 position，按照 id 的值回到原表中取出 所有字段的值返回给客户端

其实对比两个排序模式，单路排序会把所有需要查询的字段都放到 sort buffer 中，而双路排序只会把主键和需要排序的字段放到 sort buffer 中进行排序，然后再通过主键回到原表查询需要的字段。

面试追问：布隆误判？（答： 不存在可能判存在，需穿透 DB；不存在不会误判存在。）

常见坑：缓存挂掉流量打穿 DB——无降级预案。

My89. 逻辑备份与物理备份？

口述版： mysqldump 逻辑、慢可跨版本；xtrabackup 物理热备、恢复快；binlog PITR 增量。

具体介绍

方式 工具 特点
逻辑 mysqldump 跨版本、慢、可部分表
物理热备 xtrabackup / clone 快、大库友好
增量 binlog PITR 到时间点

恢复演练：定期 RTO/RPO 演练；验证 binlog 链完整。

  • 冷备 + binlog：误删表 DROP 可 flashback（row binlog）或延迟从库。

面试追问：mysqldump 锁表？（答： 看 --single-transaction InnoDB 一致性快照。）

常见坑：从不恢复演练——真故障发现 binlog 断档。

2.11 场景与开放题

My90. 亿级订单按用户查最近列表？

口述版： 索引 (user_id, created_time desc) 或 (user_id, id)；分页 seek；历史归档冷表。

具体介绍

索引：(user_id, created_time DESC, id) 覆盖列表+排序。

分页：WHERE user_id=? AND (created_time, id) < (?, ?) ORDER BY created_time DESC LIMIT 20——禁止大 offset。

数据生命周期

  • 热表 3～6 月；历史 归档表 / 冷库；用户查「全部订单」走归档+ES。

面试追问：按状态筛选？（答： (user_id, status, created_time) 联合索引，状态选择性低时放后。）

常见坑：全局 ORDER BY created_time 无 user_id——全库排序。

My91. 高并发库存扣减防超卖？

口述版： 单条 update set stock=stock-1 where id=? and stock>0；乐观 version；秒杀 Redis 预减 + DB 异步；禁止先查后改。

具体介绍

DB 原子扣减

  • affected_rows=1 才成功；=0 表示售罄或冲突。

秒杀架构：Redis DECR 预扣 + 异步 MQ 落库；DB 最终一致对账。

错误 后果
SELECT then UPDATE 超卖
无 WHERE stock 条件 负数库存

面试追问：Redis 扣了 DB 失败？（答： 补偿回滚 Redis、对账、人工。）

常见坑：事务隔离级别误用——仍要靠原子 UPDATE。

My92. 唯一约束与插入幂等？

口述版： INSERT IGNORE、ON DUPLICATE KEY UPDATE、唯一键 (biz_id)；冲突返回已有行 id。

具体介绍

业务幂等键：(biz_type, biz_id) UNIQUE。

语句 行为
INSERT IGNORE 冲突静默跳过
REPLACE 冲突删旧插新（慎用）
ON DUPLICATE KEY UPDATE 冲突更新或 noop
  • 与 消息消费 同键；消费前插入幂等表。

面试追问：和分布式锁区别？（答： 唯一键靠 DB 约束；锁靠协调；可结合。）

常见坑：REPLACE 导致自增 id 变化、触发器误伤。

My93. 线上 CPU 高怀疑 MySQL 怎么查？

口述版： top → show processlist / PFS；慢 SQL；锁等待；buffer pool 命中率；是否全表扫、排序临时表；读从库延迟。

具体介绍

排查顺序

  1. OS：top 看 mysqld CPU vs iowait。
  2. SHOW FULL PROCESSLIST / sys.session：大量 Sending data、Sorting、Locked？
  3. PFS：events_statements_summary_by_digest ORDER BY SUM_TIMER_WAIT DESC。
  4. 锁：data_lock_waits、InnoDB status。
  5. Buffer Pool：命中率低 → 冷数据或 pool 太小。
  6. 排除 从库、备份、DDL 同机干扰。

面试追问：CPU 高 IO 低？（答： 排序、哈希、解析、坏计划反复执行。）

常见坑：未开 slow/PFS 凭猜——缺证据。

延伸阅读： 行页索引底层结构、SQL 执行流程、MVCC、Explain 与优化器、两阶段提交。
