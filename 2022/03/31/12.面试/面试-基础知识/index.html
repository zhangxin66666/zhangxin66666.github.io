格式说明：每题先 口述版（面试现场 30～60 秒），下方 具体介绍 便于复习展开。

1.1 HashMap 结构与原理

1. HashMap 底层结构在 JDK 1.7 和 1.8 分别是什么？演进动机是什么？

口述版： 1.7 是数组加链表，冲突用头插；1.8 在链表过长时引入红黑树，冲突改尾插。演进主要是降低哈希冲突严重时的查询复杂度，从 O(n) 拉到 O(log n)，同时 1.8 的扩容迁移也更省事。

具体介绍

  • 1.7：Node[] table，桶内单向链表，插入采用头插法。
  • 1.8：数组 + 链表 + 红黑树（TreeNode），链表插入为尾插。
  • 动机：极端冲突下链表过长；树化后查询更稳定；尾插与并发讨论相关（1.7 头插在扩容 transfer 时易出问题）。

源码/参数

  • JDK 8 核心类：java.util.HashMap，桶节点 Node<K,V>，树节点 TreeNode 继承 LinkedHashMap.Entry 链能力。
  • 默认 DEFAULT_INITIAL_CAPACITY = 16，MAXIMUM_CAPACITY = 1 << 30。
  • 1.7 Entry 数组 + 单链表；扩容 rehash 对全表重新定位。

面试追问

  • 1.7 头插为何在并发扩容时危险？（transfer 时多线程可能交叉改 next）
  • 红黑树何时退化为链表？（删除后 binCount <= 6）

常见坑

  • 误以为 1.8 线程安全；TreeNode 只在单桶内平衡，全局仍非同步。
  • 自定义 key 未稳定 hashCode 会导致「丢在树上/链上找不到」。

2. 为什么 HashMap 容量必须是 2 的 n 次方？

口述版： 两个原因：一是算下标用 (n-1)&hash，只有 n 是 2 幂才等价于取模且更快；二是扩容时看 hash 多出来的那一位就能决定留在原桶还是原下标加 oldCap，迁移不用重新算一遍模。

具体介绍

  • 下标：index = (n - 1) & hash，当 n = 2^k 时等价于 hash % n。
  • 初始化：tableSizeFor(cap) 将期望容量向上取整到 2 幂。
  • 扩容：hash & oldCap 为 0 留原索引，为 1 则 index + oldCap（见第 11 题）。

源码/参数

  • tableSizeFor(int cap)：n - 1 | n >>> 1 | n >>> 2 | ... 向上取 2 幂。
  • 构造传入 initialCapacity 时先规整，再算 threshold = capacity * loadFactor。

面试追问

  • 若强行用非 2 幂容量会怎样？（JDK 会规整；老代码手写数组长度则 (n-1)&hash 失效）
  • 为什么不用 hash % n？（取模慢；2 幂位运算等价且利于扩容位 trick）

常见坑

  • 认为 HashMap(100) 容量就是 100（实际是 ≥100 的最小 2 幂，如 128）。

3. 负载因子 0.75 的含义与权衡？

口述版： threshold 等于容量乘 0.75，元素个数超过就扩容。0.75 是经典折中：太大冲突多变慢，太小扩容太勤浪费内存，也和泊松分布下冲突长度统计有关。

具体介绍

  • threshold = capacity × loadFactor，size > threshold 触发 resize。
  • 默认 16 容量时，第 13 个元素（严格说是超过 12）会扩容。
  • 0.75 在 JDK 文档与实现中作为时间与空间的通用平衡点；与树化阈值 8 的泊松解释同一套统计假设。

源码/参数

  • 字段 loadFactor，构造可传；threshold = (cap == 0 ? DEFAULT : cap) * loadFactor。
  • 树化阈值 TREEIFY_THRESHOLD = 8 文档引用泊松：λ=0.5 时单桶长度≥8 概率约 0.00000006。

面试追问

  • 能否把 loadFactor 设为 1.0？（可以，冲突多、链表/树化概率升，空间换时间）
  • size > threshold 还是 >=？（严格大于才 resize）

常见坑

  • 只记「0.75 经验值」说不出与 threshold、树化统计的关联。

4. hash 扰动函数做什么？为什么要让高位参与运算？

口述版： 1.8 里把 hashCode 高 16 位和低 16 位异或，因为数组不大时参与下标的只有低位，高位不参与就容易碰撞，扰动是把高位信息混进来。

具体介绍

  • HashMap：hash = h ^ (h >>> 16)，再 (n-1) & hash。
  • ConcurrentHashMap：spread() 同样思路。
  • 目的：降低仅低位不同、高位不同的 key 落到同一桶的概率。

源码/参数

  • static final int hash(Object key)：h = key.hashCode(); return h ^ (h >>> 16)。
  • 1.7 曾 4 次扰动（高/中/低混合），1.8 简化为一次异或，性能更好且实践足够。

面试追问

  • String 的 hashCode 如何算？（31 多项式，缓存 hash 字段）
  • 为何 spread 后还要 HASH_BITS & hash？（CHM 用高位存特殊节点类型）

常见坑

  • 可变 key 修改参与 hash 的字段后，Map 中「消失」——定位桶错误。

5. 链表树化阈值为什么是 8？退化为什么是 6？

口述版： 8 来自泊松分布，正常 hash 下单桶到 8 的概率极低，到了就值得树化；退化用 6 而不是 8，是为了留缓冲，避免在 7、8 附近反复树化拆树抖动。

具体介绍

  • 树化：binCount >= 8 且 table.length >= 64 才 treeifyBin。
  • 退化：UNTREEIFY_THRESHOLD = 6，拆树更保守。
  • 不对称：迟滞区间 6～8，减少结构频繁切换的开销。

源码/参数

  • UNTREEIFY_THRESHOLD = 6，MIN_TREEIFY_CAPACITY = 64。
  • 泊松解释：理想 hash 下链表长度 k 的概率约 e^-0.5 * 0.5^k / k!。

面试追问

  • 为何不是 10 才树化？（更长链表才树化，查询更慢；8 是统计与实现折中）
  • 退化 7 个节点时结构？（仍为树，直到 ≤6）

常见坑

  • 认为「链长 8 必树化」——还需 table.length >= 64。

6. 树化前为什么要求 table.length >= 64？

口述版： 表太小时就算链长也先扩容，因为扩容能打散冲突，比在小表上挂红黑树更划算。

具体介绍

  • 源码逻辑：链表 ≥ 8 但 n < 64 时优先 resize()，而非立刻树化。
  • 小表冲突往往因容量不足，扩一倍比树化更能治本。
  • MIN_TREEIFY_CAPACITY = 64：默认从 16 起可能经历 16→32→64 多次扩容，多数冲突在扩表阶段已被打散，不必过早树化。
  • TreeNode 成本：红黑树节点比 Node 大得多（颜色、父/子/左右指针、双向链表链入 LinkedHashMap 能力），小表上树化「局部优化、全局更费内存」。
  • 面试追问：为何不是「链长 8 立刻树化」？——表长不足时扩容的摊还成本往往低于维护多棵小树；树化还需 Comparable/Comparator，小表上直接扩更通用。
  • 常见坑：压测用 new HashMap(8) + 恶意 hash 强测树化，与生产默认 16 + 正常 hash 路径不一致；面试应先说「优先 resize，再谈 treeifyBin」。

源码/参数

  • treeifyBin 入口判断：if (tab.length < MIN_TREEIFY_CAPACITY) resize() 优先于 TreeBin。
  • 小表 + 高冲突 → 扩容分散比局部树化更省内存（树节点开销大）。

面试追问

  • 64 与默认初始 16 的关系？（可能经历 16→32→64 多次扩容才树化）
  • 树化对 compareTo/comparator 的要求？（TreeNode 需可比较，否则 ClassCastException）

常见坑

  • 压测时用极小 initialCapacity + 恶意 hash 测树化，与生产默认路径不一致。

7. HashMap 和 Hashtable 的区别？

口述版： HashMap 非线程安全，允许一个 null key；Hashtable 方法全表 synchronized，不允许 null。线上并发 Map 用 ConcurrentHashMap，不用 Hashtable。

具体介绍

对比项 HashMap Hashtable
线程安全 否 是（方法级 synchronized）
null 允许 null key/value 不允许
扩容 2 幂、高低位迁移 2n+1 等旧策略
推荐 单线程 / 外部锁 已过时

面试追问

  • Collections.synchronizedMap(new HashMap()) 与 Hashtable 差异？（前者锁对象可自选，后者锁 this）
  • Vector 与 ArrayList 对比是否同一类题？（是，都是早期同步 vs 非同步）

常见坑

  • 面试说「Hashtable 已删除」——类仍在 JDK，只是不推荐。
  • HashMap 允许一个 null key 多个 null value；Hashtable 全禁止 null。

8. HashSet 底层用什么实现？如何保证元素不重复？

口述版： HashSet 底层就是 HashMap，元素放在 key 上，value 是一个固定占位对象；不重复靠 key 的 hash 和 equals 契约。

具体介绍

  • 内部 HashMap<E,Object>，PRESENT 作为 value。
  • 依赖 hashCode + equals；自定义类型必须正确重写两者。

源码/参数

  • private static final Object PRESENT = new Object();，add(e) → map.put(e, PRESENT)。
  • LinkedHashSet 底层 LinkedHashMap（插入序/访问序）；TreeSet 底层 TreeMap（红黑树）。

面试追问

  • Set 去重依赖 equals 还是 ==？（equals + hashCode 契约）
  • add 返回 false 表示什么？（元素已存在）

常见坑

  • 只重写 equals 不重写 hashCode，HashSet 可能出现「逻辑相等但 add 两次都成功」。

1.2 HashMap 核心方法流程

9. 描述 HashMap put 全链路

口述版： 先算 hash，表空就 resize；用下标找桶，空桶直接放；否则比 key，相同就覆盖；是树就走树插入；否则链表尾插，链长到了 8 且表够 64 就树化，表不够 64 先扩容；最后 size 加一，超 threshold 再扩容。

具体介绍

1. put(key, value) → putVal — 写的主干

源码/参数

  • 核心 final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict)。
  • 树化分支：if (binCount >= TREEIFY_THRESHOLD - 1) treeifyBin(tab, i)（注意 -1 与尾插计数配合）。
  • modCount++ 供 fail-fast；afterNodeInsertion 钩子（LinkedHashMap 用）。

面试追问

  • putIfAbsent / putAll 最终是否都走 putVal？（是）
  • 覆盖 value 是否增加 size？（否，仅替换）

常见坑

  • 并发 put 丢数据：两线程同时认为桶空，后写覆盖先写无合并。

10. 描述 HashMap get 流程

口述版： 算 hash 定位桶，首节点命中就返回；否则沿链表比 hash 和 equals，或在红黑树里 find；找不到返回 null。

具体介绍

2. get(key) → getNode — 读的主干

源码/参数

  • getNode 与 get 相同逻辑，找不到返回 null（注意 null value 与「无 key」在 HashMap 中可区分：含 null key）。
  • 树查找：TreeNode.getTreeNode(hash, key)，比较顺序 hash → compareTo/comparator → tieBreak。

面试追问

  • resize 期间 get 能否读到？（可能读到旧表或 ForwardingNode 场景在 CHM；HashMap 可能不完整）
  • 时间复杂度？（平均 O(1)，冲突链 O(n)，树 O(log n)）

常见坑

  • 用 get 判断 key 是否存在时，应用 containsKey，避免 value 为 null 误判。

11. 描述 HashMap resize 与高低位 rehash

口述版： 容量翻倍，新 threshold 重算；每个旧桶节点看 hash 与 oldCap 按位与，为 0 留原下标，为 1 加 oldCap；1.8 把同一桶拆成 lo 和 hi 两条链一次性挂到新表。

具体介绍

3. resize() — 初始化 / 扩表与高低位迁移

  • 1.7 头插 transfer 与多线程成环相关；1.8 尾插 + lo/hi 链拆分避免环，但仍非线程安全。

源码/参数

  • resize()：新 cap 为 old 的 2 倍或首次初始化；newThr = newCap * loadFactor。
  • 1.8 迁移：Node lo = null, hi = null，按 e.hash & oldCap 拆链一次挂接。

面试追问

  • 1.7 transfer 索引 (e.hash & oldCap) == 0 ? index : index + oldCap 与 1.8 等价性？（答： 是；1.8 resize 用同一高位 bit 规则把节点拆到原索引或 i+oldCap，与 1.7 单线程 transfer 语义一致，只是 1.8 尾插 + 树化实现不同。）
  • 扩容是否线程安全？（否）

常见坑

  • 认为扩容会缩容——HashMap 无自动缩容，只增不减。

12. HashMap 何时分配数组？懒初始化？

口述版： 构造 HashMap 不会立刻建表，第一次 put 时发现 table 为空才 resize 做初始化，这是懒加载，省内存。

具体介绍

4. 懒初始化 — 何时分配 table

源码/参数

  • 带参构造 HashMap(int initialCapacity, float loadFactor) 仅保存参数，不分配 table。
  • 例外：new HashMap<>(otherMap) 会 putMapEntries 立即建表复制。

面试追问

  • new HashMap<>(map) 是否会立即复制？（会分配并 putMapEntries，非懒）
  • table 为 null 时 size 仍为 0 吗？（是）

常见坑

  • 大量 new HashMap() 但不 put 不占数组内存——这是懒加载优点；误用于「预分配极大表」应传 capacity。

13. remove / replace 是否触发扩容或树化？

口述版： remove 只会减 size，可能触发拆树（树节点过少变链表），一般不会因删而扩容；replace 只改 value，不动结构。

具体介绍

5. remove / replace — 删改结构，不缩表

源码/参数

  • removeNode：删树节点后 if (root == null || root.right == null ...) untreeify(tab, index)。
  • replace(K key, V old, V new) 仅 value 匹配时替换，不改结构。

面试追问

  • clear 是否触发缩容？（否，只置 null 数组元素，table 长度不变）
  • 删除触发 modCount 吗？（是，迭代器 fail-fast）

常见坑

  • 删元素后期望内存下降——数组槽位仍在，只有 GC 回收 Node 对象。

1.3 HashMap 并发与选型

14. JDK 1.7 多线程 HashMap 为何可能死循环？

口述版： 1.7 扩容 transfer 用头插法重排链表，多线程同时扩容可能把 next 指针搞成环，get 遍历链表就死循环了。

具体介绍

  • 场景：两线程同时 resize，对同一桶链表并发头插。
  • 结果：某节点 next 指向前驱，形成环。
  • 1.8 改为尾插 + 新表 lo/hi，避免典型成环，但不代表线程安全。

面试追问

  • 如何复现 1.7 死循环？（多线程 put 触发 resize，需特定 JDK 版本与负载）
  • 1.8 还有哪些并发问题？（数据覆盖、size 不准）

常见坑

  • 答「1.8 完全解决 HashMap 并发问题」——错误，仅避免典型链表环。

15. JDK 1.8 为何仍线程不安全？

口述版： 1.8 解决了成环，但没有同步，多线程 put 仍可能覆盖丢数据，size 也不准，所以不能当并发 Map 用。

具体介绍

  • 竞态：put、扩容、size++ 非原子组合。
  • 表现：两个 key 映射到同一桶的覆盖顺序不确定；扩容期间读可能看不到完整数据。
  • 结论：需要 ConcurrentHashMap 或 Collections.synchronizedMap（后者性能差）。

源码/参数

  • size 字段非 volatile，多线程读写无 happens-before 保证。
  • 扩容 + put 竞态：可能丢失插入或读到迁移中间状态（非 CHM 的 Forwarding 语义）。

面试追问

  • 用 ConcurrentHashMap 还是 Collections.synchronizedMap？（高并发读多写多选 CHM）
  • Hashtable 为何慢？（方法级锁整表）

常见坑

  • 在 @Transactional 单线程误以为 Map 成员变量安全——跨请求/异步仍共享则不安全。

16. 高并发场景如何选型 Map？

口述版： 读多写多默认 ConcurrentHashMap；要全局一把锁才 synchronizedMap；单线程或线程内局部用 HashMap；Hashtable 不用。

具体介绍

  • CHM：分段/桶级锁，吞吐高。
  • synchronizedMap：每个方法 synchronized，简单但锁整个 map。
  • HashMap + 外部锁：仅当锁粒度自定义且明确时使用。

面试追问

  • ConcurrentSkipListMap 何时用？（需要并发 + 有序 key）
  • Guava Cache 与 CHM？（Cache 有过期/加载语义，不是通用 Map）

常见坑

  • synchronizedMap 迭代时需手动 synchronized(map) 包住整个迭代，否则仍 CME。
  • 分段锁 1.7 CHM 与 1.8 桶锁选型表述过时——应强调 JDK8+ 桶锁 + CAS。

1.4 ConcurrentHashMap 结构与锁

17. CHM 1.7 分段锁如何工作？

口述版： 1.7 是 Segment 数组，每个 Segment 继承 ReentrantLock，里面一个小 HashMap；定位时先找 Segment 再找桶，锁的是段，不是整个表。

具体介绍

  • Segment[]，默认并发度 16（可配置）。
  • hash >>> segmentShift & segmentMask 选段。
  • 段内与 HashMap 1.7 类似（数组+链表）。

1.7 put(key) — 段锁内写入

源码/参数

  • 1.7 Segment extends ReentrantLock，Segment[] segments，默认 concurrencyLevel = 16。
  • 两次 hash：定位 Segment，再定位桶；详见 ConcurrentHashMap 源码解读。

面试追问

  • concurrencyLevel 设很大有何影响？（Segment 数多，内存开销，1.7 专属）
  • 1.7 CHM get 要加锁吗？（不加，volatile 读 + happens-before）

常见坑

  • 把 1.7 分段锁答案套在 1.8 上——1.8 已取消 Segment。

18. CHM 1.8 如何保证并发写？

口述版： 空桶用 CAS 抢第一个节点；桶里已有数据就 synchronized 锁头节点；正在扩容的桶是 ForwardingNode，别的线程来 put 会帮忙迁移。

具体介绍

  • 与 1.7 比：锁粒度从 Segment 细化到 单个桶。

1.8 写路径三分支（与 putVal 一致）

源码/参数

  • tabAt / casTabAt / setTabAt：Unsafe 保证数组元素的 volatile 语义。
  • 锁对象：桶头节点 Node，不是 key 也不是整个 table。

面试追问

  • 为何空桶 CAS、非空 synchronized？（减少锁竞争，首节点作锁锚）
  • 与 StripedLock 思想对比？（类似按桶分段）

常见坑

  • 认为 CHM 完全无锁——写路径有 synchronized 或 CAS 争用。

19. 为什么 1.8 桶内用 synchronized 而不是 ReentrantLock？

口述版： 争用多半在同一桶内，synchronized 由 JVM 优化且不用每个桶 new 一把 ReentrantLock，内存和实现都更轻；配合 CAS 够用了。

具体介绍

  • 官方设计：桶争用通常不激烈；synchronized 偏向/轻量锁优化成熟。
  • 避免 Segment 或 per-bucket ReentrantLock 的大量对象开销。

面试追问

  • synchronized 锁升级（偏向/轻量/重量）对 CHM 桶锁的影响？
  • 1.7 用 ReentrantLock 能否 fair？（Segment 可选，1.8 桶锁非 ReentrantLock）

常见坑

  • 「synchronized 比 ReentrantLock 慢」在短临界区 + JVM 优化下不一定成立。

20. CHM 是否允许 null key/value？

口述版： 不允许，和 HashMap 不同。原因是并发下 null 有歧义：是「没值」还是「就是 null」，多线程语义说不清。

具体介绍

  • putVal 对 key/value 做 null 检查抛 NPE。
  • Hashtable 同样禁止 null，但锁粒度粗。
  • 设计动机（Doug Lea）：并发下 get(key) 返回 null 无法区分「键不存在」与「值为 null」；若允许 null value，多线程下语义与缓存穿透判断都会混乱。
  • 与 HashMap 对比：单线程 Map 可用 containsKey 消歧；CHM 强调无锁读，禁止 null 让 get/putIfAbsent 契约更简单。
  • API 影响：merge/compute 等不能把 null 当作有效映射值；集合视图迭代也不会出现「值为 null 的 entry」。
Map 实现 null key null value 典型用途
HashMap 允许 1 个 允许 单线程 / 外部同步
Hashtable 禁止 禁止 遗留，不推荐
ConcurrentHashMap 禁止 禁止 高并发共享

面试追问

  • ConcurrentHashMap.get(key) 若 key 不存在返回 null，如何与「值为 null」区分？（CHM 不允许 null value，无歧义）
  • Hashtable 同样禁止 null 的原因是否相同？（类似并发语义）

常见坑

  • 把 HashMap 的 containsKey 模式套 CHM——null 检查在 put 即失败。

21. CHM 迭代器是 fail-fast 还是弱一致？

口述版： 弱一致，迭代过程中可以反映部分写入，一般不抛 ConcurrentModificationException，也不保证遍历到每一刻的最新全量。

具体介绍

  • Iterator 无 expectedModCount 强校验。
  • 适合并发读；若需要快照考虑复制或 size 等方法的语义说明。
  • 弱一致含义：遍历开始后的写入可能被看到，也可能看不到；不保证「某一时刻的全局快照」，也不保证 ConcurrentModificationException。
  • 与 HashMap fail-fast 对比：HashMap 迭代器校验 modCount，结构被改就抛 CME；CHM 桶级锁 + CAS，全局 modCount 不足以定义「非法并发修改」。
  • size / mappingCount：并发下是估计值，与迭代器看到的元素个数可能不一致——面试别当成精确计数。
  • 面试追问：keySet().iterator().remove() 在 CHM 是否安全？——支持弱一致 remove，但仍可能与其他线程写入交错；需要强一致快照应 new HashMap<>(chm) 或加业务锁。
  • 常见坑：用增强 for 遍历 CHM 同时在另一线程 bulk put，以为「要么全看到要么全看不到」——实际介于两者之间。

面试追问

  • forEach 与 Iterator 在 CHM 的语义？（弱一致，反映遍历起点快照后的部分更新）
  • 需要强一致快照怎么办？（size 也不精确；复制或使用锁/GUAVA snapshot）

常见坑

  • 在迭代中 remove 普通 HashMap 应用 Iterator.remove；CHM 支持部分并发 remove 但仍弱一致。

22. 描述 CHM putVal 全链路

具体介绍

1. put(key, value) → putVal — 写的主干

23. 描述 CHM get 流程

口述版： 读 table，算下标；如果头节点是 ForwardingNode，按新表地址继续查；否则和 HashMap 一样比链表或树，全程不加锁。

具体介绍

1.6 红黑树（桶内）

29. HashMap 桶内为什么选红黑树？

口述版： 冲突链太长查询慢，红黑树是平衡性和插入代价的折中，比 AVL 松一点，比链表快，适合读多、桶内插入相对少的 HashMap 场景。

具体介绍

  • 链表 O(n) → 树 O(log n)。
  • 红黑树：最长路径不超过最短路径 2 倍，插入旋转次数相对 AVL 少。
  • 仅在单桶冲突极端时启用，全局仍是数组寻址 O(1)。

面试追问

  • 为何不用 AVL？（插入删除旋转更频繁）
  • 为何不用跳表？（JDK HashMap 选型红黑树，TreeMap 也是 RB）

常见坑

  • 恶意 hash 全落一桶仍 O(log n) 但常数大——应用层防 hash 攻击或换结构。

1.7 List / Set / Map 与线程安全集合

30. Set、List、Map 在结构、顺序、重复性上的区别？

口述版： List 有序可重复单列；Set 不重复，HashSet 无序、LinkedHashSet 插入序、TreeSet 排序；Map 是键值对，key 不重复。选哪个看要不要顺序、要不要键。

具体介绍

  • List：有索引/顺序，元素可重复。
  • Set：元素唯一，实现决定顺序（hash 序、链序、比较器序）。
  • Map：key 唯一，value 可重复；本身不是 Collection 子接口。

面试追问

  • Map 的 keySet/values/entrySet 视图是否独立集合？（视图，改 map 反映到视图）
  • EnumSet/EnumMap 特殊性？（位向量/数组，高效）

常见坑

  • TreeSet 元素需 Comparable 或构造传 Comparator，否则运行时错误。

31. ArrayList 底层与扩容策略？

口述版： 动态数组 Object[]，默认空或 10，满了就 grow，新容量大约是旧的 1.5 倍，把元素拷贝过去，均摊插入还是 O(1)。

具体介绍

  • 字段：elementData、size。
  • 扩容：newCapacity = old + (old >> 1)，不够则 Arrays.copyOf。
  • 中间插入/删除要 System.arraycopy，O(n)。

源码/参数

  • DEFAULT_CAPACITY = 10（首次 grow 从空数组到 10）；MAX_ARRAY_SIZE = Integer.MAX_VALUE - 8。
  • trimToSize 可缩数组到 size（不常用）。

面试追问

  • subList 结构？（视图，父 list 改可能 CME）
  • 为何 1.5 倍不是 2 倍？（空间与时间折中）

常见坑

  • Arrays.asList 返回固定大小 list，add/remove 抛异常——与 ArrayList 不同。

32. LinkedList 底层与和 ArrayList 的对比？

口述版： 双向链表，随机访问慢，头尾插删快；ArrayList 查快、尾插快、中间慢。业务里列表若大量 get(i) 用 ArrayList。

具体介绍

  • 节点：Node{ prev, item, next }。
  • 实现了 Deque，可作队列/栈。
  • 内存：链表每个元素额外两个指针，缓存局部性不如数组。
  • 复杂度对照：get(i)/set(i) 为 O(n)（需从头或尾走一半）；addFirst/addLast/removeFirst/removeLast 为 O(1)；ArrayList 随机读 O(1)、尾插均摊 O(1)、中间插删 O(n)。
  • 选型：元素量大且以索引遍历为主 → ArrayList；频繁头尾进出、或需要 Deque API → ArrayDeque（一般优于 LinkedList，连续内存更 cache-friendly）。
  • 面试追问：JDK 里哪些结构仍用链表？——LinkedHashMap 维护顺序链、HashMap 桶内链/树；业务 List 很少选 LinkedList 除非明确双端队列且历史代码。
  • 常见坑：for (int i=0;i<list.size();i++) list.get(i) 在 LinkedList 上接近 O(n²)；应用迭代器或增强 for。

面试追问

  • LinkedList 作队列：offer/poll 复杂度？（O(1) 头尾）
  • ArrayDeque 与 LinkedList 作栈/队列？（一般更推荐 ArrayDeque，无 Node 开销）

常见坑

  • list.get(i) 在 LinkedList 上 O(n)——循环里用索引访问性能灾难。

33. fail-fast 与 modCount？

口述版： 迭代器记着一开始的 modCount，遍历过程中集合被别的操作改了结构，modCount 对不上就抛 ConcurrentModificationException，这就是 fail-fast。

具体介绍

  • ArrayList.Itr：expectedModCount != modCount → CME。
  • 用迭代器自己的 remove 会同步 modCount；直接 list.remove 不会。
  • HashMap 迭代同样依赖 modCount。

源码/参数

  • modCount 结构变更 +1；Itr.checkForComodification() 每步校验。
  • 增强 for 底层仍是 Iterator。

面试追问

  • 多线程并发改 list 一定 CME 吗？（不保证立刻抛，但行为未定义）
  • ConcurrentModificationException 是 Error 吗？（RuntimeException）

常见坑

  • 子 list 迭代时改父 list 也会 CME。

34. fail-safe 典型实现与场景？

口述版： 像 CopyOnWriteArrayList 迭代的是复制出来的数组快照，写时复制，迭代不抛 CME，适合读极多、写很少的配置列表。

具体介绍

  • COW：add 时复制新数组，迭代器持有旧数组引用。
  • 代价：写放大、内存；读无锁。
  • ConcurrentHashMap 迭代属弱一致，非严格 fail-safe 但目标类似。

面试追问

  • ConcurrentHashMap.keySet 迭代属哪类？（弱一致，非 COW）
  • Vector 迭代器是 fail-fast 吗？（是，但方法 synchronized）

常见坑

  • COW 迭代器读到旧数据——读多写少场景可接受；写后立刻读最新需额外同步。

35. RandomAccess 标记接口的含义？

口述版： 没方法，只是告诉调用方：我随机访问快，比如 ArrayList 实现了它，Collections 二分查找会走索引而不是迭代器。

具体介绍

  • ArrayList 实现；LinkedList 不实现。
  • Collections.binarySearch、shuffle 等会 instanceof RandomAccess 选算法。

面试追问

  • 自定义 List 是否应实现 RandomAccess？（随机访问 O(1) 才实现）
  • LinkedList 实现 Deque 但未 RandomAccess——算法如何选择？（答： 需要 随机下标访问 用 ArrayList；只 头尾增删/队列 用 LinkedList/ArrayDeque；大列表遍历优先 ArrayList（缓存友好）。）

常见坑

  • 仅实现 List 未 RandomAccess，Collections 算法走迭代路径，大列表 sort 变慢。

36. Collections.unmodifiableList 与不可变列表的区别？

口述版： unmodifiableList 是只读包装，底层 list 还能被别人改，视图跟着变；List.of 或 Guava immutable 是真不可变，更安全。

具体介绍

  • 包装器：增删改抛 UnsupportedOperationException。
  • 非拷贝：共享 backing list。
  • API 设计：对外暴露用不可变或拷贝，避免调用方误改内部状态。

面试追问

  • List.of() / List.copyOf() JDK 9+ 与 unmodifiable 区别？（真不可变）
  • Guava ImmutableList 拷贝时机？（构建时拷贝 defensive copy）

常见坑

  • 对外返回内部 unmodifiableList(inner)，调用方仍可通过其他引用改 inner。

37. CopyOnWriteArrayList 原理与场景？

口述版： 写时复制整个数组，读无锁读旧或新数组；适合监听器、白名单这种读多写极少，写可以慢一点。

具体介绍

  • 写：lock + 复制 + 替换 array 引用。
  • 读：get 无锁，可能读到略旧数据。
  • 不适合：写频繁、大列表。
  • 可见性：volatile Object[] array 保证替换后新读能看到新数组；旧迭代器仍持有复制时的数组引用，即 快照迭代。
  • 写放大：每次 mutating 操作复制整表，时间/空间 O(n)；n 很大或写 QPS 高时 CPU 与 GC 压力明显。
  • 典型场景：监听器列表、黑白名单、路由表——读远多于写，短暂读到旧版本可接受。
  • 面试追问：与 Collections.synchronizedList 比？——COW 读无锁、写贵；同步 List 读写都锁，写少读多 COW 更优。
  • 常见坑：在 COW 上 iterator.remove() 不支持；大列表上频繁 add 导致连续 full array copy。

源码/参数

  • 内部 transient volatile Object[] array；写操作 ReentrantLock lock。

面试追问

  • iterator 是否抛 CME？（不抛）
  • 适用监听器列表的原因？（读远多于写，短暂不一致可接受）

常见坑

  • 大数组频繁 add——每次复制 O(n) 内存，写放大严重。

1.8 String、equals、包装类

38. String 为什么不可变？

口述版： 底层 char/byte 数组 final，没有对外修改接口；好处是线程安全、能安全做常量池缓存、当 HashMap 的 key 时 hash 不会变。

具体介绍

  • final class，内部数组不可变（JDK 9+ compact strings）。
  • 常量池："abc" 复用，节省内存。
  • 安全：传参、缓存 key 不会被悄悄改掉。

源码/参数

  • JDK 9+ byte[] coder + compact strings（Latin1/UTF16）。
  • intern() 入常量池；native 实现与 GC 交互。

面试追问

  • StringBuilder 线程安全吗？（否；多线程用 StringBuffer 或局部 Builder）
  • 大量拼接为何用 Builder 不用 +？（编译期 + 可能优化，循环内 + 产生大量中间 String）

常见坑

39. ==、equals、hashCode 契约？

口述版： == 比引用；equals 比语义相等，重写 equals 必须重写 hashCode，否则 HashMap 里相等对象可能进不同桶；约定是对称、传递、一致。

具体介绍

  • 契约：equal 对象 hashCode 必须相同；hash 相同不必 equal。
  • 自定义实体作 Map key：字段不可变或逻辑不可变最稳。
  • Lombok @EqualsAndHashCode 注意父类、exclude 字段。

面试追问

  • 只重写 hashCode 不重写 equals 的后果？（破坏 Object 契约，集合行为异常）
  • 两个 unequal 对象 hash 相同叫？（hash 碰撞，正常，靠 equals 链上比对）

常见坑

  • Lombok @Data 在继承链上 equals/hashCode 默认不含 super——子类字段参与需 @EqualsAndHashCode(callSuper=true)。

40. Integer 缓存与装箱踩坑？

口述版： -128 到 127 的 Integer 缓存了，用 == 比较在这个范围内有时碰巧对，范围外 == 比的是引用一定错，比较值用 equals。

具体介绍

  • Integer.valueOf 默认缓存 -128～127（可 JVM 参数扩展上限）。
  • 自动装箱走 valueOf。
  • 金额用 BigDecimal，不用 double。

源码/参数

  • IntegerCache.high 默认 127，-XX:AutoBoxCacheMax=200 可调上限（≥127）。
  • == 比较两个 Integer 对象前应先 unbox 或 equals。

面试追问

  • Long 有缓存吗？（无默认小缓存 like Integer）
  • int 与 Integer 在 == 中如何比较？（拆箱）

常见坑

  • Map<Integer, ...> 用 == 比较 key；金额 double 精度——用 BigDecimal。

1.9 面向对象与 Java 8

41. 封装、继承、多态、抽象？

口述版： 封装隐藏细节只暴露接口；继承复用和扩展；多态同一引用不同子类不同行为；抽象抽共性，接口和抽象类都是手段。

具体介绍

  • 封装：private 字段 + getter/setter 或行为方法。
  • 继承：is-a，注意组合优于继承。
  • 多态：编译看引用，运行看对象，虚方法表。
  • 抽象：abstract class / interface 定义契约。

面试追问

  • 组合优于继承的典型例子？（Has-A 持有策略对象）
  • 里氏替换原则与多态关系？（答： 子类对象应能 替换父类 而不破坏程序正确性；多态是 编译看父类、运行看子类 的调用机制，LSP 是多态能安全使用的前提。）

常见坑

  • 过深继承树导致 fragile base class——改父类破坏子类。

42. 重载与重写？静态方法能重写吗？

口述版： 重载同名不同参，编译期绑定；重写子类改父类实例方法，运行期绑定。静态方法是隐藏不是重写，看引用类型。

具体介绍

  • 重写：@Override，访问权限不能更严，返回类型协变。
  • 静态：类方法 不参与多态 override。
  • private/final 不可重写。
  • 重载（Overload）：同名不同参列表（个数/类型/顺序），编译期静态绑定；与返回值无关（仅返回值不同不能构成合法重载）。
  • 重写（Override）：子类实例方法覆盖父类，运行期虚方法分派；异常不能抛出更广的 checked exception。
  • 静态隐藏（Hide）：子类定义同名 static 方法时，调用看引用类型，易与子类实例方法「看起来像重写」混淆。
  • 面试追问：Object.equals(Object) 参数类型与 equals(String) 是重载还是重写？——后者是重载；重写必须参数列表与父类一致。
  • 常见坑：父类 void foo()、子类 int foo() 不是重写而是编译错误（返回类型+签名都不匹配重载规则）。

面试追问

  • @Override 写错签名是重载还是编译错误？（编译通过则为重载，易隐藏 bug）
  • 静态方法能否被 @Override？（不能）

常见坑

  • 子类「重写」父类 static 方法——隐藏，运行期看引用类型。

43. 接口与抽象类如何选？

口述版： 接口定义能力组合，Java 8 可以有 default；抽象类适合有共享状态和模板方法。对外 API 多用接口，内部骨架可用抽象类。

具体介绍

  • 接口：多实现、解耦、default 提供演进。
  • 抽象类：单继承、可含字段与构造器。
  • 领域建模：能力用接口，模板流程用抽象类。
  • 选接口：需要多种能力组合（Serializable + Comparable）、对外 SDK、测试替身（Mock）、Java 8+ default 做非破坏演进。
  • 选抽象类：多个子类共享状态/工具方法、模板方法固定骨架（如 AbstractList）、需要 protected 钩子给子类。
  • Java 8 之后：接口可有 static/default 方法，与抽象类差距缩小——仍无实例字段（除 static）、不能单继承类 + 多接口时抽象类占掉唯一 extends 位。
  • 面试追问：abstract class 能否不声明 abstract 方法？——可以，用于禁止实例化 + 共享代码；接口从 Java 8 起也可有 default 实现。
  • 常见坑：为「省写代码」把接口当抽象类用大量 default 塞实现——破坏实现类可读性，且 default 冲突需显式解决。

面试追问

  • Java 8 接口多 default 方法冲突怎么解？（类优先、子接口优先、需显式 override）
  • 函数式接口（@FunctionalInterface）与接口关系？

常见坑

  • 接口加 default 破坏实现类——API 演进需谨慎，非 default 方法仍 breaking。

44. Java 8 常用新特性？

口述版： Lambda 和 Stream 做集合处理，Optional 减少 NPE，新日期 API 替代 Date，接口 default 方法；线上 Stream 并行要谨慎。

具体介绍

  • Stream：中间/终端操作，惰性求值。
  • Optional：表达可能缺失，勿滥用为字段。
  • 时间：Instant、LocalDateTime、ZoneId。
  • 接口：default、static 方法。

源码/参数

  • Stream 不存储数据，管道 lazy，terminal 才执行。
  • Optional.orElse vs orElseGet（后者 supplier lazy）。

面试追问

  • parallelStream 用哪个 ForkJoinPool？（common pool，注意阻塞任务饿死）
  • Instant 与 LocalDateTime 区别？（绝对时间 vs 无时区本地时间）

常见坑

  • Stream 里改外部变量非线程安全；peek 调 IO 副作用难维护。

45. 深拷贝与浅拷贝？

口述版： 浅拷贝只复制引用，嵌套对象还是同一份；深拷贝递归复制或序列化。Bean 拷贝工具多数是浅拷贝，要深拷贝得自己写或 JSON 往返。

具体介绍

  • 浅：Object.clone 默认、BeanUtils.copyProperties。
  • 深：手动 clone 嵌套、序列化、Immutable 结构。
  • 业务：DTO 与 Entity 分离时常拷贝 DTO。

面试追问

  • 序列化深拷贝需类 Serializable，transient 字段呢？（不拷贝，需自定义 readObject）
  • 不可变对象是否还需深拷贝？（共享安全，引用拷贝即可）

常见坑

  • JSON 序列化深拷贝丢失类型信息/精度；循环引用需处理。

1.10 异常

46. Exception 与 Error？Checked 与 Unchecked？

口述版： Error 是 JVM 级严重问题一般不捕；Exception 可处理。Checked 必须声明或 catch，Unchecked 是 RuntimeException，编译器不强制。

具体介绍

  • Error：OutOfMemoryError、StackOverflowError。
  • Checked：IOException、SQLException。
  • Unchecked：NPE、IllegalArgumentException 等。
  • 业务异常通常继承 RuntimeException。

面试追问

  • Throwable → Error / Exception 层次？（答： Throwable 下分 **Error**（一般不 catch，如 OOM）与 **Exception**（可处理）；Exception 又分 受检（必须声明/捕获）与 运行时（RuntimeException）。）
  • try-with-resources 对 AutoCloseable 要求？（答： 资源类实现 **AutoCloseable.close()**；编译器生成 finally 中 close，若 close 也抛异常会 addSuppressed 到主异常；close 应幂等。）

常见坑

  • catch Exception 吞掉 Error 以外所有——不应 catch Throwable 除非框架入口。

47. 业务异常如何设计？

口述版： 分错误码和可读消息，是否打栈看是业务预期还是系统故障；ControllerAdvice 统一转 HTTP 和 JSON，别在业务里到处 try-catch 吞异常。

具体介绍

  • 错误码：枚举或常量，便于监控聚合。
  • 预期内失败（库存不足）：info/warn，少打栈。
  • 非预期：error + 栈，链路 id。
  • 与 HTTP 状态：4xx 客户端，5xx 服务端。

面试追问

  • 错误码与 HTTP status 如何映射？（业务 200 + code≠0 vs 4xx/5xx）
  • 国际化 message 放哪一层？（答： 文案 key 在 资源 bundle（messages_zh_CN.properties）；业务层只抛 错误码 + 参数，由 Web/全局异常处理 或前端按 locale 渲染 message。）

常见坑

  • 用异常做正常流程控制（如找不到当 Exception）——性能与可读性差。

48. try-catch-finally 与 finally 里 return？

口述版： finally 几乎总会执行，除非 System.exit；finally 里 return 会覆盖 try 或 catch 里的 return，所以不要在 finally 写 return。

具体介绍

  • 执行顺序：try → catch → finally。
  • try 有 return：先算返回值副本，再 finally，finally 若 return 则覆盖。
  • try-with-resources 自动 close，close 异常可能 suppressed。

面试追问

  • try-with-resources 中多个资源 close 顺序？（逆序声明顺序）
  • Thread.interrupt 与 InterruptedException？（答： interrupt() 设 中断标志；阻塞方法（sleep/wait/join）可能抛 InterruptedException 并清标志；业务应在 catch 后 恢复中断 或退出。）

常见坑

  • catch 后不再 throw 也不 log——「吞异常」线上难查。

1.11 引用、ThreadLocal、泄漏

49. 强、软、弱、虚引用？

口述版： 强引用平常 new；软引用内存紧时回收，适合缓存；弱引用 GC 就收，WeakHashMap 用；虚引用跟踪对象回收，几乎业务不用。

具体介绍

  • 强：Object o = new Object()。
  • 软：SoftReference，OOM 前回收。
  • 弱：WeakReference，一次 GC 可能清。
  • 虚：PhantomReference + ReferenceQueue，堆外资源清理。

面试追问

  • SoftReference 适合做图片缓存吗？（内存紧张回收，可能抖动）
  • WeakHashMap 的 key 何时被清？（下次 GC 无强引用）

常见坑

  • 虚引用不能单独 get 对象——get() 总 null，需 ReferenceQueue 线程处理。

50. ThreadLocal 原理与线程池泄漏？

口述版： 每个 Thread 有个 ThreadLocalMap，key 是弱引用 ThreadLocal，value 是副本；线程池线程不销毁，value 不 remove 就泄漏，用完必须 remove。

具体介绍

  • 结构：Thread.threadLocals → ThreadLocalMap。
  • 弱引用 key：ThreadLocal 回收后 key 变 null，value 仍强引用直到清理。
  • 规范：try/finally { threadLocal.remove(); }。
  • 跨线程：TransmittableThreadLocal（TTL）传递上下文。

源码/参数

  • ThreadLocalMap 开放寻址，key 为 WeakReference。
  • 线程池 worker 线程长期存活 → 必须 remove()。

面试追问

  • 父子线程如何传 ThreadLocal？（InheritableThreadLocal 或 TTL）
  • 为何 key 弱引用仍可能泄漏？（value 强引用直到线程结束或 remove）

常见坑

  • 线程池任务结束未 remove，下一个任务读到脏上下文（如 userId）。

1.12 序列化与分层

51. serialVersionUID 与 RPC 少用 Java 序列化？

口述版： UID 是版本号，类改了不匹配就 InvalidClassException；Java 原生序列化慢、体积大、还挑类结构，RPC 一般用 JSON、Protobuf、Hessian。

具体介绍

  • 显式 serialVersionUID 避免自动算版本漂移。
  • 缺点：反射、全类元数据、安全（反序列化漏洞）。
  • 替代：Protobuf、Kryo（需注意兼容性）。

面试追问

  • 不加 serialVersionUID 改字段会怎样？（自动算 UID 变化，反序列化失败）
  • Kotlin/data class 与 Java 序列化？（答： data class **默认不实现 Serializable**；与 Java 互通常用 Jackson/Gson 或手写 @JvmField + 实现 Serializable，注意 默认构造/字段可见性。）

常见坑

  • 反序列化 gadget 链（Commons Collections）——生产禁用不可信字节流。

52. JSON 序列化常见坑？

口述版： Long 超过 JS 精度要转 String；日期统一时区和格式；枚举用 name 或 code 要约定；反序列化忽略未知字段要开开关，否则上线加字段就炸。

具体介绍

  • Long：前端 Number 精度 2^53-1。
  • 日期：ISO-8601 或时间戳 + 时区。
  • 循环引用：Jackson @JsonIgnore、DTO 切断环。
  • 空值：null vs 缺字段 vs "" 语义。

面试追问

  • Jackson FAIL_ON_UNKNOWN_PROPERTIES 与上线兼容？（答： 老客户端 加字段 时服务端若 true 会反序列化失败；上线兼容常 false 或 @JsonIgnoreProperties(ignoreUnknown=true)，配合 版本化 DTO。）
  • Fastjson AutoType 安全风险？（答： 开启 AutoType 可指定任意类反序列化，历史上多起 RCE；生产应 关闭 AutoType、用 白名单，优先换 Jackson 并禁 default typing。）

常见坑

  • 枚举改名导致历史 JSON 反序列化失败——用 code 字段稳定映射。

53. DTO / DO / Entity 分层？

口述版： Entity 跟表结构，DO 有时同义；DTO 对 API 或跨层传输，别把数据库字段和内部字段直接暴露给前端，方便演进和隐藏敏感信息。

具体介绍

  • Entity/DO：持久化层，跟 ORM 映射。
  • DTO/VO：入参出参，字段可裁剪、脱敏。
  • 转换：MapStruct、Assembler，避免 Controller 里手写大段 set。

面试追问

  • VO 与 DTO 是否必须两个类？（小项目可合并，大项目分离清晰）
  • Entity 带 lazy 关联直接返前端？（N+1 与 JSON 循环）

常见坑

  • Controller 直接返 Entity 暴露密码字段——必须 DTO 脱敏。

1.13 手写 / 小代码

54. 线程安全的单例写法？

口述版： 枚举最简单；静态内部类懒加载；双重检查锁要 volatile 防指令重排；别只用 synchronized 方法那种低效写法除非面试要求简单版。

具体介绍

  • 枚举：防反射、防反序列化多实例。

面试追问

  • 反射能否破坏枚举单例？（不能，JVM 禁止）
  • 懒汉 synchronized 方法瓶颈？（每次 get 加锁）

常见坑

  • DCL 未 volatile 可能看到半初始化对象（指令重排）。

55. 正确实现 equals 和 hashCode？

口述版： equals 先 == 再 null 和类型，再比关键字段；hashCode 用相同字段，保证 equal 则 hash 同；IDE 或 Lombok 生成，别只重写一个。

具体介绍

  • 契约： reflexive、symmetric、transitive、consistent。
  • hashCode：常用 Objects.hash(f1, f2)。
  • 可变对象作 key：不推荐；必须则不要改参与 equals 的字段。

面试追问

  • 只重写 equals 时 hashCode 默认 Object.identityHashCode——两个 equal 对象 hash 不同
  • 参与 equals 的字段变了，Map 查找失败——应用不可变 key 或禁止改字段

常见坑

  • 子类 equals 未检查 getClass() 对称性——与 Lombok @EqualsAndHashCode 配置相关。
