六、多线程

格式说明：每题先 口述版（面试现场 30～60 秒），下方 具体介绍 便于复习展开。与 J9（JMM）、模块一 ConcurrentHashMap 交叉阅读。

6.1 并发三性与 Java 内存模型

T1. 并发编程要解决的三个核心问题？

口述版： 原子性、可见性、有序性。原子性靠锁/CAS/原子类；可见性靠 volatile、synchronized、final；有序性靠 happens-before 和 volatile 禁重排。

具体介绍

  • 原子性：一组操作要么全完成要么全不完成；典型反例是 i++、check-then-act，需要锁、CAS 或原子类。
  • 可见性：一个线程改共享变量，别的线程能尽快看到；无同步时工作内存副本可能长期陈旧。
  • 有序性：程序执行顺序与代码顺序的感知一致（在 HB 约束下）；编译器/CPU 重排会破坏多线程下的「直觉顺序」。
  • 源码/规范锚点：java.util.concurrent 包注释与 JLS §17 将三性问题映射到 lock、volatile、原子变量；面试可画「问题 → 手段」三角对照表。
  • 场景：转账扣款+入账、库存扣减、状态机迁移都同时涉及三性；只解决其一不够。
  • 追问：只加 volatile 能否保证转账原子性？（不能，复合逻辑要锁或原子类。）
  • 追问：有序性在单线程还需要关心吗？（as-if-serial 下不用；多线程共享状态才需要 HB。）

T2. JMM 是什么？主内存与工作内存？

口述版： JMM 是 Java 内存模型规范，不是 JVM 堆栈那张图。每个线程有工作内存，存主内存变量的副本；写先刷到主内存，读从主内存或副本来，由此产生可见性问题。

具体介绍

  • 主内存：共享变量真实存放处（概念上对应堆）。
  • 工作内存：线程私有缓存/寄存器，存 read 来的副本。
  • 与 运行时数据区 的「存储」视角不同，JMM 管 并发语义。
  • 规范出处：JSR-133 修订后的 JMM（JMM.pdf / JLS 17）；不是「堆=主内存、栈=工作内存」的一一对应，工作内存是 抽象 的 per-thread 缓存视图。
  • 八步 read/write 动作（了解即可）：lock → read → load → use → assign → store → write → unlock；面试说清「为何线程 A 写后 B 可能仍读旧值」。
  • 追问：JMM 与 CPU 缓存一致性协议（MESI）什么关系？（JMM 是语言层契约，实现依赖屏障 + 一致性。）

T3. 指令重排序有哪些层次？as-if-serial 是什么？

口述版： 编译器、CPU、内存系统都可能重排，只要单线程下结果不变（as-if-serial）。多线程下重排可能破坏可见性/有序性，所以要 volatile、锁、HB 规则约束。

具体介绍

  • 编译器重排：JIT 优化。
  • 处理器重排：乱序执行、StoreBuffer。
  • 内存重排：读写缓冲、缓存一致性延迟。
  • as-if-serial：单线程内不管怎么重排，结果与顺序执行一致。
  • HotSpot：C2 编译器重排 + Load/store reordering；x86 TSO 相对强，ARM/Power 更弱，故 以 JMM 语义为准 写可移植并发代码。
  • 经典可见性案例：context 重排导致未初始化对象被发布（DCL 无 volatile）；禁止 把 as-if-serial 当成多线程也成立。
  • 追问：编译器能否把两个 volatile 写重排？（volatile 写前后有屏障约束，不能随意越过。）

T4. happens-before 八规则口述几条核心的？

口述版： 程序次序、监视器锁、volatile、线程 start/join、传递性等。面试常举：unlock 先于后续 lock；volatile 写先于后续 volatile 读；start 先于 run 里动作。

具体介绍

  • 程序次序规则：同线程内前面的操作 HB 于后面的。
  • 监视器锁：unlock HB 后续对同一锁的 lock。
  • volatile：写 HB 后续读。
  • 线程 start：start() HB 线程内动作；join 结束 HB join 后代码。
  • 传递性：A HB B，B HB C ⇒ A HB C。
  • 完整八条（补全口述）：1 程序次序 2 监视器锁 3 volatile 4 线程 start 5 线程 join 6 中断 7 对象终结 8 传递性；面试 至少背 4 条 + 传递性。
  • monitor 规则细化：线程 A 对 monitor unlock HB 于线程 B 对 同一 monitor 的 lock（含 synchronized 进入）。
  • 追问：线程内 a=1;b=2，别的线程能否看到 b=2 但 a=0？（同线程 HB 禁止；不同线程无 HB 则可能。）

T5. 为什么需要 synchronized / volatile？

口述版： synchronized 管原子性+可见性+有序性（释放锁刷内存、获取锁读最新）；volatile 主要管可见性和禁特定重排，不保证 i++ 这种复合操作原子性。

具体介绍

  • synchronized：monitorenter/monitorexit + 内存语义。
  • volatile：写带 StoreStore/StoreLoad，读带 LoadLoad/LoadStore（JMM 抽象）。
  • 字节码：monitorenter / monitorexit（可成对出现在 synchronized 块）；JMM 规定 unlock 与 lock 的内存同步。
  • volatile 伪代码（JMM）：写后 StoreStore + StoreLoad；读前 LoadLoad + LoadStore（HotSpot 用具体屏障指令实现）。
  • 追问：synchronized 能否只保证可见性不保证原子性？（同一把锁内复合操作原子；锁外仍要整体设计。）

T6. Java 线程六种状态？与 OS 线程关系？

口述版： NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。RUNNABLE 可能正在跑也可能就绪等 CPU；BLOCKED/WAITING/TIMED_WAITING 在 Java 层都算「没 CPU 使用权」。

具体介绍

  • BLOCKED：等监视器锁。
  • WAITING：wait、join(无超时)、park。
  • TIMED_WAITING：sleep、wait(超时)、join(超时)。
  • 本质创建线程都是 new Thread → start → run。
  • 源码：java.lang.Thread.State 枚举六态；Thread.getState() 映射 JVM 内部状态。
  • RUNNABLE 陷阱：包含 Running + Ready（等 CPU），jstack 里大量 RUNNABLE 可能在等内核调度。
  • OS 映射：1:1 平台线程模型下 Java 线程 ≈ pthread；虚拟线程（T81）是 M:N。
  • 追问：BLOCKED 与 WAITING 在 jstack 里怎么区分？（BLOCKED 等 monitor；WAITING 等 park/wait。）

T7. 创建/启动线程的方式？run 和 start 区别？

口述版： 继承 Thread、实现 Runnable、Callable+FutureTask、lambda、线程池提交。start 启动新线程调 run；直接 run 只是普通方法调用，没有新线程。

具体介绍

  • Callable 有返回值，配合 ExecutorService.submit。
  • 线程池是生产环境推荐方式。
  • start 源码要点：start0() native，仅 NEW 态可 start，重复 start 抛 IllegalThreadStateException。
  • FutureTask：Callable → FutureTask → executor.submit；异常封装在 ExecutionException。
  • 追问：线程池 submit Runnable 与 execute 异常传播有何不同？（submit 未 get 可能「吞」异常，见 T51。）

T8. 守护线程与用户线程？

口述版： setDaemon(true) 为守护线程，JVM 在所有用户线程结束后退出，守护线程被直接终止。典型 GC、监控；业务逻辑不要用守护线程承载。

具体介绍

  • 分类：Thread.setDaemon(true) 在 start 之前 设置；默认 false 即 用户线程。JVM 启动时自带线程（如 main）是用户线程。
  • 退出语义：当 JVM 中 仅剩守护线程 在跑时，JVM 直接退出，不会等守护线程执行完 run 里的业务逻辑；finally 块 不保证 执行完毕。
  • 典型守护线程：GC 相关、JMX、部分框架后台线程；它们做的是 JVM/框架级 辅助，不是承载「必须跑完」的业务。
  • 与 ShutdownHook：Runtime.addShutdownHook 注册的是 用户线程 逻辑，在 JVM 开始退出时执行；与守护线程 abrupt 终止是两条线。
  • 场景：把「订单落库」放在守护线程里 —— 进程被 kill 或用户线程全结束时 可能丢数据；业务任务应提交线程池（用户线程）或等任务结束再退出。
  • 追问：线程池默认线程是守护还是用户？（默认 用户线程，会阻止 JVM 退出。）
  • 追问：守护线程能创建用户线程吗？（可以；只要还有用户线程，JVM 就不会因「只剩守护」而退出。）

6.2 volatile 与双重检查锁

T9. volatile 的三大特性？

口述版： 可见性、禁止特定重排序、对单变量读写原子性；volatile++ 不是原子。底层靠内存屏障 + 缓存一致性（MESI）。

具体介绍

  • 可见性：对 volatile 变量的写，会刷新到主内存；后续其他线程读该变量，能看到最新值（配合 HB 规则）。
  • 有序性：volatile 写与读之间建立 happens-before，禁止 与 volatile 访问相关 的有害重排（如 DCL 未初始化对象问题）。
  • 原子性（有限）：仅保证 单次 32/64 位读写等「单条语义」的原子；volatile++ 仍是 read-modify-write，不是 原子。
  • HotSpot 实现：JVM_ACC_VOLATILE 访问字段走 acquire/release 语义（JDK8+ 对 volatile 读写有明确实现路径）。
  • 与 CAS 对比：volatile 保证 单次 读写的可见/有序；AtomicInteger.getAndIncrement 才是 RMW 原子。
  • 场景：volatile boolean shutdown 停机标志、一写多读 的配置发布；复合更新仍用锁或原子类。
  • 追问：volatile 能禁止所有指令重排吗？（只禁止 与 volatile 变量相关 的特定重排。）

T10. volatile 可见性怎么实现？MESI 与 lock 前缀？

口述版： 写 volatile 会刷到主内存并使其他核缓存行失效；x86 上常用 lock 修饰写内存指令，触发总线锁或缓存锁，保证 MESI 一致。

具体介绍

  • 写路径：线程写 volatile → 插入内存屏障 → 写回主内存/使其他核该缓存行 Invalid（MESI Write-invalidate）。
  • 读路径：读 volatile 前屏障 → 若本地缓存失效则从主内存或独占行加载，保证读到最新值。
  • x86：带 lock 前缀的写常使缓存行 Invalid 其他核副本；读 volatile 可能触发 load barrier（实现随 CPU/JVM 版本而变）。
  • 总线窥探 / MESI：多核通过一致性协议协调；面试链路：volatile → 屏障 → lock/原子指令 → 缓存一致性。
  • MESI 四态：Modified / Exclusive / Shared / Invalid；Write-invalidate 广播使 stale 副本失效。
  • 场景：多核下无 volatile 的标志位可能永远读不到 true；写配置后其他线程仍用旧值做分支。
  • 追问：MESI 能保证原子性吗？（只解决一致性/可见性；i++ 仍要 CAS/锁。）

T11. 四种内存屏障在 volatile 上的作用（JMM 视角）？

口述版： LoadLoad、LoadStore、StoreStore、StoreLoad。volatile 写后常插 StoreStore+StoreLoad；读前 LoadLoad+LoadStore，防止读写重排越过 volatile。

具体介绍

  • 四种屏障语义（JMM 抽象）：LoadLoad、LoadStore（读侧）；StoreStore、StoreLoad（写侧，StoreLoad 最重）。
  • volatile 写：常见插入 StoreStore + StoreLoad，防止写前的普通写被重排到 volatile 写之后，并保证写对所有后续读可见。
  • volatile 读：LoadLoad + LoadStore，防止读后的普通读/写被重排到 volatile 读之前。
  • volatile 写-读配对：写线程 StoreLoad 与读线程 LoadLoad 共同建立 跨线程可见顺序。
  • 实现差异：不同 CPU 映射到不同指令（x86 TSO 较强，ARM 更弱）；答题以 JMM 语义为准，不必背每种 CPU 汇编。
  • 场景：DCL、状态标志与普通字段的发布顺序都依赖屏障语义，不是「加了 volatile 就万能」。
  • 追问：为什么 StoreLoad 开销大？（往往实现为全屏障，冲刷 store buffer。）

T12. 为什么 volatile 不能保证 i++ 原子？

口述版： i++ 是 read-modify-write 三步，中间可能被别的线程插入，要用 AtomicInteger 或 synchronized。

具体介绍

  • 三步 RMW：i++ 在字节码层是 iload → iconst_1 → iadd → istore，中间可被其他线程插入同样操作，结果丢更新。
  • volatile 只保证：每次 单独 load/store 的可见性，不 把四步捆成原子整体。
  • 替代：AtomicInteger.incrementAndGet() 内部 CAS 自旋；或 synchronized / LongAdder（高并发计数）。
  • 场景：全局计数器、限流计数若只用 volatile int，高并发下统计偏小；应用原子类或分段计数。
  • 追问：long 型 volatile++ 呢？（同样非原子 RMW。）
  • 追问：用 volatile 存 AtomicInteger 引用行吗？（引用读写原子，但 改对象内部 仍要原子类或锁。）

T13. 单例双重检查锁为什么要 volatile？

口述版： new 对象可能指令重排成：分配内存 → 引用赋值 → 初始化；别的线程可能看到未初始化完的对象。volatile 禁止这种重排。

具体介绍

  • 问题根源：new Singleton() 可能被重排为：分配内存 → store 引用 → <init> 构造；其他线程见引用非 null 但对象未构造完。
  • volatile 作用：对 instance 的读写禁止上述重排，保证 先构造完成再发布引用（JDK5+ JMM 明确）。
  • 标准写法：private static volatile Singleton instance; + DCL 内层 synchronized。
  • 与模块一衔接：单例 DCL 是 volatile 有序性 最经典考点，不是「为了可见性 alone」。
  • 场景：懒加载单例、连接池 holder 的双重检查都需 volatile 或等价安全发布手段。
  • 追问：不用 volatile 用 final 字段能否 DCL？（final 域安全规则辅助，DCL 仍标准答 volatile 引用。）

T14. volatile 写 happens-before 后续 volatile 读？

口述版： 是 HB 规则之一：对同一 volatile 变量，写操作 HB 后续任何线程对它的读，从而保证可见性。

具体介绍

  • HB 规则：对 同一 volatile 变量，写操作 happens-before 后续 任意线程 对它的读。
  • 可见性推论：B 读到 volatile 新值后，根据 HB 传递，还可能看到 A 在写 volatile 之前 对普通变量的写（若存在 HB 链）。
  • 模式：volatile boolean shutdown + 普通字段：A 写数据再 shutdown=true；B 见 true 后读数据应一致（需设计保证 HB 传递）。
  • 场景：优雅停机、一次性初始化完成标志、事件通知（替代部分 wait/notify 的简单场景）。
  • 追问：两个不同 volatile 变量之间有无 HB？（仅各自写-读对；跨变量要靠程序次序或锁传递。）
  • 追问：volatile 能替代 synchronized 吗？（不能互斥；只适合标志位与受控发布。）

T15. final 域的可见性（重排序规则）？

口述版： final 字段在构造器结束前不能重排到构造器外被其他线程看到「未初始化完的对象」；对象引用 this 逃逸仍要小心。

具体介绍

  • final 域重排规则：构造器内对 final 字段的写，在对象引用 this 逃逸给别的线程之前，final 值对其他线程可见（final field safe publication）。
  • 限制：非 final 字段仍可能被重排可见未初始化值；this 逃逸（构造器把 this 传出去）仍危险。
  • JMM：JSR-133 起对 final 有 初始化安全性 保证，Immutable 对象常用 final 字段表达。
  • 场景：不可变 DTO、配置对象全 final 字段 + 构造器赋值，安全发布引用即可；可变对象仍要 volatile/锁。
  • 追问：final 能替代 volatile 做开关吗？（不能，final 只赋值一次，不是多线程状态位。）
  • 追问：static final 与实例 final 可见性？（static final 在类初始化 HB 规则下可见；实例 final 跟构造器 HB。）

T16. volatile 与 synchronized 选用？

口述版： 一个标志位、状态发布用 volatile；复合逻辑、临界区用 synchronized 或 Lock。volatile 无阻塞、不互斥。

具体介绍

  • volatile 适合：一写多读的标志位、状态发布、简单 shutdown/config；无阻塞、不互斥，读多写少吞吐好。
  • synchronized/Lock 适合：复合逻辑、read-modify-write、多字段不变式、临界区必须互斥。
  • 选型表：标志位/状态发布 → volatile；临界区/复合操作 → synchronized / ReentrantLock；高并发计数 → LongAdder。
  • 性能：volatile 无 阻塞 开销；锁竞争大时 volatile 无法替代互斥，反而要用减小临界区 + 锁分段。
  • 场景：running 标志用 volatile；账户余额变更用锁；QPS 统计用 LongAdder 而非 volatile int。
  • 追问：volatile 能当锁用吗？（不能互斥，两线程可同时进入临界逻辑。）

T17. long/double 非 volatile 读写为何可能「半个值」？

口述版： JVM 允许对 64 位非 volatile 读写拆成两次 32 位（32 位 JVM 上更明显），所以共享 long/double 要 volatile 或原子类。

具体介绍

  • JLS 允许 tearing：对 64 位 非 volatile 的 long/double，JVM 允许拆成两次 32 位读写（32 位 VM 必提；64 位 VM 理论上仍可能，规范允许）。
  • 现象：一个线程写 long，另一个可能读到 高 32 与低 32 来自不同写入 的「拼接怪值」。
  • 实践：共享 long/double 用 volatile、AtomicLong / DoubleAdder 或锁保护；不要裸共享非 volatile long。
  • 场景：全局 ID 生成、时间戳、金额（分）累加若用 long 共享，必须 volatile 或原子类。
  • 追问：AtomicLong 与 volatile long 选型？（仅读写的发布用 volatile；RMW 用原子类。）
  • 追问：double 在金融计算呢？（仍要可见/原子语义；精度另用 BigDecimal。）

6.3 synchronized 与锁升级

T18. 对象头 Mark Word 里与锁相关的信息？

口述版： Mark Word 存哈希、GC 年龄、锁状态（无锁/偏向/轻量/重量）。锁升级就是改 Mark Word 里的锁标志与指针。

具体介绍

  • 对象头组成：Mark Word + Klass Pointer（压缩指针时可能 klass 另存）；Mark Word 存哈希、GC 分代年龄、锁状态等，随锁升级被复用编码。
  • 锁相关位：无锁 / 偏向 / 轻量 / 重量 / GC 标记等（01/00/10/11 等组合，以 OpenJDK 版本为准）。
  • 布局：64 位压缩指针下 Mark Word 64 bit：hashcode、GC age、biased lock epoch、lock bits。
  • 源码入口：OpenJDK markWord.hpp、ObjectSynchronizer；Klass pointer 在对象头另一 word。
  • 场景：排查锁竞争、理解 synchronized 为何几乎无 API 开销路径（偏向/轻量 fast path）。
  • 追问：哈希码与锁竞争冲突吗？（计算 identity hash 可能 撤销偏向 并影响锁状态。）

T19. synchronized 锁升级路径？

口述版： 无锁 → 偏向锁（同线程反复进）→ 轻量级锁（CAS 抢 Record）→ 重量级锁（Monitor 阻塞）。JDK15+ 偏向锁默认关闭，路径常是轻量→重量。

具体介绍

  • 升级路径：无锁 → 偏向锁（同线程反复进，JDK15+ 默认常关）→ 轻量级锁（CAS 抢 Lock Record）→ 重量级锁（Monitor + 内核阻塞）。
  • 目的：无竞争时避免内核 mutex；竞争加剧 单向膨胀，一般 不能 从重量降回轻量（除 GC/撤销偏向等特殊场景）。
  • HotSpot 路径：fast_lock → 偏向 BiasedLocking → 轻量 LightweightLocking → 重量 Inflated → ObjectMonitor。
  • **JDK 15+**：-XX:-UseBiasedLocking 默认关偏向；路径常 轻量 CAS 自旋 → 膨胀。
  • 场景：短临界区、低竞争 sync 走轻量；线程数多、持锁时间长则快速膨胀，RT 上升。
  • 追问：锁能降级吗？（一般 不能 从重量降回轻量；GC STW 等场景可能 撤销偏向。）

T20. 偏向锁、轻量级锁、重量级锁各适合什么场景？

口述版： 偏向：几乎无竞争、同线程；轻量：短临界区、低竞争 CAS；重量：激烈竞争、需要 park/unpark 阻塞。

具体介绍

  • 偏向锁：几乎无竞争、同一线程 反复进入；Mark 存 threadId，再进 无需 CAS；多线程竞争则 revoke bias。
  • 轻量级锁：短临界区、低竞争；栈上 Lock Record 复制 Mark，CAS 抢；失败自旋后 inflate 为重量。
  • 重量级锁：激烈竞争、持锁时间长；内核 mutex / pthread_cond，线程 park 不占 CPU 自旋。
  • 选型直觉：单线程热点 sync 曾适合偏向；生产多线程服务更常看到 轻量→重量。
  • 场景：HashMap 非线程安全 + 外层 sync 短锁 vs 长事务持锁 —— 后者应缩小临界区或换 Lock 分段。
  • 追问：为什么 JDK 关偏向？（维护成本、延迟抖动、与某些场景不兼容。）

T21. ObjectMonitor 是什么？

口述版： 重量级锁底层 C++ Monitor：Owner、EntryList、WaitSet；enter 失败进 EntryList，wait 进 WaitSet，notify 唤醒。

具体介绍

  • ObjectMonitor：C++ 实现的重量级锁监视器；Owner 当前持锁线程，EntryList 阻塞等锁，WaitSet 调 wait() 的线程。
  • enter/exit：ObjectMonitor::enter 失败进 EntryList；wait() 释放锁并进 WaitSet；notify 唤醒进 EntryList 再抢锁。
  • 与 API 关系：synchronized、Object.wait/notify 同一套 Monitor；轻量阶段 Mark Word 尚未指向 Monitor。
  • ObjectMonitor 字段：_owner、_EntryList、_WaitSet、_cxq（竞争队列，实现随版本变）。
  • 场景：jstack 里 BLOCKED 等 monitor 时，对应某对象 inflating 后的 Monitor 队列。
  • 追问：synchronized 与 Monitor 一一对应吗？（膨胀后 Mark 指向 Monitor；轻量阶段无 Monitor。）

T22. synchronized 与 ReentrantLock 对比？

口述版： sync 是 JVM 关键字，自动释放；Lock 是 API，需 try/finally unlock，可中断、超时、公平、多 Condition。

具体介绍

  • sync 早期性能差，JDK6 后优化（偏向/轻量）；Lock 提供更灵活语义。
  • 等待：Lock lockInterruptibly；sync 不可中断除非异常/结束。
  • ReentrantLock：内部 Sync extends AQS；lock() → acquire(1)；需 try/finally unlock。
  • 能力差：tryLock(timeout)、lockInterruptibly、newCondition() 多等待队列。
  • 追问：性能上 sync 与 Lock 怎么选？（JDK6+ 差距缩小；看 语义需求 而非裸性能。）

T23. 可重入锁含义？

口述版： 同一线程对已持有锁再 lock 不会死锁，计数+1，unlock 减到 0 才真正释放。synchronized 与 ReentrantLock 都可重入。

具体介绍

  • 定义：同一线程对 已持有 的锁再次加锁不会自死锁；内部 重入计数 +1，unlock 减到 0 才真正释放。
  • Monitor 重入：_owner 同线程再 enter 重入计数 +1。
  • AQS 重入：ReentrantLock.NonfairSync.tryAcquire 看 exclusiveOwnerThread 与 state，同线程则 state++。
  • 场景：递归调用带 synchronized 的方法、锁内调同对象另一 synchronized 方法 —— 依赖可重入。
  • 追问：可重入为何仍可能死锁？（重入只解决 同线程 重复拿锁；两线程循环等待仍会死锁。）
  • 追问：不可重入锁会怎样？（同线程第二次 lock 会阻塞自己 —— 典型自死锁。）

T24. 锁消除与锁粗化？

口述版： JIT 发现锁仅单线程可达则消除；循环内反复 lock/unlock 可能粗化成一次大锁。

具体介绍

  • 锁消除（Lock Elimination）：JIT 逃逸分析 证明 synchronized 锁对象 未逃逸 出线程（如方法内 new Object() 作锁），则整个 sync 块可被 优化掉，因为无其他线程能竞争。
  • 开关与诊断：-XX:+EliminateLocks（受 -XX:+DoEscapeAnalysis 等影响）；诊断可用 -XX:+PrintEliminateLocks（版本/发行版差异大，生产慎用）。
  • 锁粗化（Lock Coarsening）：循环内反复 lock/unlock 同一锁，JIT 可能合并成 一次大锁 包住循环，减少 enter/exit 开销。
  • 风险：粗化可能 扩大持锁时间，若循环体变长或后来加了 IO，可能意外增大竞争 —— 仍以 JIT 启发式为准。
  • 场景：局部 StringBuilder + sync（极端优化路径）、微基准里「无竞争 sync」被消除导致 与生产行为不一致。
  • 追问：生产如何验证？（-XX:+PrintEliminateLocks 等诊断，版本差异大。）
  • 追问：锁消除能消除实例字段上的 sync 吗？（若对象逃逸或可被其他线程访问，不能 消除。）

T25. 自旋锁在 JVM 里的角色？

口述版： 轻量级锁获取失败先 CAS 自旋，避免立刻阻塞；自旋过多则升级重量锁。

具体介绍

  • 轻量锁阶段：CAS 抢 Mark/Lock Record 失败时，先在用户态 自旋 重试，避免立即 inflate 进内核阻塞。
  • Adaptive Spin：HotSpot 根据 历史自旋成功率 调整自旋次数；自旋过多浪费 CPU 则 升级重量锁 并 park。
  • 与 AQS：AbstractQueuedSynchronizer 入队前也有 短期自旋（spinForTimeout 等路径），思想类似。
  • 场景：锁持有 极短、竞争 偶发 时自旋划算；高竞争长临界区自旋会导致 CPU 飙高 仍拿不到锁。
  • 追问：自旋占 CPU 吗？（是；高竞争时自旋过多会 浪费 CPU，故会升级阻塞。）
  • 追问：自旋和线程池 worker 阻塞区别？（自旋仍 RUNNABLE；park 后 WAITING，不占 CPU 时间片。）

T26. sync 修饰 static 与实例方法锁什么？

口述版： 实例方法锁 this；static 锁 Class 对象；不同实例可并行进 static sync。

具体介绍

  • **实例方法 synchronized**：锁的是 当前实例 this；不同实例的实例 sync 互不阻塞（除非同一实例）。
  • **静态方法 synchronized**：锁的是 声明类的 Class 对象（java.lang.Class 实例）；该类的所有 static sync 互斥（同一 Class）。
  • 同步代码块：可显式指定任意对象作 monitor，如 synchronized(configLock)，粒度比锁整个方法更细。
  • 字节码：实例 sync 用 aload_0 作 monitor；static sync 用 ldc Class 作 monitor；monitorenter/monitorexit 成对。
  • 场景：单例 double-check 锁 Class 或专用 lock 对象；实例方法 sync 保护实例字段，static sync 保护 static 字段。
  • 追问：锁 Class 对象会影响子类吗？（static sync 锁的是 声明类的 Class，子类有自己的 Class，不共享 同一把 Class 锁。）
  • 追问：sync 实例方法锁 this，子类 override 还锁同一个 this 吗？（是，同一对象 monitor。）

T27. 公平锁 vs 非公平锁？

口述版： 非公平允许插队，吞吐高；公平 FIFO 排队，避免饥饿但切换多。synchronized 非公平；ReentrantLock 构造可选公平。

具体介绍

  • 非公平锁：新线程/刚唤醒线程可 插队 CAS 抢锁，减少上下文切换，吞吐高；可能 饥饿 但 JVM 默认如此。
  • 公平锁：严格 FIFO 排队，避免饥饿，但唤醒/调度开销大，吞吐通常更低。
  • **ReentrantLock(boolean fair)**：FairSync 先 hasQueuedPredecessors 再 CAS；NonfairSync 先 tryAcquire 插队。
  • synchronized：JVM 非公平，无 API 改公平性。
  • 场景：高并发网关、缓存更新常用非公平；需要 严格排队（如有限资源按序）才开公平锁。
  • 追问：公平锁为何吞吐低？（严格 FIFO，唤醒/调度 开销大，插队机会少。）

6.4 AQS 与 JUC 锁

T28. AQS 是什么？state 与 CLH 队列？

口述版： AbstractQueuedSynchronizer：state 表示锁/许可；CLH 变体双向队列挂阻塞线程；acquire 失败入队 park，release 唤醒后继。

具体介绍

  • AQS 定位：AbstractQueuedSynchronizer 是 JUC 锁/同步器的 框架；子类只需实现 tryAcquire/tryRelease（或 shared 版）。
  • state：volatile int 表示锁重入次数、许可数、 latch 计数等，语义由子类定义。
  • CLH 变体队列：双向链表挂 阻塞线程 Node；acquire 失败入队 park，release 成功 unpark 后继。
  • 子类：ReentrantLock.Sync、Semaphore.Sync、CountDownLatch.Sync 等 共享/独占 模式。
  • 场景：理解 ReentrantLock 阻塞队列、Semaphore 限流，都回落到同一套 AQS 模板。
  • 追问：为什么用 CLH 变体而非裸链表？（减少 全局锁，近 FIFO，支持 cancel/unpark 后继。）

T29. acquire 与 release 模板流程？

口述版： tryAcquire 成功则继续；失败则 addWaiter、自旋/checkPredecessor、shouldParkAfter、park；release 改 state、unpark 后继。

具体介绍

  • acquire 模板（独占）：tryAcquire 成功 → 返回；失败 → addWaiter → acquireQueued 自旋检查前驱 → shouldParkAfterFailedAcquire → LockSupport.park。
  • release 模板：tryRelease 改 state 成功 → unparkSuccessor(head.next) 唤醒后继（需跳过 cancel 节点）。
  • 模板方法模式：AQS 固定流程，子类只实现 try* 的 CAS/计数逻辑。
  • 场景：自定义同步器（如只允许 N 个线程进某资源）可继承 AQS 而非自己写 park 队列。
  • 追问：为什么从 head.next 唤醒？（head 是哨兵；需处理 cancel 节点 跳过。）
  • 追问：acquire 可中断吗？（acquireInterruptibly 响应 interrupt 并抛异常。）

T30. ReentrantLock 如何实现可重入？

口述版： state 记录重入次数，持有线程是当前 owner；同线程再次 lock state++。

具体介绍

  • state + owner：ReentrantLock 的 state 表重入次数；exclusiveOwnerThread 表当前持锁线程。
  • NonfairSync.tryAcquire：若 current==owner 则 state+1；否则 CAS state 0→1 并设 owner。
  • unlock：tryRelease 减 state，为 0 时 setExclusiveOwnerThread(null)；必须配对，否则 state 泄漏「假死锁」。
  • 场景：业务代码多层封装都调 lock()，只要同线程，计数正确即可；忘记 unlock 会导致其他线程永久阻塞。
  • 追问：synchronized 重入与 AQS state 类比？（概念同 计数，实现一个在 Monitor 一个在 AQS。）

T31. Condition 与 wait/notify 区别？

口述版： 一个 Lock 多个 Condition，可精确唤醒某队列；Object.wait 只有一个等待集。

具体介绍

  • 多 Condition：一个 ReentrantLock 可 newCondition() 多个队列，精确唤醒 等在某条件上的线程；Object.wait 只有一个 WaitSet。
  • ConditionObject：内部 Condition 队列 Node 链表；await 释放锁并挂起；signal 把线程转移到 AQS 同步队列 抢锁。
  • 标准用法：while (!cond) await() 防虚假唤醒；await/signal 前必须 持有 Lock。
  • 场景：有界阻塞队列 notEmpty / notFull 两个 Condition，生产者只唤醒消费者，消费者只唤醒生产者。
  • 追问：await 为何要在 loop 里？（虚假唤醒 + 条件可能被别的线程改掉。）

T32. ReadWriteLock 思路？

口述版： 读共享、写独占；state 高 16 位读计数、低 16 位写锁。读多写少提升并发。

具体介绍

  • 读写分离：读锁 共享（state 高 16 位计数），写锁 独占（低 16 位）；读多写少时并发读吞吐高于互斥锁。
  • ReentrantReadWriteLock：写持有时阻塞所有读；读持有时阻塞写；不支持读锁升级写锁（易死锁）。
  • StampedLock：乐观读 tryOptimisticRead + validate；适合读极多、写极少；注意 不可重入写 等限制。
  • 实现细节：读锁可重入，写锁可重入；写锁与读锁互斥；锁降级（写→读）RRWLock 支持，升级不支持。
  • 场景：本地缓存、配置快照读多写少；写频繁则 RWL 反而不如单锁简单。
  • 追问：读锁能升级写锁吗？（RRWLock 不支持 升级，易死锁；需先释放读再拿写。）
  • 追问：读锁之间会互斥吗？（不会，共享读；写与读/写互斥。）

T33. Semaphore 做什么？

口述版： 信号量，控制同时访问资源的线程数；acquire 减许可，release 加许可。

具体介绍

  • 信号量：维护 permits 许可；acquire 减许可（无则阻塞），release 加许可；控制 同时访问 某资源的线程数。
  • 实现：Semaphore 内部 Sync 继承 AQS，state=permits；acquireShared / releaseShared。
  • 公平/非公平：构造参数 fair 选 FairSync / NonfairSync。
  • 场景：限流（并发最多 N）、连接池 概念配额（实际池化另说）、停车场车位模型。
  • 追问：Semaphore 与线程池区别？（Semaphore 不执行任务，只限并发度；线程池 调度 worker。）

T34. CountDownLatch 与 CyclicBarrier？

口述版： Latch 一次性倒数，await 等 count 到 0；Barrier 多线程互相等到齐再一起走，可循环。

具体介绍

  • CountDownLatch：一次性倒数；countDown 减 AQS state，await 阻塞到 0；不可重置，适合「主等子任务」。
  • CyclicBarrier：多线程 互相等到齐 再一起走；内部 ReentrantLock + Condition，可循环 _generation 换代。
  • 场景：Latch —— 启动 10 个并行任务，主线程 await 后汇总；Barrier —— 多阶段计算每阶段 barrier 同步。
  • CountDownLatch：走 acquireShared 等 state==0。
  • 追问：Latch 用共享还是独占 acquire？（acquireShared 等 state。）

T35. Stoppable 与 AQS 共享模式？

口述版： Semaphore/CountDownLatch 用 shared acquire；ReentrantLock 用 exclusive。

具体介绍

  • 独占模式（exclusive）：ReentrantLock —— 同一时刻一个 owner；tryAcquire / tryRelease。
  • 共享模式（shared）：Semaphore、CountDownLatch —— 多个线程可同时 acquire；tryAcquireShared / tryReleaseShared。
  • 题面笔误说明：应为 共享模式（shared） vs 独占（exclusive）。
  • 返回值语义：tryAcquireShared 负=失败，0=成功无剩余，正=成功且有剩余许可。
  • 场景：限流用 shared；互斥锁用 exclusive —— 选错模式无法实现正确语义。
  • 追问：ReentrantLock 为何用 exclusive？（互斥，同一时刻仅一个 owner。）

6.5 wait / sleep / interrupt

T36. sleep 和 wait 区别？

口述版： sleep 是 Thread 静态方法，不释放锁；wait 是 Object 方法，要持锁，释放锁进等待集。sleep 到点醒；wait 要 notify 或超时。

具体介绍

  • Thread.sleep：Thread 静态方法；不释放 已持有的 monitor；到时间唤醒，不依赖 notify。
  • Object.wait：实例方法；必须在 synchronized 内；释放锁 并进 WaitSet，需 notify/超时/中断唤醒。
  • API 归属：Thread.sleep 不释放 monitor；Object.wait 释放 monitor 并进 WaitSet。
  • 场景：sleep 做简单延迟/退避；wait 做 条件协作（生产者消费者）。
  • 中断：两者都响应 interrupt，抛 InterruptedException 并 清中断位（除非自己处理）。
  • 追问：wait 不带超时与 park 区别？（wait 必须持锁且与 notify 协作；park 更底层。）

T37. wait/notify 为什么必须在 synchronized 里？

口述版： 避免 lost wakeup：先检查条件再 wait，与 notify 的原子性由锁保证。

具体介绍

  • lost wakeup：若 if (!ok) wait() 不在锁内，notify 可能在 检查与 wait 之间 发生，导致 wait 永久睡下去。
  • 标准写法：synchronized(obj) { while (!cond) obj.wait(); } —— while 防虚假唤醒与条件被改。
  • 锁保证：检查条件 + wait() 原子 与 notify 互斥，不会丢信号（在正确模式下）。
  • 场景：任何自定义条件变量若用 wait/notify，都必须持锁 + while 循环。
  • 追问：用 if 一次 wait 可以吗？（不行，虚假唤醒 与条件变化都要 while。）

T38. interrupt 机制？

口述版： 线程有中断标志；interrupt() 设标志，阻塞中抛 InterruptedException 并清标志。正确处理：捕获后恢复中断或退出。

具体介绍

  • 中断标志：Thread.interrupt() 设中断位；阻塞方法（sleep/wait/join/take）抛 InterruptedException 并 清标志（除非捕获后自行 interrupt() 恢复）。
  • 协作式取消：任务应定期检查 isInterrupted() 或在阻塞点响应 IE，不能 靠 stop() 这种 deprecated 强杀。
  • Lock：lockInterruptibly() 等待锁时可被中断；普通 lock() 不可中断直到拿到锁。
  • 场景：线程池 shutdownNow、超时取消 Future，都依赖 interrupt + 业务代码响应。
  • 追问：任务取消最佳实践？（协作式：标志 + interrupt + 响应阻塞点。）

T39. yield 与 sleep(0) 区别？

口述版： yield 让出 CPU 进 Runnable，不释放锁，不保证优先级低的立刻跑；sleep(0) 行为依赖 OS 调度。

具体介绍

  • Thread.yield()：提示调度器 让出当前时间片；线程仍为 RUNNABLE，不释放 synchronized 锁；不保证 低优先级线程立刻运行（OS 实现相关）。
  • **Thread.sleep(0)**：在不少系统上触发 重新进入就绪队列 的调度机会，语义 依赖 OS/JVM；同样不释放锁（除非在 sync 外 sleep）。
  • 不可靠性：两者都不能用于 精确同步 或替代锁/volatile；高并发下靠 yield 做「公平」几乎无效。
  • 场景：自旋 CAS 失败后的 轻度退避（更推荐 LockSupport.parkNanos 带超时）；基准测试里 yield 可能导致结果抖动。
  • 与 busy-wait：纯自旋占满 CPU；yield 降低占用但增加调度不确定。
  • 追问：忙等 vs yield？（高并发 CAS 失败可 yield/park 退避，见 LockSupport。）
  • 追问：yield 能提升吞吐吗？（偶尔缓解自旋；滥用增加上下文切换，通常 不 作为优化手段。）

T40. park/unpark 与 wait/notify？

口述版： LockSupport 不要求持锁；unpark 可先于 park（许可计数），避免 lost signal。

具体介绍

  • LockSupport.park/unpark：不要求 持锁；per-thread 许可：unpark 可 先于 park，避免 wait/notify 的顺序依赖与 lost signal。
  • 与 wait 对比：wait 必须 synchronized；park 不会 释放 synchronized 锁（虚拟线程 pin 相关考点见 T83）。
  • AQS：阻塞线程用 LockSupport.park(this)，unpark 唤醒指定 Node 线程。
  • 场景：自定义同步器、JUC 内部实现；业务层更常用 Lock/Condition 而非裸 park。
  • 追问：park 会释放 synchronized 锁吗？（不会；与 wait 不同，这也是虚拟线程 pin 原因之一。）

6.6 CAS 与原子类

T41. CAS 是什么？ABA 问题？

口述版： Compare-And-Swap：期望值相等则更新。ABA 是值从 A→B→A，业务上可能有问题；用 AtomicStampedReference 带版本。

具体介绍

  • CAS：Compare-And-Swap，期望值相等则更新为新值；CPU 提供原子 cmpxchg，Java 通过 Unsafe/VarHandle 暴露。
  • ABA：值从 A→B→A，指针相同 但中间状态变过；栈/链表 pop-push 同节点可能出问题。
  • 解决 ABA：AtomicStampedReference / AtomicMarkableReference 带 版本戳。
  • 局限：自旋开销、只能保证 单变量 原子、复合逻辑仍需锁。
  • 场景：CHM 空桶插入、原子计数、无锁栈（需防 ABA）。
  • 追问：CAS 有什么问题？（自旋开销、ABA、只能保证单变量原子。）

T42. AtomicInteger 与 LongAdder？

口述版： 高并发计数 LongAdder 分段累加，读 sum 时再合并，比 AtomicLong 自旋少。

具体介绍

  • AtomicLong：单变量 CAS 链，高并发下 碰撞多 自旋重试。
  • LongAdder：Cell[] 分段 + base；add 分散到不同 Cell 减少 CAS 碰撞；sum() 是 弱一致快照 非实时精确。
  • 选型：统计 QPS、监控计数 → LongAdder；需要 每次读都精确 或 CAS 链逻辑 → AtomicLong。
  • 场景：Micrometer 类指标、网关 QPS 用 LongAdder；分布式序号仍用 AtomicLong 或外部 ID 服务。
  • 追问：LongAdder 能替代计数器上报精确值吗？（实时 sum 是近似，最终一致可接受。）

T43. Unsafe 与 VarHandle（JDK9+）？

口述版： Unsafe 提供 CAS、内存屏障等底层 API；VarHandle 是规范化的变量句柄，替代部分 Unsafe。

具体介绍

  • Unsafe：底层 CAS、内存屏障、直接内存等；JDK9 模块化 后应用代码难直接依赖 sun.misc.Unsafe。
  • VarHandle（JDK9+）：MethodHandles.lookup().findVarHandle，类型安全，提供 compareAndSet / getAndSet / memory fence。
  • 新代码：库与框架优先 VarHandle / 封装好的原子类，而非裸 Unsafe。
  • Atomic*：OpenJDK 内部仍大量通过 Unsafe/VarHandle 实现。
  • 场景：写 JUC 扩展、性能库才碰 VarHandle；业务用 AtomicInteger 即可。
  • 追问：Atomic* 底层现在用什么？（OpenJDK 仍大量 Unsafe/VarHandle 封装。）

T44. 乐观锁 vs 悲观锁？

口述版： 乐观：CAS 重试，无阻塞；悲观：先加锁再操作。synchronized/ReentrantLock 偏悲观；ConcurrentHashMap put 空桶 CAS 偏乐观。

具体介绍

  • 悲观锁：先假定会冲突，先加锁 再操作；synchronized、ReentrantLock、DB SELECT FOR UPDATE。
  • 乐观锁：假定冲突少，CAS/版本号 更新，失败重试；CHM 空桶 CAS、 AtomicReference.update。
  • CHM：空桶乐观 CAS，冲突则 synchronized 锁桶（退化悲观）。
  • 数据库：版本号 update ... where id=? and version=? 是典型乐观锁；行锁是悲观。
  • 场景：读多写少配置用乐观版本号；金融扣款、库存扣减常用悲观或 DB 行锁。
  • 追问：乐观锁失败怎么办？（重试 或退化为悲观；CHM 转 synchronized 锁桶。）
  • 追问：乐观锁一定比悲观快吗？（高冲突 时重试风暴，悲观更稳。）

6.7 线程池 ThreadPoolExecutor

T45. 线程池七大参数一口气说全？

口述版： corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、RejectedExecutionHandler。

具体介绍

  • 七大参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、RejectedExecutionHandler —— 构造 ThreadPoolExecutor 时 显式传入，生产忌用 Executors 魔法默认值。
  • 源码类：java.util.concurrent.ThreadPoolExecutor；默认拒绝策略 AbortPolicy；状态与 worker 数打包在 ctl（AtomicInteger）。
  • Worker 模型：HashSet<Worker>，Worker 继承 AQS 作 不可重入锁，保护 runWorker 里对中断的处理，避免外部 interrupt 与任务执行竞态。
  • 与提交方式：execute(Runnable) 走拒绝策略；submit 包 FutureTask，异常在 get() 才抛 ExecutionException。
  • 场景：Tomcat/Spring @Async 自定义池、批处理、MQ 消费 —— 七参都要能解释 为何这么配。
  • 易错点：无界队列 + 小 max → 线程数永远卡在 core，任务无限堆队列，最终 OOM 或 RT 爆炸。
  • 追问：七大参数里哪个最容易配错？（无界队列 + 小 max 导致永远不扩线程只堆队列。）
  • 追问：prestartAllCoreThreads 有什么用？（预热 core worker，削峰时减少 首任务建线程 延迟。）

T46. corePoolSize 含义与如何配置？

口述版： 核心线程数，池里常驻 worker 的 baseline。一般按 常态并发 或 CPU/IO 公式估算 设，不是越大越好；与 max 搭配，core ≤ max。

具体介绍

  • 含义：corePoolSize 是线程池希望 长期维持 的 worker 数量 baseline（在默认 allowCoreThreadTimeOut=false 下，core 线程 不因空闲 被 keepAlive 回收）。
  • 配置思路：按 常态并发 或 CPU/IO 公式初值（T57–T60）设，再 压测微调；必须满足 corePoolSize ≤ maximumPoolSize。
  • IO 密集：等待 DB/RPC 时间长，可 适当增大 core 填等待；CPU 密集 core 接近 availableProcessors() 或 N+1。
  • 源码：execute 时若 workerCount < corePoolSize 优先 addWorker(…, true) 建 core；prestartAllCoreThreads() 可提前建满 core。
  • allowCoreThreadTimeOut：设为 true 时，core 空闲超过 keepAlive 也可回收，适合 低频突发、不想常驻线程占内存。
  • 场景：电商大促前预热 core；夜间低峰开 allowCoreThreadTimeOut 省资源。
  • 追问：core 设成 0 可以吗？（可以，任务来再建线程，适合 低频突发。）
  • 追问：core 大于 max 呢？（非法，构造抛 IllegalArgumentException。）

T47. maximumPoolSize 含义？何时创建超过 core 的线程？

口述版： 允许的最大 worker 数。当前线程数 ≥ core 且 workQueue 已满，再 submit 才会创建非核心线程，直到 max。

具体介绍

  • 含义：maximumPoolSize 是池中 允许存在的 worker 上限（含 core 与非 core）；不是「一超 core 就立刻开新线程」。
  • 触发非 core 条件（面试必背）：当前 workerCount >= corePoolSize 且 workQueue.offer(task) 失败（队列满） 且 workerCount < maximumPoolSize → addWorker(..., false)。
  • 源码路径：ThreadPoolExecutor.execute → 三分支：补 core → offer 队列 → 尝试非 core → reject。
  • 无界队列陷阱：LinkedBlockingQueue() 默认容量极大时 offer 几乎永不失败 → 永远不会 创建超过 core 的线程，max 名存实亡。
  • 场景：有界 ArrayBlockingQueue(100) + core=10 max=50：高峰时队列满才会扩到 50；保护下游又限制线程爆炸。
  • 追问：队列无界时 max 还有用吗？（几乎无用，线程数卡在 core，任务无限堆积。）
  • 追问：SynchronousQueue 时 max 意义？（几乎 每任务一手交接，线程数可快速顶到 max，适合 Cached 模式。）

T48. keepAliveTime 与 unit？

口述版： 非核心线程（或 allowCoreThreadTimeOut=true 时的核心线程）空闲超过该时间会被回收，直到线程数 ≤ core。

具体介绍

  • 含义：keepAliveTime + unit 表示 非 core worker（默认）在空闲时，等待新任务的 最长存活时间；超时则 processWorkerExit 回收，直到 workerCount ≤ corePoolSize。
  • 源码：getTask() 里非 core 用 workQueue.poll(keepAliveTime, unit)；超时无任务则线程退出；core 默认用 take() 无限等。
  • allowCoreThreadTimeOut=true：core 也按 keepAlive 回收，适合 波动大、不想常驻 的池。
  • 设太大：多余非 core 线程占 栈内存（默认每线程 ~1MB 量级）；设太小：频繁建毁 线程，增加开销与抖动。
  • 场景：突发流量用较大 max + 较短 keepAlive，峰过后自动缩容；稳定负载 core≈max 则 keepAlive 影响小。
  • 追问：keepAlive 对 core 默认生效吗？（默认 不回收 core，除非 allowCoreThreadTimeOut。）
  • 追问：线程退出时 runWorker 做什么？（循环 getTask → run，退出前从 workers 集合移除并减 ctl 计数。）

T49. workQueue 存什么？常见队列如何选？

口述版： 阻塞队列存 待执行的 Runnable/Callable 任务（任务对象，不是「队列实现 Runnable」）。ArrayBlockingQueue 有界；LinkedBlockingQueue 可有界/无界；SynchronousQueue 不存任务直接交接。

具体介绍

  • 存什么：BlockingQueue<Runnable> 存 待执行的 Runnable（含 FutureTask 包装），不是 Thread 对象；worker 从队列 取任务 在自己的线程里 run()。
  • ArrayBlockingQueue：有界 数组 + 一把 ReentrantLock；公平/非公平构造可选；适合 固定容量背压。
  • LinkedBlockingQueue：链表；可指定容量，默认 Integer.MAX_VALUE 等价无界 —— FixedThreadPool 隐患所在。
  • SynchronousQueue：零容量 handoff，put 必须配对 take；CachedThreadPool 配合大 max，任务直接交给空闲 worker 或新建线程。
  • PriorityBlockingQueue / DelayQueue：按优先级/延迟调度；ScheduledThreadPoolExecutor 用 DelayedWorkQueue。
  • 选型原则：生产 有界队列 + 合理 max + 明确拒绝策略；防止 OOM 与无限 RT 堆积。
  • 场景：订单异步：有界 500 + CallerRuns 反压；日志异步：小队列 + Discard 仅非关键。
  • 追问：ArrayBlockingQueue 与 LinkedBlockingQueue 锁粒度？（Array 一把 ReentrantLock；Linked 经典 两把锁 头尾，JDK 实现以版本为准。）

T50. threadFactory 作用？

口述版： 创建线程：命名（pool-1-thread-3）、daemon、优先级、UncaughtExceptionHandler，便于日志与排查。

具体介绍

  • 职责：ThreadFactory.newThread(Runnable) 创建 池内 worker 线程；可统一 命名、daemon、优先级、UncaughtExceptionHandler。
  • DefaultThreadFactory：线程名 pool-N-thread-M；非 daemon；NORM_PRIORITY；便于 jstack 定位。
  • 最佳实践：业务前缀如 order-async-%d、设置 UncaughtExceptionHandler 打日志，避免任务异常 静默吞掉（尤其 submit 未 get 时）。
  • Guava：ThreadFactoryBuilder.setNameFormat(...).setUncaughtExceptionHandler(...).build()。
  • 场景：多池并存时无命名则 jstack 满屏 pool-2-thread-3 无法对应服务；生产必须 可观测命名。
  • 追问：线程工厂能返回同一个 Thread 吗？（可以但不推荐；破坏池语义。）
  • 追问：能设 daemon 吗？（可以；daemon worker 可能导致 任务未跑完 JVM 就退出，业务池一般 用户线程。）

T51. 任务提交流程？为何先入队再开非 core 线程？

口述版： 若 worker < core，新建 core worker；否则 offer 队列；队列满且 worker < max，新建非 core；否则 拒绝策略。先入队是为了 控制 max 以下线程数、减少线程创建开销。

具体介绍

  • execute 流程（四步）：① workerCount < core → 新建 core worker；② 否则 workQueue.offer；③ offer 失败且 workerCount < max → 新建 非 core；④ 否则 拒绝策略。
  • 为何先入队再扩 max：设计意图是 优先排队，把并发度压在 max 以内，减少 线程创建与上下文切换；只有队列 装不下 才继续加线程。
  • submit vs execute：submit 包装 FutureTask，异常封装在 ExecutionException 直到 **get()**；execute 异常走 UncaughtExceptionHandler。
  • SHUTDOWN 后：不再 accept 新 task（或按策略处理）；已在队列的任务仍可能被 worker 执行（shutdown 非 shutdownNow）。
  • 场景：画流程图是线程池面试 必考；结合有界队列说明「为何线程数不是一超 core 就涨」。
  • 追问：拒绝发生在哪一步？（offer 失败且 worker>=max，或 pool 已 SHUTDOWN/STOP。）
  • 追问：同一线程 execute 再 submit 自己池内任务会死锁吗？（可能，若池满 + CallerRuns + 在 worker 内阻塞 get。）

T52. 线程池五种状态？

口述版： RUNNING 接受新任务；SHUTDOWN 不接新任务但处理队列；STOP 不接且不处理队列；TIDYING 收尾；TERMINATED 结束。

具体介绍

  • 五种状态：RUNNING（接新任务+跑队列）、SHUTDOWN（不接新，跑完队列）、STOP（不接且不跑队列）、TIDYING（worker=0 且 queue 空过渡）、TERMINATED（terminated() 钩子完成）。
  • ctl 打包：高 3 位 runState，低 29 位 workerCount，一个 AtomicInteger 原子更新。
  • 迁移：shutdown() → SHUTDOWN → 任务与队列清空 → TIDYING → TERMINATED；shutdownNow() → STOP + interrupt workers + 返回未执行列表。
  • TIDYING：调用 terminated() 钩子（可 override 做监控），然后置 TERMINATED。
  • 场景：优雅下线：先 shutdown 停接新请求，awaitTermination 超时再 shutdownNow；监控 runState 防 假死池。
  • 追问：TIDYING 做什么？（worker=0 且 queue 空时 terminated() 钩子，然后 TERMINATED。）
  • 追问：RUNNING 直接到 STOP 可以吗？（shutdownNow 可以。）

T53. AbortPolicy？

口述版： 拒绝时抛 RejectedExecutionException，默认策略；调用方必须处理，适合不能静默丢任务。

具体介绍

  • 策略类：ThreadPoolExecutor.AbortPolicy，默认实现；rejectedExecution 直接 throw new RejectedExecutionException。
  • 语义：拒绝 不执行 该 task，强失败；调用方必须 catch 或上层统一处理，适合 不能静默丢 的核心链路。
  • 触发条件：队列满且 worker≥max，或 pool 已 shutdown；与 自定义 Handler 同一入口。
  • 适用场景：订单创建、支付回调、库存扣减 —— 失败应 告警、重试、降级，而不是无声消失。
  • 与监控：线程池指标应统计 reject 次数；Abort 便于触发熔断与扩容决策。
  • 对比：比 CallerRuns 不阻塞调用线程；比 Discard 可感知。
  • 追问：默认策略是什么？（AbortPolicy。）
  • 追问：Spring @Async 默认池满了会怎样？（取决于你配的 Handler，未配则 Abort。）

T54. CallerRunsPolicy？

口述版： 队列满时由 提交任务的线程 自己 run，形成 反压，减慢上游；适合能容忍主线程变慢、削峰场景。

具体介绍

  • 策略类：ThreadPoolExecutor.CallerRunsPolicy；拒绝时在 调用 execute/submit 的线程 里同步执行 r.run()。
  • 反压（backpressure）：上游 submit 变慢（HTTP 线程被占去跑任务），队列不再无限涨，形成 自然削峰。
  • 风险：若调用者是 Tomcat 请求线程，RT 会 同步拉长，甚至拖垮整个 Web 容器；需评估调用链身份。
  • 死锁风险：在 池内 worker 再 submit 本池任务且已满，CallerRuns 可能在 worker 内跑新任务 —— 设计时避免 同池嵌套阻塞 submit。
  • 适用场景：批处理允许主线程慢一点、MQ 消费可接受 producer 侧减速、有界队列 + 可控调用线程。
  • 追问：CallerRuns 会死锁吗？（若调用线程 同池 且 pool 满且任务内再 submit 阻塞 get，可能；避免在池内 submit 再 CallerRuns。）
  • 追问：CallerRuns 算「执行了任务」吗？（算，在 调用线程 执行，不占 worker 槽位。）

T55. DiscardOldestPolicy？

口述版： 丢弃队列 队首 最老任务，再尝试提交当前任务；适合 新任务比老任务更重要（谨慎使用）。

具体介绍

  • 策略类：ThreadPoolExecutor.DiscardOldestPolicy；拒绝时 poll 丢弃队列队首（最老）任务，再 尝试 submit 当前任务。
  • 语义：优先保证 最新 任务有机会进队/执行，牺牲 最老 任务 —— 仅当业务明确「新比旧重要」时考虑。
  • 破坏顺序：FIFO 业务（订单、消息）可能 乱序、饥饿；老任务永远被挤掉。
  • 实现细节：poll 丢 oldest 后通常再 execute(command)；若仍失败则继续 reject（取决于实现循环）。
  • 适用场景：极谨慎 —— 如实时行情只保留最新 tick、非关键 telemetry； 订单/支付禁用。
  • 追问：与 Discard 区别？（Oldest 腾位 再试提交当前；Discard 直接扔当前。）
  • 追问：与自定义「丢最新」比？（Oldest 是 JDK 标准 丢最老；丢最新需自写 Handler。）

T56. DiscardPolicy？

口述版： 静默丢弃被拒绝的任务，不抛异常；只适合 可丢 的埋点、非关键日志。

具体介绍

  • 策略类：ThreadPoolExecutor.DiscardPolicy；rejectedExecution 空实现，静默丢弃 当前被拒绝的任务，不抛异常。
  • 危险点：调用方 无感知，任务计数对不上、业务 丢数据；若无监控极难排查。
  • 适用场景：可丢 的非关键路径 —— 采样埋点、重复 debug 日志、超限的 metrics 上报。
  • 禁用场景：支付、消息、审计日志等 任何不能丢 的链路。
  • 可观测性：需自行埋点 submit 成功 vs 实际执行；不能依赖异常捕获。
  • 对比 Abort：Abort 强失败 可告警；Discard 静默 只适合明确可丢。
  • 追问：如何发现用了 Discard？（任务数对不上、无异常；靠 监控 submit 计数与队列长度。）
  • 追问：Discard 会丢队列里已有任务吗？（不会，只丢 本次拒绝 的那个 task；Oldest 才会 poll 队首。）

T57. CPU 密集型（CPU-bound）定义？

口述版： 程序大部分时间在做计算、逻辑判断，CPU 占用高，例如大量数学运算、编解码（纯 CPU 部分）、复杂规则引擎。

具体介绍

  • 定义：任务大部分时间在做 CPU 计算（运算、编解码 CPU 段、规则引擎、加密压缩纯计算），线程 很少阻塞 等 IO，CPU 利用率高。
  • 原文表述：CPU bound 系统中程序大部份时间用于计算、逻辑判断等 CPU 动作；如算圆周率到千位以下属于典型 CPU bound。
  • 识别手段：CPU 利用率高；jstack 线程栈多在 用户态计算（非 socket/JDBC 阻塞）；profiler 热点在方法体而非 IO wait。
  • JVM 侧：ForkJoinPool.commonPool() 并行 Stream、纯 CPU 分片任务；不适合 开海量线程（上下文切换反而慢）。
  • 与 IO 密集对比：IO bound 线程大量 WAITING 在 read/write；CPU bound 应 少线程多计算。
  • 场景：图像处理 pipeline 纯算法段、本地 JSON 大对象序列化 CPU 热点。
  • 追问：CPU 密集能用虚拟线程提速吗？（不能，carrier 仍占满 CPU，见 T84。）

T58. CPU 密集线程数 ≈ CPU 核数 + 1？原因？

口述版： 避免核数过少时空闲，+1 给 缺页中断、GC 辅助 等留一点余量；现代 CPU 超线程下「核数」常指 可并行硬件线程数。

具体介绍

  • 口述公式（保留）：线程数 = CPU 核数 + 1（现代 CPU 支持超线程）
  • +1 含义：在 N 个并行硬件线程都跑满时，留 一个额外线程 应对 缺页中断、GC 辅助线程协作、偶发短阻塞，减少 CPU 空转（Brian Goetz 等平台线程经验法则）。
  • 「核数」取法：Runtime.getRuntime().availableProcessors()；容器内应取 cgroup CPU quota 可见核数，不是宿主机物理核。
  • 超线程：逻辑核可并行两个硬件线程，公式里的 N 通常指 可并行硬件线程数 而非物理 die 数。
  • 局限：仍是 初值；锁竞争、NUMA、GC 压力都会偏离；必须 压测 看利用率与 P99。
  • 场景：ForkJoin 并行度、CPU 线程池 core=max≈N 或 N+1 起步。
  • 追问：+1 在容器 CPU limit 下怎么取 N？（按 ** cgroup 可见核数**，不是宿主机物理核。）

T59. IO 密集型（I/O bound）定义？

口述版： CPU 经常在等磁盘、网络、数据库等 IO，线程阻塞在 read/write，CPU 利用率相对低。

具体介绍

  • 定义：线程大部分时间 等待 IO（磁盘、网络、DB、RPC），CPU 在等 read/write，整体 CPU 利用率相对低。
  • 原文表述：相对硬盘/内存，CPU 很快，运行中 CPU 常在等 I/O 读写 —— Web、RPC、JDBC 典型 IO bound。
  • 识别：jstack 大量 WAITING/TIMED_WAITING 在 socket、HTTP client、JDBC、Future.get 等；APM 上 Wall time >> CPU time。
  • Little 定律联想：并发 ≈ 吞吐 × 响应时间；IO 等待越长，理论上可用 更多线程 填坑 —— 受 内存、连接池、文件句柄、下游 QPS 上限约束。
  • 场景：Tomcat maxThreads、HTTP 客户端池、DB 查询线程池常按 IO 模型 sizing。
  • 追问：IO 密集线程越多越好吗？（否，连接池、FD、上下文切换 有上限，见 T61。）

T60. IO 密集线程数公式？

口述版： 线程数 ≈ ((线程等待时间 + 线程 CPU 时间) / 线程 CPU 时间) × CPU 数目；用 APM/压测估 wait 与 compute 比例。

具体介绍

  • 口述公式（保留）：线程数 = ((线程等待时间 + 线程 CPU 时间) / 线程 CPU 时间) × CPU 数目
  • 公式含义：设 W=等待时间、C=CPU 时间，则每任务周期 W+C，CPU 占用比 C/(W+C)；要占满 N 核，线程数约 (W+C)/C × N。
  • 测量：APM/链路拿 Wall time 与 CPU time；压测不同并发看拐点；无数据时公式只是 估算。
  • 边界：结果还受 DB maxActive、下游限流、内存每栈 1MB 限制；不能无限放大。
  • 与 NIO：Netty 少线程多连接，不适用「一请求一线程」裸套公式；模型不同。
  • 容器：N 取 cgroup 可见核数；虚拟线程下 carrier 数 仍接近 N，虚拟线程数可远大于公式结果。
  • 场景：接口 P99=200ms 其中 CPU 20ms → 比例大，可支撑较多平台线程；迁移虚拟线程后 carrier 仍 ≈ N。
  • 追问：Netty 线程模型还要套这个公式吗？（NIO 少线程多连接，与 一请求一线程 模型不同。）
  • 追问：公式算出来 500 线程但连接池只有 50？（以 连接池与下游 为硬上限，公式只是 CPU 维度初值。）

T61. 线程池与连接池（如 Druid maxActive）如何一起压测？

口述版： 线程过多会导致 连接池争用、上下文切换；过少队列堆积 RT 上升。压测扫 core/max/queue，看 CPU、RT、池等待、拒绝次数，找拐点。

具体介绍

  • 联动关系：业务 线程数 与 连接池 maxActive 是两层并发；线程 >> 连接时，大量线程堵在 getConnection()，RT 升、假「线程池不够」。
  • 压测方法：固定连接池（如 Druid maxActive=50），扫 core/max/queue，看 CPU、接口 RT、active/waiting 连接数、拒绝次数 找拐点。
  • 瓶颈叠加：只调线程不调连接 → 线程空转等连接超时；只调连接不调线程 → 队列堆积 RT 升。
  • 指标：Druid getConnection 等待线程数、Tomcat queue size、线程池 queue size + reject。
  • 公式角色：T57–T60 给 初值，联调压测 定最终参；Little 定律帮助理解并发与延迟关系。
  • 场景：50 连接 + 200 业务线程 → jstack 满屏 BLOCKED 在 getConnection；应 对齐并发度 或 缩短持连接时间。
  • 追问：只调线程池不调连接池会怎样？（RT 好但 getConnection 超时 或相反。）

T62. shutdown 与 shutdownNow？

口述版： shutdown 平滑：不接新任务，跑完已提交；shutdownNow 尝试 interrupt 正在跑的 worker，返回未执行列表。

具体介绍

  • shutdown()：状态 → SHUTDOWN；不再 accept 新任务（execute 抛 RejectedExecutionException）；继续执行 已在队列与正在跑的任务；中断 空闲 worker 促退出。
  • shutdownNow()：状态 → STOP；尝试 interrupt 所有 worker；返回 未开始执行 的任务列表；不保证 正在跑的任务立刻停（需任务响应 interrupt）。
  • **awaitTermination(timeout, unit)**：阻塞等待 TERMINATED 或超时；常与 shutdown 组合 优雅退出。
  • 场景：Spring 容器 destroy、MQ consumer 下线：shutdown → 等队列 drain → 超时 shutdownNow。
  • 钩子：可 override terminated() 打日志/告警；ShutdownHook 里不要嵌套无限 await。
  • 追问：shutdown 后 execute 会怎样？（RejectedExecutionException。）
  • 追问：shutdownNow 返回的 list 是什么？（尚未执行 的 queued task，需业务决定是否重投。）

T63. 为什么不用 Executors 工厂？

口述版： Fixed/Single 用 无界 LinkedBlockingQueue 可能堆积 OOM；Cached 用 Integer.MAX_VALUE 线程数；阿里规约要求显式 ThreadPoolExecutor + 有界队列。

具体介绍

  • FixedThreadPool：Executors.newFixedThreadPool(n) → LinkedBlockingQueue() 无界，线程数 fixed=n；任务无限堆 可能 OOM。
  • SingleThreadExecutor：同上无界队列，单 worker；顺序执行但 队列无上限。
  • CachedThreadPool：SynchronousQueue + maximumPoolSize=Integer.MAX_VALUE，线程数可 爆炸，适合短任务原型 不适合生产。
  • ScheduledThreadPoolExecutor：DelayedWorkQueue 无界，延迟任务堆积同样 OOM 风险。
  • 阿里规约：生产用 显式 ThreadPoolExecutor + 有界队列 + 命名 ThreadFactory + 明确 RejectedExecutionHandler。
  • 场景：Demo/单元测试可用 Executors；线上网关、订单 必须显式七参 并可监控调参。
  • 追问：ScheduledThreadPoolExecutor 呢？（DelayedWorkQueue 无界，也要注意堆积。）

T64. 动态调参 setCorePoolSize / setMaximumPoolSize？

口述版： 运行时可调，会唤醒/中断 worker 重建；调小 max 不会立刻杀多余线程，依赖 keepAlive 回收。

具体介绍

  • setCorePoolSize(int)：运行时修改 core；增大 可 prestartCoreThread 或等任务触发建新 core；减小 且当前 worker>新 core 时会 interrupt 空闲多余 core。
  • setMaximumPoolSize(int)：运行时改 max；调小 不会 立刻 kill 超出的 worker，依赖 无任务 + keepAlive 逐步回收。
  • 不支持：队列容量 构造后不可改；要改队列只能 新建池 + 迁移（灰度切换 submit 入口）。
  • 动态线程池：Hippo4j、DynamicTp 等监听配置中心/MQ 热更新 core/max/keepAlive，配合监控与告警。
  • 场景：大促前调大 core/max；低峰调小 + allowCoreThreadTimeOut 缩容；注意 与连接池、下游限流 同步变更。
  • 追问：运行时改 queue 容量？（不支持，队列容量构造时固定，只能新建池迁移。）
  • 追问：改参时正在跑的任务？（不受影响；worker 数变化主要影响 新任务调度。）

6.8 ThreadLocal 与 TransmittableThreadLocal

T65. ThreadLocal 原理？

口述版： 每个 Thread 有 ThreadLocalMap，key 是弱引用 ThreadLocal，value 是副本；get/set 在当前线程 map 里操作，实现线程隔离。

具体介绍

  • 结构：每个 Thread 有 threadLocals（ThreadLocalMap）；ThreadLocal.set/get 在当前线程 map 里以 ThreadLocal 为 key（弱引用）、value 强引用存副本。
  • 线程隔离：A 线程 set 的值 B 读不到 —— 空间换时间，无锁。
  • Spring：TransactionSynchronizationManager 绑 Connection；MyBatis SqlSessionHolder 同理。
  • ThreadLocalMap：开放寻址、线性探测；初始容量小，冲突时探测链变长。
  • 场景：traceId、用户上下文、SimpleDateFormat 每线程一份（更推荐 DateTimeFormatter）。
  • 追问：为什么 key 是弱引用？（避免 ThreadLocal 实例无法回收；但 value 泄漏风险仍在，见 T67。）

T66. ThreadLocal 应用场景？

口述版： 跨层传用户上下文免参数传递、线程内事务资源、SimpleDateFormat 等非线程安全对象的 per-thread 实例。

具体介绍

  • 典型用法：跨层传递 用户/租户/trace 免层层传参；线程内 事务资源绑定；非线程安全对象的 per-thread 实例。
  • Spring 事务：同一线程内 @Transactional 共用同一 Connection 绑定在 TL。
  • 反模式：static 共享 SimpleDateFormat 并发 parse —— 用 TL 或 线程安全 DateTimeFormatter。
  • 日志 MDC：Slf4j MDC 基于 TL；线程池下需 clear/remove 或 TTL（T69）。
  • 场景：网关鉴权后 UserContext.set()，DAO 层直接 get；批处理每线程独立缓冲区。
  • 追问：ThreadLocal 能跨线程吗？（不能，除非 ITL/TTL，见 T68/T69。）

T67. ThreadLocal 内存泄漏原因与避免？

口述版： key 弱引用 GC 后 entry 还在，value 强引用链可达导致泄漏。用完 **remove()**；static ThreadLocal 配合 remove。

具体介绍

  • 泄漏原因：Entry 的 key（ThreadLocal）是 弱引用，GC 后 key=null，但 value 仍被 Entry 强引用，而 Entry 在 Thread 的 map 里 → Thread 不销毁则 value 泄漏。
  • 线程池加剧：worker 复用，不 remove 则 上一任务 value 串到下一任务 + 内存泄漏。
  • 修复：try/finally { threadLocal.remove(); }；线程池任务 必 remove；static ThreadLocal 尤其小心。
  • 场景：在线程池里 set 用户 ID 未 remove → 下一请求读到 错误用户（严重安全 bug）。
  • 追问：static ThreadLocal 为何危险？（value 生命周期跟 线程 一样长，池线程不退出。）

T68. InheritableThreadLocal？

口述版： 子线程创建时复制父线程 ITL 值；线程池下 子线程并非每次 new，值不传，需 TTL。

具体介绍

  • 机制：InheritableThreadLocal 在 new Thread 时 复制父线程 ITL map 到子线程（浅拷贝 引用）。
  • 线程池失效：池 worker 复用，不是每次 new Thread，提交任务时 不会 自动复制父 ITL → 子线程仍是 旧请求 上下文。
  • 浅拷贝风险：复制的是 引用，可变对象内容仍共享，需 immutable 或自己深拷贝。
  • 源码：Thread.init 调用 InheritableThreadLocal.inherit()；仅 新建 Thread 路径生效。
  • 场景：仅 parent 显式 new Thread(r).start() 的子任务能继承；**@Async 线程池几乎必丢**。
  • 追问：ITL 复制是深拷贝吗？（浅拷贝 引用，对象可变仍共享。）
  • 追问：和 TTL 比何时用 ITL？（仅父子 new Thread 且不用池；生产异步统一 TTL。）

T69. TransmittableThreadLocal（TTL）解决什么？

口述版： 线程池任务包装，提交时 capture 上下文，执行前 replay，执行后 restore，保证 trace/用户信息在线程池不丢。

具体介绍

  • 问题：线程池 capture 提交时刻 的上下文，worker replay 执行前注入，restore 执行后还原，避免 trace/用户信息丢失。
  • Alibaba TTL：TransmittableThreadLocal + TtlRunnable.get(task) 包装，或 Java Agent 增强 ThreadPoolExecutor 自动包装。
  • 流程：submit 线程 capture → worker replay → run → restore（防止污染下一任务）。
  • 与 MDC：Logback MDC 在线程池也需 clear/TTL 传递 traceId。
  • 场景：全链路 tracing、灰度标签、租户 ID 进异步线程。
  • 追问：与 MDC（Slf4j）关系？（Logback MDC 也是 TL；在线程池需 MDC.clear 或 TTL 传递 traceId。）

T70. ThreadLocal 与 synchronized 对比？

口述版： ThreadLocal 空间换时间，无锁隔离；synchronized 时间换空间，共享数据互斥访问。

具体介绍

  • ThreadLocal：空间换时间，每线程 独立副本，读写在各自 map，无锁；内存 ≈ 线程数 × 对象大小；适合 不可跨线程共享 的上下文。
  • synchronized：时间换空间，一份共享数据 互斥访问；内存省但 竞争大 时阻塞、上下文切换。
  • 选型：能 线程内隔离 就不要共享可变状态；必须共享则用锁、并发容器或消息传递。
  • 对比表：隔离性 TL 强、锁无；一致性共享数据要锁；TL 不解决 跨线程可见。
  • 场景：用户上下文 TL；账户余额共享必须用锁/DB 事务；TL 不能 替代对同一变量的并发写保护。
  • 追问：ThreadLocal 能替代锁吗？（仅当 无需跨线程共享 同一可变状态。）
  • 追问：虚拟线程海量 TL？（内存放大，考虑 ScopedValue 等，见 T86。）

6.9 并发工具与容器

T71. CompletableFuture 常用场景？

口述版： 异步编排：thenApply、thenCombine、allOf；比 Future.get 阻塞更灵活，配合自定义线程池。

具体介绍

  • 默认 ForkJoinPool.commonPool()，生产建议指定 Executor。
  • API：supplyAsync / thenApply / thenCompose（扁平化）/ allOf / anyOf；异常用 exceptionally / handle。
  • 线程池：CompletableFuture.supplyAsync(task, executor) 勿用 commonPool 跑阻塞 IO。
  • 追问：thenApply 与 thenCompose 区别？（apply 嵌套 Future；compose 扁平 一层 Future。）

T72. ForkJoinPool 工作窃取？

口述版： 分治任务，双端队列：空闲 worker 从别队 队尾偷 任务，提高 CPU 利用。

具体介绍

  • 工作窃取：每个 worker 有 双端队列 deque；自己从 头 取任务；空闲时从别的 worker 尾 偷任务，减少 CPU 空闲。
  • ForkJoinPool：分治递归（如归并排序、大数组 sum）拆成子任务 fork，本线程 join 结果。
  • 类：ForkJoinTask 分 RecursiveTask（有返回值）/RecursiveAction（无返回）。
  • commonPool：ForkJoinPool.commonPool() 默认并行度约 CPU-1；parallelStream 默认用它 —— 阻塞 IO 别放 commonPool。
  • 场景：CPU 密集、可递归拆分的大计算；不适合长阻塞 IO。
  • 追问：commonPool 并行度？（默认 CPU-1，可通过系统属性调整。）

T73. BlockingQueue 家族？

口述版： ArrayBlockingQueue 有界数组；LinkedBlockingQueue 链表；PriorityBlockingQueue 堆；DelayQueue 延迟；SynchronousQueue 零容量。

具体介绍

  • ArrayBlockingQueue：有界数组，一把锁；线程池 固定背压 常用。
  • LinkedBlockingQueue：链表，可选界，默认极大；注意 无界 OOM。
  • PriorityBlockingQueue：堆排序优先级；作一般池队列 不保证 FIFO 公平。
  • DelayQueue：Delayed 元素，内部 PriorityQueue + Leader-Follower 等待到期。
  • SynchronousQueue：零容量 handoff，CachedThreadPool 核心。
  • 场景：线程池选型 = 七参里的 queue 选型，直接决定 扩线程时机（T47）。
  • 追问：PriorityBlockingQueue 能作一般线程池队列吗？（可以但不保证 FIFO 公平。）

T74. ConcurrentHashMap 与线程池配合注意？

口述版： 共享缓存用 CHM，见模块一；迭代弱一致；size 用 mappingCount。

具体介绍

  • 共享缓存：多 worker 线程读写的 本地缓存 用 ConcurrentHashMap，见模块一；迭代 弱一致，size() 用 mappingCount()。
  • JDK8+ 结构：Node 数组 + CAS 空桶插入 + synchronized 锁桶 扩容/冲突；避免 Segment 分段（JDK7）。
  • 与线程池配合：computeIfAbsent 内 禁止 慢 RPC/锁外阻塞 —— 会堵整条桶甚至拖死池内其他任务。
  • 任务去重：同一 key 异步加载用 CHM 去重时，注意 异常缓存 与 过期策略（Caffeine 更合适复杂缓存）。
  • 场景：线程池 + CHM 做请求级 dedupe、结果缓存；高写热点 key 仍可能 锁单桶 竞争。
  • 追问：CHM 允许 null key/value 吗？（不允许，与 HashMap 不同。）
  • 追问：CHM 迭代能删吗？（Iterator.remove 支持；弱一致不抛 CME。）

T75. CopyOnWriteArrayList 适用？

口述版： 读极多写极少，写时复制数组，读无锁；写开销大，适合监听器列表。

具体介绍

  • COW 思路：读 无锁 遍历底层数组 快照；写时 复制整个数组 再替换 volatile 引用，写开销大。
  • 迭代安全：迭代器基于 创建时快照，不抛 ConcurrentModificationException，弱一致 可能看不到最新写。
  • 场景：监听器列表、黑白名单配置 读极多写极少；写频繁则 禁止 用 COW。
  • 实现：add/remove copy-on-write；读路径无 synchronized；写放大 O(n)。
  • 与线程池：注册/注销监听器若在请求路径，写少可读 COW；高频注册用 同步 List + 读锁 更合适。
  • 追问：迭代器 weakly consistent 含义？（可能看不到最新写，但不抛 CME。）
  • 追问：COW 能保证读到最新吗？（不保证 实时最新，保证快照自洽。）

6.10 死锁与排查

T76. 死锁四个条件？如何避免？

口述版： 互斥、占有且等待、不可抢占、循环等待。破坏其一：固定加锁顺序破循环；tryLock 超时破占有等待；一次性申请所有资源。

具体介绍

  • 四条件（Coffman）：互斥、占有且等待、不可抢占、循环等待 —— 四者同时成立 才死锁。
  • 破坏循环等待：全局锁顺序（按 objectId/hash 排序依次加锁）最常用。
  • 破坏占有且等待：tryLock(timeout) 失败则 释放已持有锁 并退避重试。
  • 互斥：锁的本质，通常 不破坏；一次性申请所有资源（银行家思路，少用）。
  • 线程池场景：池满 + 同池嵌套 submit + 外部锁顺序反转，可能 假死 类似死锁。
  • 场景：转账 A→B 与 B→A 若锁顺序不一致易死锁；统一按账户 ID 排序加锁。
  • 追问：数据库死锁与 Java 死锁排查异同？（DB 看 deadlock graph；Java 用 jstack。）

T77. 线上如何排查死锁？

口述版： jstack 看 Found one Java-level deadlock；或 VisualVM、Arthas thread -b；结合业务锁顺序。

具体介绍

  • jstack：jstack <pid> 搜 Found one Java-level deadlock，会打印 monitor 持有与等待链。
  • VisualVM / Arthas：thread -b 找阻塞；dashboard 看线程数与 CPU。
  • 多次采样：对比 BLOCKED 线程栈，区分 瞬时竞争 与 永久死锁。
  • 结合业务：锁 顺序、粒度、嵌套 与代码路径对照；核对 线程池队列满 是否参与。
  • 线上流程：先 jstack 是否 deadlock → 无则看 BLOCKED 等谁 → 查慢 SQL/连接池/锁持有时间。
  • 场景：发布后出现全站 BLOCKED，优先 jstack 是否 deadlock 而非先重启。
  • 追问：假死与死锁区别？（假死 无循环等待，可能是资源耗尽或慢依赖。）

T78. CPU 飙高如何查线程？

口述版： top -H pid 找线程 tid，printf %x 转 16 进制，jstack 搜 nid=0x…；看是否死循环、频繁 GC、锁自旋。

具体介绍

  • 步骤：top -Hp <pid> 看各线程 CPU → 取高 CPU 的 tid → printf '%x\n' tid 转 16 进制 → jstack <pid> 搜 nid=0x...。
  • Arthas：thread -n 3 直接列最忙线程栈，省手工换算。
  • 常见栈：死循环、灾难性正则、CHM 扩容热点、GC 线程 占用（配 jstat -gcutil）。
  • RUNNABLE 占满：可能是 纯计算、Native 代码，或 采样瞬间 都在跑；结合 perf/async-profiler。
  • 场景：单机 CPU 100% 接口超时，先定位 哪条线程栈热点 再改代码。
  • 追问：CPU 高但 jstack 全 RUNNABLE？（可能是 内核态、Native 或 采样瞬间 问题。）

T79. 连接池 BLOCKED 与线程池关系？

口述版： 业务线程在 getConnection 阻塞，jstack 大量 BLOCKED；可能是连接泄漏、慢 SQL、pool 过小或线程池过大争连接。

具体介绍

  • 现象：业务线程池很大，但 jstack 大量 BLOCKED 在 DruidDataSource.getConnection / Hikari getConnection。
  • 根因：连接泄漏（未 close）、慢 SQL、maxActive 过小、或 线程池过大 争少量连接。
  • 对齐：经验上 Tomcat maxThreads 与 maxActive 同级或连接略小，以 压测 为准（T61）。
  • 场景：200 线程 + 20 连接 → 180 线程等连接，RT 飙升误以为是「线程不够」。
  • 追问：连接池 maxActive 与 Tomcat maxThreads 怎么配？（经验：同级或连接略小，压测验证。）

T80. Linux / JDK 常用线程命令？

口述版： ps -eLf、top -H；jps、jstack、jconsole；kill 杀进程非首选。

具体介绍

  • Linux：ps -eLf | grep java 看线程数；top -H 按线程 CPU；perf top -p pid 热点。
  • JDK：jps 列进程；jstack 线程栈；jcmd <pid> Thread.print；jconsole 图形化线程 Tab。
  • 容器：docker exec 进容器需自带 JDK 工具或 arthas-boot.jar；pid 1 有时需 -1 指定 Java 进程。
  • 慎用：kill -9 不跑 shutdown hook，数据可能脏；优先 优雅下线。
  • 场景：K8s pod 内排查先 jcmd 是否可用，再决定拷 arthas。
  • 追问：kill -9 与 shutdown hook？（-9 不跑 hook，数据可能脏。）

6.11 虚拟线程（JDK 21+）

T81. 虚拟线程是什么？

口述版： JVM 调度的轻量线程（Project Loom），大量虚拟线程映射到少量平台线程（carrier），阻塞时 mount/unmount。

具体介绍

  • 虚拟线程：Project Loom，JVM 调度的 轻量用户态线程，大量虚拟线程映射到 少量平台线程（carrier）。
  • 阻塞行为：阻塞 IO 时 unmount，释放 carrier 给其他虚拟线程，提高 并发连接数 而不线性增加 OS 线程。
  • 实现：java.lang.VirtualThread + Continuation；调度常用 ForkJoinPool 作 carrier 池。
  • 适合：IO 密集、大量短任务；不适合 CPU 占满（T84）。
  • 场景：HTTP 网关每请求一虚拟线程，替代传统 maxThreads=500 平台线程模型。
  • 追问：虚拟线程是内核线程吗？（否，JVM 用户态调度，映射到少量 平台线程。）

T82. 虚拟线程与平台线程区别？

口述版： 创建成本低、数量可百万级；不要池化虚拟线程（用 newVirtualThreadPerTaskExecutor）；阻塞 IO 会 unmount 不占用 carrier。

具体介绍

  • 平台线程：1:1 映射 OS 线程，创建/栈成本高，数量 百级 常见上限思维。
  • 虚拟线程：创建极 cheap，百万级 可行；不要池化 虚拟线程，用 newVirtualThreadPerTaskExecutor 一任务一线程。
  • 阻塞 IO：虚拟线程在 socket read 等阻塞点 unmount，不占用 carrier 空等。
  • 错误做法：把虚拟线程塞进 固定大小平台线程池（限制 carrier 的是另一层）。
  • 场景：微服务同步阻塞风格代码 + 高并发，JDK21+ 可换虚拟线程降低内存与调度成本。
  • 追问：虚拟线程默认 daemon 吗？（与用户线程语义类似，非 daemon 会阻止 JVM 退出。）

T83. pinned 虚拟线程问题？

口述版： 在 synchronized 块内阻塞或某些 native 操作可能 pin 到 carrier，失去伸缩性；可改 ReentrantLock 或缩短 sync。

具体介绍

  • JEP 持续改进 pin 场景。
  • pin 原因：在 synchronized 块内阻塞、部分 Native/JNI、旧版 Object.wait 等可能 固定 carrier（JEP 444 持续减少 pin）。
  • 缓解：临界区改 ReentrantLock + 短持有；避免在 sync 里调 阻塞 IO（仍可能 pin，视 JDK 版本）。
  • 监控：JDK jfr 事件 jdk.VirtualThreadPinned（版本支持时）。
  • 追问：pin 和 platform thread 阻塞有何不同？（pin 时 carrier 被占满，其它虚拟线程饿死 carrier。）

T84. 虚拟线程适合 / 不适合什么？

口述版： 适合大量短生命周期 IO 任务（HTTP 网关、微服务调用）；不适合长时间 CPU 占满或大量 synchronized/native pin。

具体介绍

  • 适合：大量 短生命周期 IO —— HTTP、RPC、JDBC（驱动需 friendly）、文件 IO 阻塞型。
  • 不适合：长时间 CPU 占满、大量 synchronized 内阻塞（pin，T83）、海量 ThreadLocal 占内存。
  • 平台线程数：carrier 约 CPU 核数 即可，不必再套 IO 公式开几百平台线程。
  • 对比传统池：IO 多时用虚拟线程减 平台线程与栈内存；CPU 密集仍用有限并行度。
  • 迁移：同步风格代码收益大；已深度绑定平台线程池 + TL 需审计（T87）。
  • 场景：Tomcat 虚拟线程模式；CPU 加密服务仍用固定小池。
  • 追问：虚拟线程还需要 IO 公式开很多平台线程吗？（平台线程 ≈ 核数 作 carrier 即可。）

T85. Executors.newVirtualThreadPerTaskExecutor？

口述版： 每个任务一个虚拟线程，简单；结构化并发 StructuredTaskScope（JDK 21+ 预览/后续）做子任务生命周期管理。

具体介绍

  • Spring Boot 3.2+ 可选 virtual threads。
  • API：Executors.newVirtualThreadPerTaskExecutor() 返回 ExecutorService，每 task startVirtualThread。
  • StructuredTaskScope（预览）：子任务 树状取消、超时统一 shutdown（JDK 21+ 演进中）。
  • **Spring Boot 3.2+**：spring.threads.virtual.enabled=true 切换 Tomcat 虚拟线程处理请求。
  • 追问：虚拟线程 Executor 需要 shutdown 吗？（需要，ExecutorService 生命周期 仍要管理。）

T86. 虚拟线程与 ThreadLocal？

口述版： 仍支持 ThreadLocal，但海量线程下 TL 内存放大；优先 scoped value（JDK 预览）等替代传递上下文。

具体介绍

  • 仍支持 ThreadLocal：每虚拟线程可有 TL；但 百万虚拟线程 × 大对象 TL → 内存爆炸。
  • 线程池时代问题：worker 复用要 remove；每任务一新虚拟线程 仍要注意 任务结束 remove 防泄漏。
  • ScopedValue（预览）：不可变上下文传递，减少 remove 模式泄漏（JEP 446 等方向）。
  • 与 MDC/TTL：日志 traceId 在线程池/虚拟线程场景都要 传递或清理；优先 ScopedValue/TTL 设计。
  • 场景：traceId 传递优先 ScopedValue/TTL 设计；避免在虚拟线程里放大 static TL 大 Map。
  • 追问：TTL 在虚拟线程下还要吗？（若仍用平台池则否；每请求虚拟线程 仍要注意 TL 生命周期。）

T87. 从传统线程池迁移到虚拟线程注意点？

口述版： 连接池、DB 驱动仍有限；ThreadLocal/TTL 要审计；synchronized 热点改 Lock；压测对比 carrier 数与 pin。

具体介绍

  • 平台线程数 ≈ CPU 核数做 carrier 池即可。
  • 审计清单：连接池大小、JDBC 驱动 virtual-thread 说明、synchronized 热点、ThreadLocal/TTL、线程池改 Executor。
  • carrier 配置：-Djdk.virtualThreadScheduler.parallelism=N（默认约 CPU 核数）。
  • 压测：对比 pin 事件数、P99、carrier 利用率 vs 传统线程池。
  • 追问：现有 @Async 线程池怎么迁？（改为 虚拟线程 Executor 或 Spring 虚拟线程支持。）

延伸阅读： JMM 与内存区域见 J9、J9；并发 Map 见 ConcurrentHashMap。线程池 T45～T64 含原文 CPU/IO 公式与拒绝策略，建议与压测数据对照记忆。
