七、spring

格式说明：每题先 口述版（面试现场 30～60 秒），下方 具体介绍 便于复习展开。专题见 模拟核心原理 等系列。

7.1 IOC 与 Bean 身份

S1. Spring / IOC 容器解决什么问题？BeanFactory 与 ApplicationContext？

口述版： Spring 是 IOC 容器加生态，把对象创建、组装、生命周期交给容器。BeanFactory 是最小容器接口；ApplicationContext 是增强版，带事件、国际化、自动注册 BPP 等，业务几乎都用 ApplicationContext。

具体介绍

  • IOC：控制反转的是「谁 new 谁、谁组装依赖」。
  • BeanFactory：getBean、单例缓存等基础能力。
  • ApplicationContext：继承 BeanFactory，启动时预加载单例、支持 @Autowired 解析、发布事件。
  • 常见实现：AnnotationConfigApplicationContext、Boot 的 ServletWebServerApplicationContext。

面试追问

  • DI 与 IOC 谁先谁后？（IOC 是思想，DI 是常见实现手段）
  • ConfigurableApplicationContext 与 ApplicationContext？（答： 前者 extends 后者，增加 refresh/close、环境、事件发布等；开发中注入常用 ApplicationContext，需要生命周期控制时用 Configurable。）

常见坑

  • 手动 new 的对象不受容器管理，@Autowired 无效。

S2. BeanFactory vs FactoryBean？getObject 返回谁？

口述版： BeanFactory 是容器；FactoryBean 是工厂 Bean，getObject 才返回你要的业务对象。getBean(‘myFactory’) 拿的是 getObject 产物，getBean(‘&myFactory’) 才是 FactoryBean 本身。

具体介绍

  • FactoryBean<T>：getObject() 创建对象；isSingleton() 等。
  • 典型：MyBatis SqlSessionFactoryBean。
  • 容器里注册的 name 往往对应 产品 Bean，不是 FactoryBean 类实例。

面试追问

  • SmartFactoryBean 与 FactoryBean？（答： SmartFactoryBean 是 FactoryBean 子接口，多 isPrototype() 等语义；Spring 对 Smart 实现有特殊处理，一般了解 FactoryBean 即可。）
  • 为什么 getBean 默认拿产品？（答： 容器注册 FactoryBean 时，对外暴露的 beanName 指向 getObject() 产物，工厂本身用 &beanName 获取，避免业务代码直接依赖工厂类。）

常见坑

  • 把 FactoryBean 当普通 Bean 注入类型搞错。

S3. @Component 族与 @Autowired / @Resource？

口述版： @Component 及 Service/Repository/Controller 都是组件扫描；Autowired 默认按类型，多个实现靠 Qualifier 或 Primary；Resource 默认按名称。

具体介绍

  • @Service / @Repository / @Controller：语义分层，扫描机制相同。
  • @Autowired：required=false 可可选注入。
  • @Resource（JSR-250）：name 属性指定 beanName。

面试追问

  • @Autowired 构造器 vs 字段注入官方推荐？（构造器利于不可变、测试）
  • 同一类型两个 Bean 不标 Qualifier 会怎样？（答： 启动或注入时抛 NoUniqueBeanDefinitionException；需 @Qualifier、**@Primary** 或 @Autowired List<接口> 收集全部。）

常见坑

  • 字段注入导致类难以单测；循环依赖时构造器注入失败。

S4. XML、Java Config、@Configuration？

口述版： 三种配 Bean：XML、@Configuration 里 @Bean、组件扫描。Configuration 类会被 CGLIB 增强成 Full 模式，保证 @Bean 方法单例互调仍是容器里同一个 Bean。

具体介绍

  • Lite vs Full：Full 模式 @Configuration 代理 @Bean 方法。
  • @ComponentScan 指定包路径。
  • Boot 以 注解 + 自动配置 为主。

面试追问

  • @Bean 方法 @Scope("prototype") 每次调用 new 吗？（答： Full @Configuration 下 @Bean 方法被 CGLIB 拦截，prototype 仍由容器按 scope 管理——每次 getBean 新实例；若 Lite 模式直接调 @Bean 方法则每次执行方法体。）
  • @Import 与 @ComponentScan 区别？（答： Import 显式导入 @Configuration/类/ImportSelector；ComponentScan 按包路径扫描带 @Component 的类。Import 更精确，Scan 适合包级批量。）

常见坑

  • 两个 @Configuration 互相 @Import 循环；Lite 模式 @Bean 互调得到 新实例。

S5. Scope：singleton / prototype？

口述版： singleton 容器里一份，默认；prototype 每次 getBean 新实例。singleton 才支持三级缓存解循环依赖，prototype 不行。

具体介绍

  • request/session：Web 作用域依赖 Web 容器。
  • prototype 不随容器 destroy 统一销毁（需自行管理）。

面试追问

  • singleton Bean 注入 prototype 字段为何总是同一个 prototype？（需 ObjectFactory / @Lookup）
  • request scope 在非 Web 环境？（答： 需要 Web 应用上下文（如 WebApplicationContext）；纯 AnnotationConfigApplicationContext 无 request 生命周期，会报错或无法使用。）

常见坑

  • prototype 当成员变量注入 singleton，生命周期错配。

S6. BeanDefinition 是什么？

口述版： BeanDefinition 是 Bean 的图纸：类名、scope、依赖、init/destroy 方法等。容器先注册 BD，再按 BD 创建实例。

具体介绍

  • 来源：XML、@Bean、@Component 扫描解析。
  • BFPP 可在实例化前改 BD（如改 beanClass、属性）。

源码/参数

  • RootBeanDefinition / GenericBeanDefinition；beanClass、scope、lazyInit。
  • refresh() 里 invokeBeanFactoryPostProcessors 在实例化前。

面试追问

  • BD 与 Bean 是一对一吗？（factory method 可动态 class）

7.2 Bean 的初始化过程

S7. Bean 的初始化过程（总题）

口述版： 从 getBean 触发 createBean：实例化、属性填充、initializeBean（Aware、BPP 前后、init 方法），最后得到可用 Bean，可能是 AOP 代理。对照初始化过程图从前往后讲。

具体介绍

主路径：getBean → doGetBean → createBean → doCreateBean。

  • 实例化：反射或工厂方法得到原始对象。
  • 属性填充：populateBean 注入依赖。
  • 初始化：initializeBean（Aware、BPP、init 回调）。

详见 initializeBean()。

源码/参数

  • 核心类：AbstractAutowireCapableBeanFactory#createBean → doCreateBean。
  • earlySingletonExposure 在 populate 前决定是否暴露三级缓存。

面试追问

  • getBean 与 @Autowired 注入最终都走同一创建链吗？（是）

常见坑

  • 认为「初始化 = 实例化」——实例化后还有一大段 initialize。

S8. 初始化中的属性填充 populateBean？

口述版： populateBean 在实例化之后，给 @Autowired/@Value 等字段和方法注入赋值，循环依赖的 setter 注入也发生在此阶段前后配合早期引用。

具体介绍

  • InstantiationAwareBeanPostProcessor.postProcessProperties 可干预注入。
  • 构造器注入在实例化阶段，无法再「先半成品后填依赖」解循环。

面试追问

  • @Autowired 在 populate 哪个子步骤解析？（答： 在 populateBean 内，由 AutowiredAnnotationBeanPostProcessor 等在 postProcessProperties / 注入阶段解析字段与方法参数。）
  • 循环 A→B→A 时 A 实例化后谁先进入三级缓存？（答： 先创建的那个 Bean（如 A） 在实例化后、populate 前，将其 ObjectFactory 放入 singletonFactories（三级）。）

常见坑

  • 在构造器里调用另一个 Bean 的方法，对方可能尚未 populate 完成。

S9. initializeBean 内各步骤？

口述版： 先 invokeAwareMethods，再 BPP beforeInit，再 @PostConstruct/afterPropertiesSet/init-method，再 BPP afterInit，AOP 代理多在 afterInit 产生。

具体介绍

  • applyBeanPostProcessorsBeforeInitialization
  • invokeInitMethods（含 @PostConstruct）
  • applyBeanPostProcessorsAfterInitialization ← AOP 常见织入点

源码/参数

  • 见 DefaultSingletonBeanRegistry 与 AbstractAutowireCapableBeanFactory#initializeBean。

面试追问

  • AOP 代理一定在 afterInit 吗？（循环依赖时可能 early 代理）

常见坑

  • 在 beforeInit 里使用尚未 init 完的依赖 Bean。

S10. 初始化阶段与循环依赖早期引用？

口述版： singleton setter 循环时，实例化后先 put 三级缓存 ObjectFactory，再 populate；对方 getBean 可从工厂拿早期引用，填完后再进 initializeBean。

具体介绍

  • 早期引用 尚未 走完 BPP afterInit，故需要 singletonFactory 延迟决定是否代理。

面试追问

  • 只有 singleton 且 setter/field 注入才走三级缓存？（答： 是。 构造器注入在实例化阶段无法暴露半成品；prototype 每次新建，无法复用 early 引用语义。）
  • 二级缓存何时有值、何时删三级？（答： 从三级 ObjectFactory.getObject() 得到 early 引用后放入 二级；通常 移除三级 中对应 factory。成品进 一级 后二三级该 name 一般清空。）

常见坑

  • 误以为 early 引用等于最终代理——可能后续还会变。

7.3 Bean 的生命周期

S11. Bean 的生命周期（总题）

口述版： 生命周期指从容器创建 Bean、使用到容器关闭销毁的完整过程：创建链（实例化→初始化）→ 业务使用 → 销毁回调。对照生命周期图讲创建与销毁两半截。

具体介绍

  • 创建阶段：见 S7～S12。
  • 销毁阶段：单例在容器 close() 时统一销毁。

面试追问

  • 生命周期与初始化过程图的关系？（初始化是生命周期创建段的核心）
  • Bean 何时「可用」？（afterInit 返回后注册到一级）

常见坑

  • 在 @PostConstruct 里 publish 事件，监听者可能读到未完全就绪的依赖。

S12. 生命周期全流程：实例化→…→销毁

口述版： 背一条链：实例化、属性填充、Aware、BPP 前置、三种 init、BPP 后置、使用、PreDestroy/destroy。

具体介绍

面试追问

  • 哪一步之后 Bean 可能被替换为代理引用？（答： 正常在 BPP postProcessAfterInitialization 返回代理；循环依赖时可能在 getEarlyBeanReference 提前得到 early 代理。）
  • destroy 与 JVM finalize 区别？（答： destroy 是 Spring 容器回调（@PreDestroy 等），时机可控；finalize 是 GC 回收前 JVM 调用，不可靠且已废弃，不能替代资源释放。）

常见坑

  • 跳过 Aware 直接依赖 ApplicationContext 静态持有——内存泄漏。

S13. 实例化 createBeanInstance？

口述版： 根据 BD 选构造器或工厂方法创建对象；构造器循环依赖在此阶段无法暴露「未完成构造的对象」给另一方。

具体介绍

  • @Autowired 构造器在实例化时解析。
  • 工厂方法 @Bean 则调用 @Configuration 代理方法。

面试追问

  • @Autowired 多构造器如何选？（优先参数多的或 @Autowired 构造器）
  • Kotlin 类默认单构造器自动注入？（答： 是；Kotlin 单主构造器等价于 Java 的 单 @Autowired 构造器，Spring/Kotlin 插件支持构造器注入。）

常见坑

  • 构造器循环依赖：Spring 直接 BeanCurrentlyInCreationException。

S14. Aware 接口族？

口述版： Aware 让 Bean 拿到容器基础设施：BeanName、BeanFactory、ApplicationContext 等，在 initializeBean 里 invokeAwareMethods 统一回调。

具体介绍

  • 顺序在 BPP beforeInit 之前。
  • 业务代码慎用 Aware，优先注入具体依赖。

面试追问

  • ApplicationContextAware 拿到上下文后可以做哪些事？（发布事件、查 Bean）
  • 为什么说不推荐业务实现过多 Aware？（答： 强耦合容器 API，难测试、难迁移；应优先 构造器注入 所需依赖，而非从上下文「掏」Bean。）

常见坑

  • Aware 里 getBean 触发过早初始化，打乱启动顺序。

S15. BeanFactoryPostProcessor vs BeanPostProcessor？

口述版： BFPP 改 BeanDefinition，在 Bean 实例化之前；BPP 改 Bean 实例，在实例化之后每个 Bean 都会走。

具体介绍

对比 BeanFactoryPostProcessor BeanPostProcessor
操作对象 BeanDefinition Bean 实例
时机 refresh 早期，实例化前 每个 bean 初始化前后
典型 占位符配置、MapperScanner Autowired 解析、AOP 代理创建

面试追问

  • BeanPostProcessor 能返回 null 吗？（可短路后续 BPP）
  • InstantiationAwareBeanPostProcessor 属于 BPP 子接口，还能拦截实例化前。（答： 是。 可在 实例化前/后 干预（如 postProcessBeforeInstantiation 直接返回代理短路创建）。）

常见坑

  • 自定义 BPP 未注册到容器（需 @Bean 或 spring.factories）。

S16. @PostConstruct 执行时机？

口述版： 在 populate 之后、BPP afterInit 之前，作为 invokeInitMethods 一部分执行；顺序上在 BPP beforeInit 之后。

具体介绍

  • 常见顺序：BPP before → @PostConstruct → afterPropertiesSet → init-method（具体以 InitDestroyAnnotationBeanPostProcessor 为准）→ BPP after。
  • 不要在 @PostConstruct 里做依赖其他 Bean 尚未 init 完的重活。

源码/参数

  • InitDestroyAnnotationBeanPostProcessor 处理 @PostConstruct / @PreDestroy。
  • CommonAnnotationBeanPostProcessor（JDK 9+ 模块变化需留意）。

常见坑

  • 同一方法既 @PostConstruct 又 implements InitializingBean 重复执行 init 逻辑。

S17. 销毁回调顺序？

口述版： 容器关闭时调 destroy：@PreDestroy、DisposableBean、destroy-method，prototype 默认不托管销毁。

具体介绍

  • 单例 destroy 与 JVM 退出顺序：先 Spring 容器 shutdown。

面试追问

  • prototype 谁负责 destroy？（答： 容器不托管 prototype 销毁；若实现了 destroy 回调，需业务自己 getBean 后手动调或自定义逻辑，容器 close 不会统一 destroy prototype。）
  • 注册 shutdown hook 在 Boot 里默认有吗？（答： 默认会 注册 JVM shutdown hook，在进程退出时触发 context.close()，除非 SpringApplication.setRegisterShutdownHook(false)。）

常见坑

  • 非 Spring 管理的线程池在 destroy 未关闭。

S18. singleton 容器关闭销毁？

口述版： registerShutdownHook 或 close() 触发 DisposableBean 销毁；释放资源、关连接池等。

具体介绍

  • Boot 内嵌容器停止时同样走 Spring 生命周期结束。

面试追问

  • context.close() 与 registerShutdownHook？（答： close 主动关闭容器、触发 destroy；registerShutdownHook 在 JVM 退出时自动 close，二者配合保证优雅停机。）
  • 销毁顺序与依赖关系是否相反？（答： 大致是 依赖方先销毁、被依赖方后销毁（与创建顺序相关），但不保证严格逆拓扑，以 DisposableBean 注册顺序为准。）

常见坑

  • kill -9 跳过 destroy，连接未释放。

7.4 循环依赖与三级缓存

S19. 什么是循环依赖？哪些不解决？

口述版： A 依赖 B、B 依赖 A 成环。单例 setter 可解；构造器注入、prototype 循环无法解。

具体介绍

  • 构造器：实例未建完无法注入。
  • prototype：每次新实例，无法缓存早期引用，会 OOM 风险。

面试追问

  • 双向依赖 vs 更长环 A→B→C→A 同样可解（singleton setter）？（答： 是；只要环上都是 单例 + setter/field 注入，三级缓存对环上每个节点同样适用，与环长度无关。）
  • 用 @DependsOn 会加剧还是缓解循环？（答： 可能加剧 启动失败：DependsOn 强制创建顺序，环上无法满足先后；解循环靠 setter 三级缓存或改设计，不靠 DependsOn。）

常见坑

  • 把 prototype 当 singleton 成员，每次 get 新实例导致「伪循环」排查困难。

S20. 三级缓存各自放什么？

口述版： 一级 singletonObjects 成品；二级 earlySingletonObjects 早期引用；三级 singletonFactories 是 ObjectFactory，不是 Bean 本身。

具体介绍

缓存 内容
一级 singletonObjects 完全初始化好的 成品 Bean（可能是代理）
二级 earlySingletonObjects 早期引用（半成品或已 early 代理）
三级 singletonFactories ObjectFactory λ，调用才 getEarlyBeanReference

源码/参数

面试追问

  • 二级有值时三级对应 key 是否删除？（通常 get 后删 factory）
  • 一级与二级互斥吗？（成品进一级后不再 early）

常见坑

  • 背错「二级是工厂」——三级才是 Factory。

S21. 完整工厂 vs 早期引用？

口述版： 三级存工厂，getBean 发现循环时才 getObject，此时可决定要不要提前做 AOP 包装；二级直接放对象则少了这层延迟。

具体介绍

  • getEarlyBeanReference 可能返回 早期代理。
  • 与 最终一级缓存 中对象类型一致性问题：面试答「工厂延迟决定代理」。

面试追问

  • AbstractAutoProxyCreator#getEarlyBeanReference 做什么？（答： 在循环依赖暴露 early 引用时，判断是否需要 提前创建 AOP 代理，若需要则返回代理对象，否则返回原实例。）
  • early 引用与 postProcessAfterInitialization 返回的代理是否同一对象？（答： 通常应是同一最终对外引用；early 若已代理，完整 init 后一般不再重复包装，避免双层代理（具体以实现类为准）。）

常见坑

  • 认为二级放 always 代理——可能是目标或 early 代理，取决于 factory。

S22. 为什么需要第三级？二级为何不行？

口述版： 若二级直接放早期代理，会跳过正常 BPP 链，破坏生命周期；三级工厂延迟到需要时才 early 引用，并配合后续完整初始化。

具体介绍

  • AOP 默认 afterInit 才代理；循环依赖要提前暴露，用 factory 在 getEarlyBeanReference 统一处理。
  • 二级只有 early 引用、无 factory → 无法兼顾「循环」与「正常代理时机」。

面试追问

  • 若只用二级 earlySingletonObjects 存半成品，AOP 何时织入？（答： 若二级只存 裸实例，则要等到正常 afterInit 才代理——但循环依赖时 B 拿到的 A 是裸对象，后续 A 变代理会导致 不一致；故需三级 factory 延迟决定。）
  • 为何说「提前固定代理破坏生命周期」？（答： 代理应在 完整 BPP 链 后生成；若在 populate 前就把二级固定为 early 代理，会 跳过 部分 beforeInit/初始化逻辑，导致与正常 Bean 生命周期不一致。）

常见坑

  • 面试只答「三级为了 AOP」——要补 ObjectFactory 延迟决策。

S23. 构造器注入 / prototype 为何无法解决？

口述版： 构造器阶段对方 Bean 还不存在；prototype 无法复用单例三级缓存语义。

具体介绍

见 三级缓存&循环依赖。

面试追问

  • 构造器注入循环 A(B b), B(A a) 报错阶段？（答： 实例化阶段：创建 A 要 B、创建 B 要 A，任一无法完成构造，抛 BeanCurrentlyInCreationException 或类似循环创建异常。）
  • 多例 + @Autowired 单例依赖是否安全？（单例只创建一次）

常见坑

  • 用 @Lazy 构造器参数掩盖设计问题，调试时仍难追踪。

S24. @Lazy 打破循环原理？

口述版： Lazy 注入代理或延迟 getBean，打破环上同步初始化；等真正调用时再初始化目标。

具体介绍

  • @Lazy on 字段/构造参数：注入 Lazy 代理。
  • 设计层仍建议减少循环依赖。

源码/参数

  • @Lazy 注入 LazyInitializationProxy（JDK 代理或 CGLIB）。

面试追问

  • @Lazy 在循环依赖环的哪一环打断？（答： 加在 被注入的一端（如 @Lazy B b）：先注入 Lazy 代理，延迟 真正创建 B，打破同步建链，等 A 完成后再 init B。）
  • @Lazy + @Transactional 同时用注意什么？（答： Lazy 代理首次调用才初始化；若首次调用 非 public 或 自调用，事务/AOP 仍可能失效；且调试栈更深。）

常见坑

  • Lazy 代理首次调用才 init，首次失败表现为运行时异常而非启动失败。

S25. 一级缓存最终存谁？

口述版： 初始化完成后放入一级的是 最终对外 Bean，若 AOP 生效则一般是 代理对象（与 getBean 一致）。

具体介绍

  • 早期三级暴露 ≠ 一级最终形态；完整 init 后才进一级。

面试追问

  • getBean 拿到的是一级里的引用吗？（答： singleton 完全初始化后 从 singletonObjects（一级） 返回；若仍在创建中，可能走 early 路径，最终一致进一级。）
  • 两个 getBean 同一 name 同一对象吗？（singleton 是）

常见坑

  • 比较 == 原始 Bean 与代理 Bean——应比业务语义或接口类型。

7.5 AOP 与代理

S26. JDK 动态代理 vs CGLIB？

口述版： 有接口默认 JDK 动态代理；无接口或强制 CGLIB 子类代理。final 类/方法无法 CGLIB 覆盖，AOP 不生效。

具体介绍

  • JDK：基于接口 InvocationHandler。
  • CGLIB：子类 + MethodInterceptor。
  • spring.aop.proxy-target-class=true 倾向 CGLIB。

面试追问

  • 目标类有接口但强制 CGLIB：proxyTargetClass=true？（答： 设置 spring.aop.proxy-target-class=true 或 @EnableAspectJAutoProxy(proxyTargetClass=true)，强制 CGLIB 子类代理，即使存在接口。）
  • @Transactional 在 private 方法为何无效？（含 final 同类）

常见坑

  • 类无接口且非 public 类无法 CGLIB 代理。

S27. 代理对象创建时机？

口述版： 默认在 Initialization 的 BPP postProcessAfterInitialization；之前是目标对象，之后对外是代理（若需要）。

具体介绍

  • 与循环依赖：early 可能经 getEarlyBeanReference 提前 代理。
  • 见系列 Aop 两种实现。

面试追问

  • AnnotationAwareAspectJAutoProxyCreator 注册在哪个 BPP？（答： 它是 BeanPostProcessor（且继承 AbstractAutoProxyCreator），在容器 refresh 时注册，在 afterInit（及 early 路径）创建代理。）
  • 循环依赖 early 代理与正常 afterInit 代理会重复包装吗？（答： 设计上避免重复；若 early 已返回代理，afterInit 通常识别并返回同一代理，不再包一层。）

常见坑

  • 以为 Bean 创建完才需要代理——循环场景必须 early。

S28. Spring AOP 两种实现思路？

口述版： AspectJ 注解 + 运行时通过代理织入；多重切面可层层代理（洋葱模型）。

具体介绍

  • 开发可先理解 Advisor 链 与 Interceptor 调用顺序。

面试追问

  • 多个 @Aspect 如何叠加代理层？（答： 多个 Advisor 按 @Order 排序，代理调用链 洋葱模型 逐层 invoke；可理解为多层 MethodInterceptor。）
  • @EnableAspectJAutoProxy 做了什么？（答： @Import(AspectJAutoProxyRegistrar.class)，向容器注册 AnnotationAwareAspectJAutoProxyCreator 等，启用基于 @Aspect 的自动代理。）

常见坑

  • 把 Spring AOP 说成能织入 private static——不能。

S29. 切面执行顺序？Spring 4 vs 5？

口述版： 同类型通知看 @Order；不同切面 Order 小者优先。Spring 4/5 在 AutoProxyCreator 注册顺序 等与事务 Advisor 叠加顺序有差异，以版本文档为准，面试能说「事务与切面都是 Advisor，顺序影响谁先包谁」。

具体介绍

  • 原文：spring4 和 spring5 是不一样的。
  • @Order on Aspect 类。

面试追问

  • 同一 Aspect 内 @Before @After 顺序？（答： @Before 按 Order 升序 先执行；**@After** / @AfterReturning 在目标方法后，**@After** 类似 finally 语义；同类型通知看 @Order 值。）
  • @Order(Ordered.HIGHEST_PRECEDENCE) 事务与切面谁在外层？（答： Order 值越小优先级越高；谁在外层取决于 TransactionInterceptor 与 AspectJ Advisor 的 Order 注册顺序，Spring 4/5 默认顺序不同，以实测/版本为准。）

常见坑

  • 升级 Spring 4→5 后切面顺序变化导致「事务失效」假象——其实是顺序变了。

S30. AOP 失效场景？

口述版： 同类内部 this 调用绕过代理；对象非 Spring 管理；public 方法以外（protected 等）默认不织入。

具体介绍

  • 必须通过代理入口 调用。

面试追问

  • 从 AopContext 取代理的条件？（exposeProxy=true）
  • 外部类调用 public 方法一定走代理吗？（调用方经容器注入则走）

常见坑

  • 同类 this.foo() 调 @Transactional 的 bar()——经典失效。

S31. AOP 失效与 @Transactional 失效（同一入口）？

口述版： 事务也是 AOP；自调用、非 public、this 调用导致 既无事务也无切面。

具体介绍

  • 解决：AopContext.currentProxy()、拆类、@Lazy self inject（慎用）。

面试追问

  • 拆类 @Service + @Transactional 到独立类是否最佳实践？（答： 推荐：业务类 + 独立 Facade/Service 调事务方法，避免 自调用；比 exposeProxy 更清晰。）
  • 自注入 self 的风险？（答： 掩盖设计问题、易 循环依赖、测试困难；仅作过渡方案，长期应拆类。）

常见坑

  • enableExposeProxy 忘记开，currentProxy() NPE。

S32. AspectJ vs Spring AOP？

口述版： AspectJ 可编译期/加载期织入；Spring AOP 仅 Spring Bean 方法 运行时代理，功能子集。

具体介绍

  • 复杂切点用 AspectJ；业务事务/日志 Spring AOP 够用。

面试追问

  • @within / @annotation 切点 Spring AOP 是否全支持？（答： 支持 常见 AspectJ 注解切点（方法级 @annotation、类级 @within 等），但 不能 切 private、不能切非 Spring Bean。）
  • load-time weaving 需要 -javaagent？（答： AspectJ LTW 需要 -javaagent:aspectjweaver.jar 与 aop.xml；与 Spring 运行时代理是两套机制。）

常见坑

  • 用 AspectJ 语法写切点但只用 Spring AOP，部分切点不生效。

7.6 Spring 事务的传播机制

S33. Spring 事务的传播机制（总题）

口述版： 传播行为定义方法加入现有事务还是新建。七种 PROPAGATION，重点 REQUIRED、REQUIRES_NEW、NESTED，其余了解即可。

具体介绍

  1. PROPAGATION_REQUIRED：支持当前事务，没有则新建。
  2. PROPAGATION_SUPPORTS：有则加入，没有则以非事务执行。
  3. PROPAGATION_MANDATORY：必须在事务内，否则异常。
  4. PROPAGATION_REQUIRES_NEW：新建事务，挂起当前。
  5. PROPAGATION_NOT_SUPPORTED：非事务执行，存在则挂起当前。
  6. PROPAGATION_NEVER：非事务，存在事务则异常。
  7. PROPAGATION_NESTED：有事务则嵌套（savepoint），没有则同 REQUIRED。

（与原文 TransactionDefinition.PROPAGATION_* 一致。）

三种传播对比（重点）

传播 事务边界 挂起外层 内层 rollback 对外层
REQUIRED Join 或新建 否 全 rollback
REQUIRES_NEW 总是新建 是 互不影响
NESTED savepoint 嵌套 否 仅滚到 savepoint

面试追问

  • 传播行为绑定在 @Transactional 方法还是类？（答： 均可；类上注解作用于 public 方法，方法级 覆盖 类级；实际生效靠 方法拦截。）
  • 同类不同方法不同 propagation 如何表现？（答： 必须通过 代理调用 进入各方法；自调用 不生效。外层方法开事务，内层 REQUIRES_NEW 需调 另一个 Bean 或代理入口。）

常见坑

  • 默认 REQUIRED 以为「只读不会开事务」——仍会 join/create。

S34. REQUIRED 挂起点？

口述版： 有事务就加入同一个物理事务；没有就 begin。挂起点：外层方法进入时若新建事务，则内层 REQUIRED 都在同一事务边界内。

具体介绍

  • 默认传播行为。
  • 回滚：同一 connection，一处 rollback 全 rollback。

面试追问

  • 外层 REQUIRED、内层 REQUIRED 几个物理连接？（通常 1）
  • 内层 rollback 外层是否 rollback？（是）

常见坑

  • 只读 @Transactional(readOnly=true) 仍可能 join 写事务。

S35. REQUIRES_NEW 与挂起？

口述版： 总是新开事务，把当前事务 suspend 到一边；内层 commit/rollback 不影响 外层已挂起事务（外层恢复后继续）。

具体介绍

  • 场景：日志、审计必须落库，即使外层回滚。
  • 注意连接池占用两份连接。

面试追问

  • suspend/resume 在 JDBC 上如何体现？（Connection 绑定 ThreadLocal）
  • 内层 REQUIRES_NEW commit 后外层 rollback，内层数据还在吗？（在）

常见坑

  • REQUIRES_NEW 滥用导致连接池耗尽。

S36. NESTED 与 REQUIRES_NEW 区别？

口述版： NESTED 在外层事务里用 savepoint 嵌套；内层 rollback 只滚到 savepoint，外层可继续。REQUIRES_NEW 是独立事务，与外层完全分离。

具体介绍

  • 无外层事务时 NESTED 表现类似 REQUIRED。
  • 部分驱动/容器对 nested 支持有限，生产常 REQUIRED + 编程式拆分。

面试追问

  • MySQL InnoDB 对 savepoint 支持？（答： 支持 SAVEPOINT；Spring NESTED 依赖底层 JDBC savepoint，InnoDB 可用；MyISAM 等不支持事务则 NESTED 无意义。）
  • NESTED 内层 rollback 外层继续，savepoint 谁创建？（答： Spring TransactionManager 在进入 NESTED 方法时 创建 savepoint；内层 rollback 滚到该点，外层事务继续。）

常见坑

  • 把 NESTED 当成 REQUIRES_NEW——回滚语义完全不同。

S37. SUPPORTS / MANDATORY / NOT_SUPPORTED / NEVER？

口述版： 了解即可：SUPPORTS 随有无事务；MANDATORY 强制有事务；NOT_SUPPORTED 强制无；NEVER 禁止在事务中调用。

具体介绍

  • 只读查询偶用 SUPPORTS；MANDATORY 用于必须被事务方法调用的子方法。

面试追问

  • NEVER 在已有事务方法里被调用会怎样？（答： 抛 IllegalTransactionStateException（或类似），因为当前存在事务却要求 禁止 事务。）
  • NOT_SUPPORTED 只读查询为何有时故意挂起事务？（答： 避免只读操作 加入长事务 占连接、或与写事务锁冲突；挂起后无事务读，需注意 脏读 取决于是否另有读策略。）

常见坑

  • MANDATORY 用于 service 内部方法，被非事务 Controller 直接调就炸。

S38. 隔离级别与三问题？

口述版： 默认常为 READ_COMMITTED（视 DB）；脏读、不可重复读、幻读与隔离级别对应。

具体介绍

  • @Transactional(isolation=...) 可指定。

面试追问

  • @Transactional(isolation=READ_UNCOMMITTED) 生产会用吗？（答： 极少；脏读风险大。MySQL InnoDB 默认 RR，设 RU 往往仍受引擎行为限制，生产多用 READ_COMMITTED 或默认。）
  • 幻读与 MVCC 在 MySQL 默认 RR 下表现？（答： InnoDB RR + next-key lock 多数场景 避免幻读；快照读靠 MVCC，当前读靠间隙锁，面试答「RR 下 InnoDB 通过 MVCC+锁减少幻读」。）

常见坑

  • 以为 Spring 隔离级别能超越 DB 实际能力。

S39. 事务失效八大场景？

口述版： 自调用、非 public、catch 吞异常、rollbackFor 默认只滚 RuntimeException 和 Error、多线程、传播设错、引擎不支持、final 方法 CGLIB 无法增强。

具体介绍

  1. 自调用 / this 调用（无代理）
  2. 方法非 public
  3. 异常被 catch 未抛出
  4. rollbackFor 默认：RuntimeException 与 Error（检查异常默认不回滚）
  5. 多线程 新线程无 ThreadLocal 事务上下文
  6. 传播行为 设置错误
  7. 数据库引擎 不支持（如 MyISAM）
  8. final 方法（无法被 CGLIB 覆盖，事务切面进不去）

面试追问

  • @Transactional(rollbackFor=Exception.class) 何时必加？（答： 业务抛 checked Exception 且需要回滚时 必加；默认只回滚 RuntimeException 和 Error。）
  • 多线程 @Async 里调 @Transactional 方法事务在哪？（答： 新线程无 原 ThreadLocal 事务上下文；@Transactional 在新线程 无效 除非经 代理 重新开启事务（如 REQUIRES_NEW + 独立 Bean 调用）。）

常见坑

  • catch Exception 打日志不 rethrow——事务不回滚。

S40. rollbackFor 与检查异常？

口述版： checked Exception 默认不回滚，需 rollbackFor=Exception.class 或抛 RuntimeException。

具体介绍

  • noRollbackFor 排除某异常。

面试追问

  • rollbackForClassName 与 class 数组？（答： rollbackForClassName 用 全限定类名字符串 指定回滚异常；rollbackFor 用 **Class[]**，类型安全，推荐后者。）
  • 业务自定义 Checked Exception 默认提交事务？（答： 默认 commit（不回滚），除非 rollbackFor 包含该异常或异常包装为 RuntimeException 抛出。）

常见坑

  • 只写 rollbackFor 不写 noRollbackFor 误伤业务异常。

S41. 声明式 vs TransactionTemplate？

口述版： 声明式 @Transactional 简洁；编程式 Template 精确控制边界。

具体介绍

  • 同类测试常用 Template。

面试追问

  • TransactionTemplate.execute 与声明式选型？（答： Template 适合 小范围、编程式 边界清晰；声明式 适合业务方法级横切；同类内 Template 仍可在当前线程绑事务。）
  • 编程式在同类内是否绕过代理问题？（仍要拿到代理或拆类）

常见坑

  • Template 忘记在 callback 里抛异常，事务仍 commit。

S42. 多数据源与 @Async？

口述版： 指定 transactionManager；@Async 另线程需 @Transactional(propagation=REQUIRES_NEW) 或 TransactionSynchronization 传递策略。

具体介绍

  • 异步默认 无 事务。

面试追问

  • @Transactional("txManager2") 多数据源路由？（答： 指定 PlatformTransactionManager beanName，配合 多 DataSource 配置，使该方法事务绑定 对应数据源/库。）
  • 分布式事务 Seata 与 @Transactional 关系？（答： 本地 @Transactional 只管 单库；Seata @GlobalTransactional 协调多资源，是 另一层，需 Seata 代理 DataSource。）

常见坑

  • 主从库只读从库加 @Transactional 仍可能写到主库——路由在 DataSource 层。

7.7 Spring Boot

S43. @SpringBootApplication 拆解？

口述版： 等于 @Configuration + @EnableAutoConfiguration + @ComponentScan，Boot 应用入口复合注解。

面试追问

S45. 自定义 Starter 步骤？

口述版： autoconfigure 模块写 *AutoConfiguration + *Properties，注册 imports/factories；starter 模块只聚合依赖。

具体介绍

  1. xxx-autoconfigure
  2. @ConfigurationProperties

  4. xxx-spring-boot-starter 空壳依赖 autoconfigure

面试追问

常见坑

S46. SpringApplication.run 流程？

口述版： 推断 Web/普通应用类型 → 准备 Environment → 打印 Banner → createApplicationContext → refresh（IOC）→ 内嵌 Tomcat start → 调 Runner。

具体介绍

  • refresh 即 Spring 容器加载 Bean。
  • ApplicationRunner / CommandLineRunner 在容器就绪后。

源码/参数

  • SpringApplicationRunListeners：environmentPrepared、contextPrepared、started、ready。

面试追问

  • ApplicationContextInitializer 与 EnvironmentPostProcessor 谁先？（答： EnvironmentPostProcessor 更早，在 Environment 准备阶段 改配置；ApplicationContextInitializer 在 context 创建后、refresh 前 回调。）
  • 内嵌 Tomcat 在哪个 listener 阶段 start？（答： 一般在 contextRefreshed / WebServerInitializedEvent 前后，ServletWebServerApplicationContext 在 refresh 末尾 启动嵌入式 WebServer。）

常见坑

  • 在 main 里手动 new 数据源却期望 Boot 自动配——未进自动配置链。

S47. refresh 与经典 Spring？

口述版： Boot 仍走 AbstractApplicationContext.refresh() 12 步，只是之前 AutoConfiguration 已注册 BD。

具体介绍

  • 手动 Spring 项目同样 refresh。

面试追问

  • refresh 12 步里哪步实例化非懒加载单例？（答： finishBeanFactoryInitialization 阶段 preInstantiateSingletons，实例化所有非 lazy 单例。）
  • finishRefresh 发布 ContextRefreshedEvent？（答： 是，在 refresh 最后 finishRefresh 中发布 ContextRefreshedEvent，表示容器就绪（可重复 refresh 需注意）。）

常见坑

  • 在 BFPP 里 getBean 触发过早初始化循环。

S48. 常用 @ConditionalOn*？

口述版： OnClass 有类才配；OnMissingBean 无 Bean 才配；OnProperty 配置开关。

具体介绍

  • 自动配置互斥靠 MissingBean。

面试追问

  • @ConditionalOnWebApplication 区分 Servlet/Reactive？（答： 可指定 type=SERVLET / REACTIVE / ANY，分别匹配 SpringMVC 与 WebFlux 应用类型。）
  • @AutoConfigureAfter 排序作用？（答： 指定当前自动配置在 某些 AutoConfiguration 之后 加载，保证 Bean 依赖顺序（如 DataSource 先于 JdbcTemplate）。）

常见坑

  • 自定义自动配置未加 @AutoConfigureOrder 被覆盖。

S49. 外置 vs 内嵌 Tomcat？

口述版： Boot 默认内嵌；war 包外置 Servlet 容器部署时 SpringBootServletInitializer。

具体介绍

  • 内嵌：ServletWebServerFactory Bean。

面试追问

  • WAR 部署外部 Tomcat 时谁创建父容器？（答： 外部 Servlet 容器 创建 ServletContext；Spring 通过 SpringBootServletInitializer 启动 AnnotationConfigWebApplicationContext 作为 Web 容器子上下文。）
  • 内嵌容器端口 server.port 绑定时机？（答： WebServer 启动时 读取 Environment 中 server.port，在 ApplicationContext refresh 过程中完成绑定与 listen。）

常见坑

  • 外置部署仍打 Boot 可执行 jar 的包结构混淆。

7.8 SpringMVC 处理请求流程

S50. SpringMVC 处理请求流程（总题）

口述版： 请求进 DispatcherServlet，找 Handler、适配器执行 Controller，再解析视图或 MessageConverter 写 JSON，返回响应。对照 MVC 流程图讲。

具体介绍

  • 前端控制器模式：DispatcherServlet 统一入口。

MVC 使用篇

面试追问

  • 一个 DispatcherServlet 能否配多个 HandlerMapping？（可以，链式尝试）
  • @RequestMapping 在类与方法上如何组合？（答： 类级 path + 方法级 path 拼接；HTTP method、consumes/produces 可类/方法叠加，方法级可覆盖。）

常见坑

  • 404 是 Mapping 没找到还是 view 没找到——看日志 HandlerMapping 结果。

S51. 贯穿：DispatcherServlet → 视图协商

口述版： HandlerMapping 找处理器，HandlerAdapter 执行，返回 ModelAndView 或 @ResponseBody，ViewResolver 解析视图，ContentNegotiation 协商 JSON/HTML。

具体介绍

面试追问

  • @ResponseBody 谁调用 HttpMessageConverter？（答： RequestResponseBodyMethodProcessor 在 HandlerAdapter 中，根据 Accept/Content-Type 选 HttpMessageConverter 写 body。）
  • ContentNegotiation 根据 Accept 选 JSON/XML？（答： ContentNegotiationManager + MappingJackson2HttpMessageConverter 等；客户端 Accept 决定优先 converter，也可 produces 限定。）

常见坑

  • 返回 String 又加 @ResponseBody 与视图名混淆——走 MessageConverter 写字符串。

S52. DispatcherServlet 与 Web 三大组件？

口述版： Servlet、Filter、Listener；DispatcherServlet 是核心 Servlet。

具体介绍

初始化 Web 三大组件。

面试追问

  • Filter 与 DispatcherServlet 谁先谁后？（答： Filter 链先（Servlet 规范），再到 DispatcherServlet；Filter 可拦截静态资源，Interceptor 仅 DispatcherServlet 内。）
  • CharacterEncodingFilter 位置？（答： 通常 最前 的 Filter 之一，保证 request/response UTF-8，Boot 自动配置 Ordered.HIGHEST_PRECEDENCE。）

常见坑

  • Interceptor 里拿不到 Filter 已包装的 request wrapper 若顺序错。

S53. HandlerInterceptor vs Filter？

口述版： Filter Servlet 规范链；Interceptor Spring MVC 层，pre/post/afterCompletion。

具体介绍

  • Filter 更底层，Interceptor 可拿 Handler 对象。

面试追问

  • preHandle false 会怎样？（答： 中断 后续 Interceptor 的 preHandle，且 不调用 Controller 与 postHandle，只调 afterCompletion（已执行过的）。）
  • 多个 Interceptor 顺序 @Order？（答： 在 WebMvcConfigurer.addInterceptors 注册顺序或 Interceptor @Order；preHandle 正序，postHandle/afterCompletion 逆序。）

常见坑

  • 在 Interceptor 里抛异常未进 ControllerAdvice。

S54. @Controller vs @RestController？

口述版： RestController = Controller + ResponseBody，返回值走 HttpMessageConverter。

具体介绍

  • REST API 常用 RestController。

面试追问

  • @RestControllerAdvice 与 @ControllerAdvice？（答： RestControllerAdvice = ControllerAdvice + ResponseBody，异常处理方法默认 JSON 写回，不需视图。）
  • @PathVariable 缺失 required 默认？（答： required=true 默认；路径无该变量 400；可选变量需 {id} 配合或 required=false + 默认值。）

常见坑

  • GET 请求 @RequestBody 无 body 400。

S55. @ControllerAdvice 全局异常？

口述版： 统一 @ExceptionHandler 返回错误体。

具体介绍

  • 可配合 @ResponseStatus。

面试追问

  • @ExceptionHandler 匹配最近异常类型？（答： 匹配 抛出的异常类型 与 @ExceptionHandler 声明类型的 最近父类；多个 handler 取 最具体 匹配。）
  • 与 @ResponseStatus 组合？（答： @ExceptionHandler 方法上加 @ResponseStatus 设置 HTTP 状态码；也可在异常类上标注。）

常见坑

  • 吞掉异常不抛，全局 handler 收不到。

S56. MVC vs WebFlux？

口述版： 阻塞 Servlet vs 响应式 Netty；高并发 IO 密集可评估 WebFlux。

具体介绍

  • 多数业务 Servlet 栈足够。

面试追问

  • WebFlux 无 DispatcherServlet 用什么？（DispatcherHandler）
  • 何时坚持 MVC 栈？（答： 主流业务 Web、团队熟悉 Servlet、生态（Filter/Interceptor）成熟；阻塞 IO 足够时用 MVC，不必追 WebFlux。）

常见坑

  • 混依赖 spring-webmvc 与 webflux 导致自动配置冲突。

7.9 扩展与排查

S57. BFPP / BPP 典型实现？

口述版： BFPP：PropertySourcesPlaceholderConfigurer；BPP：AutowiredAnnotationBeanPostProcessor、AbstractAutoProxyCreator。

具体介绍

  • 理解扩展点便于排查 Bean 未注入、未代理。

面试追问

  • BeanDefinitionRegistryPostProcessor 与 BFPP 区别？（答： RegistryPostProcessor 在 标准 BFPP 之前，可直接 registerBeanDefinition 动态注册 BD；BFPP 只能改已有 BD。）
  • MyBatis MapperScannerConfigurer 属于哪类？（答： 实现 BeanDefinitionRegistryPostProcessor（或 BFPP 系），扫描 Mapper 接口 注册为 FactoryBean BD。）

常见坑

  • BPP 里改 BD 太晚——应使用 BFPP。

S58. ApplicationEvent？

口述版： 容器事件 publish/listener；@EventListener 同步默认。

具体介绍

  • 异步需 @Async + EnableAsync。

面试追问

  • @TransactionalEventListener 阶段 AFTER_COMMIT？（答： phase=AFTER_COMMIT 时 事务提交成功后 才触发 listener，避免回滚后仍处理事件。）
  • 同步 listener 异常是否回滚事务？（答： 默认同步 且在事务线程：异常 可能传播 导致回滚；AFTER_COMMIT 则在提交后，不再回滚 原事务。）

常见坑

  • 在 listener 里又发事件导致循环。

S59. @Async 原理？

口述版： BPP 或后处理生成异步代理，提交到 TaskExecutor。

具体介绍

  • 自调用同样失效。

面试追问

  • 默认 SimpleAsyncTaskExecutor 与自定义线程池？（答： 未配 TaskExecutor 时 @Async 可能用 SimpleAsyncTaskExecutor（每任务新线程，不复用）；生产应配 ThreadPoolTaskExecutor Bean。）
  • @Async 返回值 Future/CompletableFuture？（答： 返回 Future 可异步取结果；CompletableFuture 支持组合；void 则 fire-and-forget。）

常见坑

  • 异步方法 @Transactional 无效——新线程无事务。

S60. 循环依赖设计规避？

口述版： 拆分服务、事件驱动、@Lazy、构造器改 setter。

具体介绍

  • 架构上优于强依赖环。

面试追问

  • 领域事件 vs Spring Event？（答： 领域事件 是 DDD 业务概念；Spring ApplicationEvent 是 基础设施 广播机制，可在领域层定义事件类由 Spring 发布。）
  • 模块拆分后依赖方向？（答： 依赖倒置：上层依赖接口，避免 模块互引 形成环；事件/防腐层解耦。）

常见坑

  • 循环依赖靠 @Lazy 长期不 refactor。

S61. 启动失败怎么读？

口述版： 看 Caused by：NoSuchBeanDefinition、BeanCurrentlyInCreationException（循环依赖）。

具体介绍

  • --debug 看条件报告。

面试追问

  • BeanDefinitionOverrideException 如何关闭允许覆盖？（答： Boot 2.1+ 默认 禁止 同名 BD 覆盖；设 spring.main.allow-bean-definition-overriding=true 允许（慎用）。）
  • 条件不匹配日志在哪看？（答： --debug 或 logging.level.org.springframework.boot.autoconfigure=DEBUG 看 Negative matches；Actuator conditions 端点（若启用）。）

常见坑

  • 多 profile 激活错误导致 Bean 未加载误判为扫描问题。

S62. @Primary 与自动配置冲突？

口述版： 多实现时 Primary 优先注入；自动配置 OnMissingBean 避免覆盖用户 Bean。

具体介绍

  • 自定义 Bean 可覆盖 Boot 默认。

面试追问

  • @Qualifier 与 @Primary 同时存在听谁的？（答： 注入点 显式 @Qualifier 优先于 @Primary；无 Qualifier 时用 Primary 候选。）
  • Boot 默认 DataSource 与用户 Bean 覆盖规则？（答： 用户定义 同名 @Bean DataSource 且 @ConditionalOnMissingBean 自动配置让位；否则用 自动配置 的 HikariCP。）

常见坑

  • 两个 @Primary 仍启动失败。

延伸阅读： 生命周期与 AOP 见 initializeBean()、三级缓存、AOP 实现；Boot 与 MVC 见 基本使用篇、MVC 使用篇。
