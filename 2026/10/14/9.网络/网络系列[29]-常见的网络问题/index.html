网络系列[29]-常见的网络问题

发表于2026-10-14|更新于2026-10-15|9.网络
|字数总计:2.4k|阅读时长:7分钟|阅读量:

网络问题在生产系统里是最常见、最难排查、也是最容易被误判成”服务端慢”的那类问题。下面从 OSI 七层模型 + 常见生产环境场景 两个角度出发，把常见网络问题分门别类整理清楚。

常见网络问题

超时类问题

连接建立成功，但响应迟迟不回来或数据传输中断。

问题

常见报错

原因

ConnectTimeout

java.net.ConnectTimeoutException

TCP三次握手超时（目标不可达或 SYN 被丢）

ReadTimeout

java.net.SocketTimeoutException: Read timed out

连接建立成功但无响应，可能服务端慢或网关卡住

WriteTimeout

java.net.SocketTimeoutException: Write timed out

请求发送出去被阻塞（网络阻塞或服务端未读）

DNS问题

域名无法解析、解析时间长或解析错误。

  • DNS 服务器慢或异常；
  • 使用了公网 DNS（例如 8.8.8.8）而非内网 DNS；
  • Kubernetes / Docker 容器 DNS 缓存失效；
  • 域名解析频繁变化导致缓存不一致。

工具： dig, nslookup, host。

TLS/HTTPS握手慢

HTTPS 请求延迟高，但 HTTP 正常。

  • 证书链过长（多层 CA）
  • Cipher Suite 过多导致握手耗时；
  • 客户端频繁新建连接（未复用 SSL Session）
  • 证书吊销检查（CRL/OCSP）阻塞。

优化手段：

  • 启用 Keep-Alive；
  • 开启 TLS session resumption；
  • 使用 HTTP/2（多路复用）；

问题

排查思路

常见网络问题 ≈ DNS + TCP + TLS + 网关 + 跨机房 + 连接池。

排查顺序永远是：从外往内、从低层到高层、从现象到根因。

SocketTimeoutException

问题本质

java.net.SocketTimeoutException: Read timed out 是生产环境中非常常见的网络超时类问题，表示客户端成功建立了 TCP 连接，但在等待服务端响应数据时超过了指定的 read timeout 时间。

当出现该异常，意味着：

  • 客户端（你的服务）成功建立了 TCP 连接；
  • 请求已经发送给对方；
  • 但在 readTimeout 时间内未能从服务器读取到任何响应数据；
  • 最终客户端主动断开连接并抛出异常。

换句话说：

“连接没问题，数据回不来。”

可能的原因

类型

说明

服务端处理慢

服务端执行时间过长（如 SQL 慢查询、线程池满、GC 停顿）

网络传输延迟

网络抖动、跨机房延迟、NAT、负载均衡健康探测问题

客户端超时配置太短

readTimeout 太小（例如默认 1-3s）导致还没等到响应就超时

代理/网关中断

Nginx、Kong、Spring Cloud Gateway、Envoy 超时中断连接

防火墙或安全组

某些中间防火墙会丢包或 reset TCP

线程或连接池耗尽

服务端线程池、数据库连接池或 HTTP 连接池打满导致无法响应

排查思路

确认超时时间

在客户端（如 RestTemplate、WebClient、HttpClient）中检查：setReadTimeout(5000);，如果太短（< 服务端平均响应时间），请适当调大。

服务端性能问题

登录被调用的服务服务器：

  • 检查日志（请求是否被处理？）
  • 是否有长时间 GC、线程阻塞、数据库慢查询？
  • 线程池是否耗尽？
  • CPU、内存、I/O 是否过高？

典型指标：

  • HTTP access log 里没看到这次请求？可能被网关截断。
  • 看到了请求，但处理耗时很长？那是服务端处理慢。

网络路径

  • 使用 curl -v 或 telnet host port 测试目标端口是否可连；
  • 使用 ping / traceroute / mtr 检查网络延迟；
  • 如果是跨机房或跨云，重点查看 NAT 和 SLB 日志；
  • 检查 网关 / 负载均衡（如 Nginx、Kong、ELB） 是否配置了 timeout（例如 Nginx 默认 60s）。

中间件与链路追踪

使用 Zipkin / SkyWalking / OpenTelemetry 等链路追踪工具：

  • 查看调用链中哪一段耗时异常；
  • 是否某个下游服务响应过慢；
  • 确认问题发生的节点。

日志对比

  • 客户端超时时间戳 vs 服务端处理时间戳；
  • 对比请求是否真的送达；
  • 如果客户端超时但服务端仍继续执行，说明响应被卡在网络或中间层。

网络延迟

何为网络延迟

“网络延迟高” 可能来自 网络路径、服务端性能、中间层代理 或 DNS/SSL 等握手阶段。网络延迟（Network Latency）指从客户端发起请求，到服务端返回第一个字节所花费的时间（RTT — Round Trip Time）。

如果请求耗时高，但服务端处理正常（例如 < 100ms），那延迟可能发生在：

  • TCP 连接建立（慢三次握手）；
  • SSL 握手（TLS 协商慢）；
  • DNS 解析；
  • 网络传输路径（丢包、抖动、拥塞）；
  • 代理、负载均衡中转；
  • 或客户端排队等待 socket 可用。

排查思路

分层定位：是网络延迟还是服务端慢

使用链路追踪或日志：

  • 客户端耗时 vs 服务端处理耗时

  • 如果服务端日志显示处理只花了 50ms，但客户端耗时 2s → 网络问题。

  • 如果服务端日志本身处理就慢 → 性能瓶颈。

网络连通性测试

基础连通性：

  • ping <host>：查看延迟（RTT）

  • mtr <host>（Linux上非常好用）：

  • 结合 ping + traceroute

  • 检查在哪一跳延迟飙升、是否丢包

TCP层测试：

  • `telnet

`：测试端口连通性

  • curl -v -w "@curl-format.txt"：

输出如下：

  • time_namelookup：DNS解析耗时
  • time_connect：TCP握手耗时
  • time_appconnect：SSL握手耗时
  • time_starttransfer：服务器开始响应前的耗时（TTFB）
  • time_total：总耗时

检查网络路径

  • 如果请求穿过 负载均衡（ELB / SLB）：

  • 检查负载均衡是否跨可用区；

  • 查看是否有 NAT / 公网 IP 转发；

  • 确认是否经过代理（例如 Nginx / API Gateway）。

  • 如果是 跨云或跨地域：

  • 查看路由表、公网出口、VPN；

  • 尝试部署相同脚本到同地域测试延迟差异。

DNS和TLS问题

  • DNS解析慢：

  • 使用 dig <domain> 看延迟；

  • 检查本地 / 容器 / Kubernetes DNS 缓存；

  • 尝试直接访问 IP 以排除 DNS。

  • TLS 握手慢：

  • 检查证书链是否过长；

  • 查看服务端是否启用过多 cipher；

  • 若频繁新建连接，考虑开启 Keep-Alive 或 连接池复用。

应用层问题

  • HTTP连接池未复用（每次新建TCP连接）

  • 检查客户端是否设置连接池；

  • Spring RestTemplate / OkHttp 默认要启用 PoolingHttpClientConnectionManager。

  • 代理或防火墙限速

  • 检查 Nginx、WAF 是否对流量限速；

  • 某些安全组或代理会丢包、Reset。

服务端网络/资源瓶颈

查看服务端：

  • sar -n DEV 1 → 网络吞吐
  • ss -s → TCP连接状态
  • `netstat -anp | grep

` → 检查 backlog 是否满

  • dmesg | grep drop → 内核丢包
  • 检查 CPU、GC、I/O wait、线程池阻塞。
