网络系列[23]-防火墙的结构和原理

发表于2026-10-14|更新于2026-10-15|9.网络
|字数总计:2.6k|阅读时长:7分钟|阅读量:

网络包在进入互联网后通过通信线路和运营商网络到达服务器POP端之后，会继续朝着服务器前进，最终通过服务器前面的防火墙，缓存服务器，负载均衡器等等到达服务器。

主流的包过滤方式

服务器前面一般会部署一个防火墙，如果网络包无法通过防火墙，就无法到达服务器。防火墙的基本思路就是只允许发往特定服务器中的特定应用程序的包通过，然后屏蔽其他包。如何分辨哪些网络包可以通过哪些不能通过呢？目前最为普及的是包过滤的方式。

如何设置包过滤规则

网络包的头部包含了大量用于控制通信的控制信息，其中部分字段常被用于配置包过滤规则。

假设我们的网络结构如图所示：对外提供服务的服务器与公司内部网络分开部署，Web 服务器所在的网络可以被互联网直接访问。现在我们希望实现以下目标：允许来自互联网的请求访问 Web 服务器（图①），但禁止 Web 服务器主动访问互联网（图②）。

过去很少限制 Web 服务器访问外网，但随着一些能够在服务器间传播的恶意软件出现，阻止 Web 服务器访问互联网已成为一种有效的安全措施。通过这种方式，可以防止受感染的 Web 服务器进一步传播病毒或攻击其他主机。

要实现这样的访问控制，我们需要合理设置包过滤规则。首先要了解数据包的流向。通过观察数据包的发送方 IP 地址和接收方 IP 地址，我们可以判断其起点和终点。

在图①中，数据包从互联网流向 Web 服务器。来自互联网的包，其发送方 IP 地址是不确定的，但接收方是确定的，即 Web 服务器。因此，我们可以设置如下规则：允许“发送方 IP 任意、接收方 IP 为 Web 服务器地址”的数据包通过。如果能确定具体的来源地址，也可以进一步限定规则以提升安全性。这样，来自互联网的请求就能顺利到达 Web 服务器。

但仅仅允许外部访问还不够。因为当 Web 服务器收到请求后，还需要发送响应包以完成通信确认（ACK 应答等）。因此，我们还需要允许 Web 服务器向互联网发送响应包。可以设置规则：允许“发送方 IP 为 Web 服务器地址、接收方 IP 任意”的数据包通过。

通过这种方式，我们可以根据数据包的发送方与接收方地址来判断其流向，并据此灵活地设置防火墙规则，以控制数据包的通过或阻止，从而实现安全而合理的网络访问控制。

通过端口限定应用程序

按照上面的设置，相当于允许了互联网和Web服务器之间所有的包通过，这个状态很危险。假如服务器上还有其它程序在工作，那么这些程序就可能会被非法访问从而造成风险。因此我们最好是阻止除了必需服务以外的所有应用程序的包。

当我们要限定某个应用程序时，可以在判断条件中加上TCP头部或者 UDP头部中的端口号。也就是说：

  • 当包的接收方IP地址为Web服务器地址，且接收方端口号为80时，允许这些包通过。
  • 当包的发送方IP地址为Web服务器地址，且发送方端口号为80时，允许这些包通过。

如果要允许访问除Web之外的其他应用程序，则只要将该应用程序的端口号设置到防火墙中并允许通过就可以了。

通过控制位判断连接方向

目前，我们还无法直接阻止 Web 服务器访问互联网。原因在于 Web 使用的 TCP 协议是双向通信的——数据包必须在两个方向上都能发送和接收。如果简单地禁止从 Web 服务器发往互联网的包，那么来自互联网访问 Web 服务器的请求也将受到影响，通信将无法正常进行。可见，仅凭数据包的流向还不足以判断访问方向，我们需要更精确的依据。这就要用到 TCP 头部中的控制位（Flags）。

在建立 TCP 连接的“三次握手”过程中，通信双方会交换三个包。其中，第一个包的 TCP 控制位中，SYN=1 且 ACK=0；而后续的包中，这两个标志位的组合值都不同。因此，我们可以利用这一特征来识别 TCP 连接的第一个包。

如果检测到这个“第一个包”是从 Web 服务器发往互联网的，就可以将其阻止。这样，Web 服务器就无法主动发起对外的 TCP 连接。由于第一个包被防火墙拦截，对方自然也不会返回第二个响应包，TCP 连接无法建立。换句话说，只要 Web 服务器试图主动访问互联网，其连接都会在初始阶段被防火墙阻断，从而实现了“禁止 Web 服务器访问外网”的目标。

那么，这样的设置是否会影响从互联网访问 Web 服务器呢？答案是否定的。

当外部客户端访问 Web 服务器时，第一个包的接收方是 Web 服务器，因此允许通过。随后 Web 服务器返回的响应包虽然是从内部发往外部，但其 TCP 控制位不符合“第一个包”的特征，因此不会被阻止。此后通信双方的所有数据包要么属于外部发起、要么属于正常响应，都符合允许的规则，因而可以顺利通过防火墙。

通过综合判断 接收方 IP 地址、发送方 IP 地址、接收方端口号、发送方端口号以及 TCP 控制位 等条件，我们不仅能确定通信的起点与终点，还能识别通信的应用类型和访问方向。当然，除了这些字段，网络包中还有许多其他可用于过滤的特征字段。通过灵活组合这些条件并设置多条规则，我们可以逐步细化防火墙策略，实现“允许的访问能通过，不允许的访问被拦截”的目标。

然而，实际中也存在难以精确区分“允许”与“禁止”访问的情况。最典型的例子是 DNS 服务。DNS 查询使用 UDP 协议，而 UDP 不像 TCP 那样具有连接过程，因此没有控制位可供判断访问方向。也就是说，我们无法仅允许内部网络访问外部 DNS 服务器、同时阻止外部访问内部 DNS 服务。这一限制不仅适用于 DNS，对所有基于 UDP 协议的应用都同样成立。

在这种情况下，只能在安全性与可用性之间权衡：要么冒一定风险，允许该应用的所有包通过；要么牺牲一定的便利性，彻底阻止此类通信。

从公司内网访问公开区域的规则

在上图所示的网络结构中，我们不仅需要在互联网与公开区域（DMZ）之间设置包过滤规则，还应当在公司内网与互联网之间、以及公司内网与公开区域之间配置相应的过滤规则。

需要特别注意的是，这些规则之间不能互相干扰。例如，如果希望公司内网与公开区域之间的网络通信能够自由进行，我们可能会设置一条规则：允许所有接收方 IP 地址为公开区域的包通过。然而，如果这条规则没有进一步限定发送方 IP 地址，那么来自互联网的包也会被错误地允许进入公开区域，导致公开区域内的服务器暴露在外部威胁之下。

因此，在编写包过滤规则时，必须谨慎规划、明确边界，确保不同区域之间的访问控制互不冲突，既满足业务通信需求，又不降低整体安全性。

此外，包过滤型防火墙不仅具备控制数据包通行的能力，还支持 地址转换（NAT） 功能。因此，在互联网与公司内网之间传输数据包时，还需要进行地址转换设置。只有完成相应的 NAT 配置，数据包才能在不同地址空间之间正常传递。

防火墙无法抵御的攻击

防火墙可以根据数据包的起点和终点来判断是否允许其通过，但仅凭这些信息并不能筛选出所有存在风险的包。举例来说，假设某个 Web 服务器在接收到包含特定数据内容的包时会发生宕机。由于防火墙只关注包的来源和目的地址，即使该包中含有触发宕机的特定数据，防火墙也无法识别其危险性，从而仍会放行该包。结果，当数据包抵达 Web 服务器时，就可能导致系统崩溃。要识别并防御这种类型的攻击，必须检查数据包的实际内容，而这超出了传统包过滤防火墙的能力范围。

针对这种问题，通常有两种应对方式：

  1. 修复漏洞。
  2. 部署能够检测数据内容的安全设备或软件。

不过，在实际环境中，如果服务器数量较多、软件版本更新周期较长，或者存在更新维护不及时的情况，那么部署具备内容检测能力的安全防护设备（如 IDS/IPS）仍然是非常有效的补充手段。它可以在漏洞修复前提供一定程度的防御，降低系统暴露于攻击的风险。
