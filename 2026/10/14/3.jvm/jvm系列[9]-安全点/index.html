jvm系列[9]-安全点

发表于2026-10-14|更新于2026-10-15|3.jvm
|字数总计:834|阅读时长:2分钟|阅读量:

在 Java 虚拟机（JVM） 中，垃圾回收（GC） 需要遍历所有存活对象，并回收无用对象。但是，JVM 线程是多线程并发执行的，而对象的引用关系会不断变化，因此在 GC 过程中不能随意扫描堆内存，否则可能导致：

  • 对象引用发生变化（导致 GC 标记错误）。
  • 正在执行的方法修改了对象（破坏 GC 过程）。
  • 并发修改导致崩溃（GC 访问无效指针）。

因此，JVM 需要在 GC 扫描对象引用之前，确保 所有 Java 线程都处于一个稳定状态，这就引入了 Safepoint（安全点）。

Safepoint 是 JVM 允许 GC 或其他全局操作执行的一个特殊状态。当 GC 需要执行时，JVM 会让所有 Java 线程暂停并进入 Safepoint，这样就能确保 堆中的对象引用关系不会改变，从而安全地进行 GC Root 枚举和对象回收。

最早期的 JVM 采用 抢占式暂停（Preemptive Suspension），即：

  • 当 GC 发生时，JVM 直接强行暂停所有线程。
  • 但在 现代多线程环境 下，JVM 无法直接暂停本地线程（如 Native Code 或 JNI 调用），导致某些线程可能无法及时响应 GC，影响垃圾回收的效率。

因此，JVM 逐步改用主动式中断（主动轮询） 机制。

HotSpot 通过以下方式实现主动轮询：

  • 在 JIT 编译的代码中插入 Safepoint Polling 指令

  • JIT 编译时，在特定的位置插入 Safepoint Polling 代码，让线程主动检查是否应该暂停。

  • 在解释器（Interpreter）中加入 Safepoint 轮询

  • 解释执行的 Java 代码 也会在方法调用、循环回边等地方插入 Safepoint 轮询。

  • 某些 Java 方法隐式触发 Safepoint

  • 对象分配（如 new 操作）

  • 方法调用

  • 线程睡眠或阻塞（如 Thread.sleep()、wait()）

  • 异常抛出

  • 同步代码块（synchronized）

当 GC 需要执行时，JVM 采用以下流程：

  1. GC 线程通知所有 Java 线程** 进入 Safepoint。**
  2. Java 线程主动检查****（通过 Safepoint Polling）。
  3. 已经在 Safepoint 的线程立即暂停****，未进入 Safepoint 的线程会继续执行到最近的 Safepoint 位置再暂停。
  4. 所有线程暂停后，GC 开始执行。

当垃圾回收需要进行时，GC 线程会要求所有用户线程进入安全点。若某个线程正在执行 JNI 方法，它可能无法进入安全点，因为 JNI 代码通常不包含 JVM 中的安全点（除非开发者显式地将 JNI 方法标记为允许 GC 中断的地方）。因此，GC 线程和已经到达安全点的其他用户线程会被迫等待，直到这个线程完成 JNI 调用，进入安全点为止。

这种情况可能会导致 停顿（停顿时间延长），因为 GC 的启动被延迟，直到所有线程进入安全点。为了减少这种延迟，现代 JVM 会尝试通过各种优化措施来减少依赖 JNI 的线程阻塞 GC 的时间，例如使用混合垃圾回收器（如 G1 GC）和一些非阻塞的 GC 策略。
