jvm系列[3]-G1垃圾收集器

发表于2026-10-14|更新于2026-10-15|3.jvm
|字数总计:2.8k|阅读时长:9分钟|阅读量:

G1 的发展历程

  • Java 6：G1 收集器进入实验状态。
  • Java 7：G1 收集器移除实验标识，成为正式可用的 GC。
  • Java 8：G1 收集器新增并发类卸载支持，被 Oracle 称为“全功能垃圾收集器”。
  • Java 9：G1 收集器取代 Parallel Scavenge + Parallel Old 组合，成为服务端模式下的默认 GC。

G1 的核心机制

G1 的核心目标是建立可预测的停顿时间模型，即：在一个 M 毫秒的时间片内，GC 运行时间大概率不超过 N 毫秒。

1. 摆脱传统分代收集理论

G1 并未严格遵循分代收集模型，而是对整个 Java 堆进行分区，以回收收益而非代际归属来决定垃圾回收的优先级。这种策略被称为 Mixed GC 模式，即在回收年轻代的同时，可能会选择部分老年代进行回收，以提高 GC 效率。

2. Region 分区管理

G1 将 Java 堆拆分成多个大小相等的独立区域（Region），每个 Region 可动态分配为 Eden、Survivor 或 老年代。
此外，G1 还引入了一类特殊的 Region——Humongous Region，用于存储大对象（超过单个 Region 一半大小的对象）。如果大对象超出了单个 Region 容量，它们会占用多个连续的 Humongous Region，并被视为老年代的一部分。

✅ Region 关键特性：

  • 可调大小：默认范围为 1MB ~ 32MB，必须是 2^N。
  • 灵活分配：不同 GC 阶段下，Region 角色可动态变化。

3. 停顿时间可控的优先回收策略

G1 采用 增量式回收，通过跟踪每个 Region 的垃圾占比和回收成本，构建优先级列表。
在 GC 过程中：

  1. 计算回收收益（垃圾占比 × 预估回收时间）。
  2. 在允许的最大停顿时间（默认 200ms）内，优先选择回收收益最高的 Region 进行回收。

这一策略保证了 G1 在有限停顿时间内获得尽可能高的回收效率，避免传统 GC 由于大规模回收导致的长时间 STW（Stop-The-World）。

4. 记忆集（Remembered Set）优化跨 Region 引用

  1. 年轻代的卡表（Card Table）

  • 位置：存在于 年轻代，但它可以视作一种特殊的记忆集。

  • 功能：记录 老年代 对年轻代对象的引用。

  • 在年轻代的每个区域中，G1使用 卡表 来快速追踪 老年代对象 对年轻代对象的引用。卡表通过将老年代对年轻代对象的引用记录在卡片中，减少了年轻代回收时对老年代的扫描需求。

  • 每次老年代的对象引用了年轻代的对象时，G1会在卡表中标记相应的卡片，这样在进行年轻代的垃圾回收时，G1能够有效地知道哪些年轻代区域需要检查，以清理相关引用。

  1. 老年代的记忆集（Remembered Set）

  • 位置：存在于 老年代 中，每个老年代的 区域（Region） 都维护一个记忆集。

  • 功能：记录 其他区域对该区域内对象的引用。

  • 每个老年代区域维护一个自己的记忆集（本质上是一个哈希表结构），记录其他老年代区域对该区域内对象的引用。假设老年代的区域A中的某个对象被区域B的对象引用，区域A的记忆集就会记录这个引用。

  • 这样，在进行老年代的垃圾回收时，G1能够只关注记忆集中的引用，而不必重新扫描整个老年代的所有区域，避免不必要的性能开销。

  1. 综合回收机制

  • 年轻代和老年代的协同工作：G1垃圾收集器通过卡表和记忆集结合，优化了跨代、跨区域引用的回收工作。

  • 卡表 主要处理 年轻代 和 老年代 之间的引用，帮助G1快速定位老年代中引用年轻代的区域。

  • 记忆集 在 老年代 内部处理跨区域引用，确保在进行混合回收时（即同时回收年轻代和部分老年代时），G1能够高效地清理各个老年代区域之间的引用，避免重复扫描。

✅ 记忆集的改进：

  • 采用双向卡表（卡页粒度），不仅记录“我指向谁”，还记录“谁指向我”，提升查询效率。
  • 更高的内存占用，但避免全堆扫描，提高并发 GC 效率。

5. 并发标记与 TAMS 机制

在并发标记阶段，G1 采用原始快照（SATB, Snapshot-At-The-Beginning）技术，保证 GC 线程和用户线程互不干扰：

  1. TAMS（Top-at-Marked-Start）指针：将部分 Region 预留给新对象，确保回收期间仍可分配新对象，这两个指针地址以上的新对象默认存活。
  2. 写前屏障（Write Barrier）：跟踪对象引用变化，避免影响并发标记精度。
  3. 避免 Full GC：如果新对象分配速度超过 GC 回收速度，会导致 Full GC STW，影响性能。

G1 的停顿预测模型

G1 采用衰减均值算法，对 GC 过程中各个阶段的耗时进行统计分析（如回收时间、脏卡数量等）。

✅ 停顿预测逻辑：

  1. 记录每次回收的 Region 回收时间，计算移动平均值和置信区间。
  2. 衰减均值使近期数据权重更高，提供更准确的预测。
  3. 基于用户设定的停顿时间（默认 200ms），动态调整回收目标，在不超过设定停顿时间的前提下，回收收益最高的 Region。

注意：

  • 设定过低的停顿时间会导致单次回收区域过少，GC 速度跟不上对象分配，最终触发 Full GC，影响整体性能。
  • 默认 200ms 一般是合理的阈值，可根据业务需求调整。

G1的运作过程

G1 主要有三种 GC 过程：

  • 年轻代回收（Young GC）
  • 老年代回收（Mixed GC）
  • Full GC

下面分别介绍这三种 GC 过程的详细步骤。

1. 年轻代回收（Young GC）

年轻代回收主要用于清理 Eden 和部分 Survivor 区域，通常在 Eden 空间填满时触发。它是 STW（Stop-The-World） 事件，但因为只扫描年轻代，停顿时间通常较短。

执行过程：

  1. 根可达性分析（Root Scanning）
  • 遍历 GC Roots（如线程栈、本地变量、静态字段等），找到可达对象。
  • 由于年轻代回收不涉及老年代，只扫描 RSet（记忆集）中标记的部分。
  1. 复制存活对象（Evacuation）
  • Eden 中的存活对象 复制到 Survivor 区（S0 或 S1）。
  • Survivor 区存活次数超过阈值的对象 可能会晋升到 老年代。
  • 大对象直接晋升到老年代（如果 -XX:G1HeapRegionSize 限制未满足，会触发 Full GC）。
  1. 更新 RSets（Remembered Set）
  • 维护跨 Region 的引用关系，避免下一次 GC 需要扫描整个老年代。
  1. 清理 Eden
  • 回收 Eden 区域的所有未被引用的对象，Eden 重新变为空。

特点：

  • 只处理年轻代，停顿时间短。
  • Eden 为空，Survivor 轮换。
  • 部分对象晋升到老年代，可能触发 Mixed GC。

2. 老年代回收（Mixed GC）

老年代的对象不会被 Young GC 回收，而是由 Mixed GC 处理。Mixed GC 是 G1 GC 特有的 GC 过程，它既回收 年轻代，也部分回收 老年代（但不是全部）。

​

触发条件：

  • **老年代使用超过 **-XX:InitiatingHeapOccupancyPercent（默认 45%）
  • 触发后，G1 进入 并发标记周期，之后会执行 Mixed GC

​

执行过程：

  1. 并发标记（Concurrent Marking）
  • 这个阶段和 CMS（Concurrent Mark-Sweep）类似，G1 采用 SATB（Snapshot-At-The-Beginning） 进行并发标记。
  • 标记存活对象，同时应用仍在运行（不会 STW）。
  • 标记过程中，会维护老年代 Region 的 回收优先级（垃圾最多的 Region 最先回收）。
  1. 最终标记（Final Remark，STW）
  • 由于并发标记过程中对象可能发生变化，因此需要短暂停顿来处理 剩余的引用变更。
  1. 筛选回收集（Cleanup）
  • 确定要回收的老年代 Region，并计算回收收益（垃圾比例高的 Region 先回收）。
  1. 混合回收（Mixed GC，STW）
  • 执行 Young GC 回收年轻代（和 Young GC 一样的过程）。
  • 同时回收部分老年代 Region（回收最垃圾最多的部分）。
  • 被清理的 Region 可能重新变为 Eden，提升内存利用率。

特点：

  • 年轻代 + 老年代 的组合回收。
  • 不会回收整个老年代，而是按 Region 回收，避免长时间停顿。
  • 随着回收次数增加，老年代的存活对象越来越多，当无法跟上分配速度时，可能触发 Full GC。

3. Full GC

如果 G1 GC 发现老年代无法通过 Mixed GC 及时回收，或者堆空间耗尽，会触发 Full GC。
Full GC 会 暂停所有应用线程（STW），并执行 整个堆的垃圾回收，通常由 Serial Old GC 处理。

执行过程：

  1. STW（Stop-The-World）
  • 暂停所有应用线程，避免对象状态变化。
  1. 标记存活对象（Marking）
  • 扫描整个堆（年轻代 + 老年代），标记所有存活对象。
  1. 整理对象（Compaction）
  • 复制存活对象 到新的连续区域（避免碎片化）。
  • 释放回收的空间。
  1. 更新对象引用
  • 由于对象位置可能变化，更新所有对象的指针。
  1. 释放空闲空间
  • 清理无用的 Region，恢复堆的可用空间。

特点：

  • 最慢的 GC 过程，会导致 长时间停顿，影响应用性能。
  • 会压缩内存（Compaction），减少碎片。
  • 如果 Full GC 频繁发生，说明 G1 GC 无法及时回收老年代，可能需要调整参数。

G1 的整体设计取向

  1. 优先保证吞吐量和响应时间的平衡，不再追求“一次清理整个堆”，而是确保GC 回收速度跟得上对象分配速度。
  2. 整体上基于标记-整理算法，避免内存碎片问题，提升堆利用率。
  3. 局部采用标记-复制算法，保证 Survivor 与老年代之间的对象移动高效。

G1 的执行负载与开销

尽管 G1 具备可控停顿时间和更高的回收效率，但其内存占用和执行负载比传统 GC 更高：

  • 内存占用更大：由于更复杂的卡表结构和记忆集，G1 需要更多的内存用于维护 GC 元数据。
  • 写屏障开销：G1 需要写前屏障（SATB）和写后屏障（卡表维护），引入额外的 CPU 开销。
  • 写屏障优化：G1 采用消息队列机制，将写前/写后屏障任务异步处理，减少对应用线程的影响。

总结

✅ G1 适用于：

  • 需要稳定停顿时间的应用（如 Web 服务器、交易系统）。
  • 大堆内存（数 GB 以上），Parallel GC 无法有效管理的场景。

🚫 G1 可能不适合：

  • 低内存环境（G1 本身占用的GC 元数据较多）。
  • 超低延迟场景（如 ZGC 或 Shenandoah 可能更优）。

从 G1 开始，现代 GC 的设计方向已经转变为追求适应应用分配速率，而不是“一次性清理整个堆”。只要GC 速度跟得上对象分配速度，应用就可以平稳运行。
